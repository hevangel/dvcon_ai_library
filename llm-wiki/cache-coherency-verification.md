# Cache Coherency Verification

> *"Cache coherency is the topic that has haunted every multi-core SoC team since roughly 2010. Get it wrong and you don't get a crash — you get silent data corruption, the worst class of bug, the kind that lands in field returns and security advisories. Cavium knew this when they taped out their 48-core server chip and made cache coherency the central pre-silicon challenge, asking Breker to automatically generate the multi-SoC test cases no human could write by hand [Using Portable Stimulus to Verify Cache Coherency in a Many-Core SoC, 2016]. The reason it is so hard is structural: the protocol lives in a state machine (MESI, MOESI, or its many successors) that has to be exercised across every master, every cache line, every memory channel, and every legal interleaving — a space that grows combinatorially with cores and is invisible to directed tests. By 2025 MediaTek was combining Perspec, CPU VIP, and CHI VIP to catch corner RTL issues that cause system hangs and performance bottlenecks, and Samsung was extending the problem to multi-die UCIe chiplets where coherency now has to survive crossing a die boundary [Expedite multi-die coherency verification through adaptive VIP subsystem, 2025]. So what's actually going on under the hood of cache coherency verification, and why does the field keep inventing new tool flows for it? Let's dig in."*

## What it is

A **cache coherency protocol** is a state machine that guarantees every master in a shared-memory system observes a consistent view of memory. The protocol tags each cache line with a state — **M (Modified), O (Owned), E (Exclusive), S (Shared), I (Invalid)** in MOESI, with MESI dropping the Owned state. When a master reads or writes, the protocol defines what snoop, intervention, and data-transfer transactions must occur on the coherency fabric, and each transaction can fan out across multiple channels (Request, Snoop, Response, Data) executed out of order — a vast space where each opcode's lifecycle involves many permutations of state, channel flow, and agent interaction [From Specification to Closure: A Semi-Automated Coverage-Driven Verification Methodology for Cache Coherent Home Nodes, 2026]. Modern coherency fabrics are spelled out as protocols like ARM **ACE** and its successor **AMBA CHI**, and the **Home Node (HN)** is the coherence authority that has to handle every interaction reliably while adhering to MOESI semantics [From Specification to Closure: A Semi-Automated Coverage-Driven Verification Methodology for Cache Coherent Home Nodes, 2026].

The verification problem is doubly hard because the protocol behavior is invisible at the CPU's instruction boundary. A single load instruction might trigger a snoop across multiple caches, a writeback, and an L3 update — and the order in which these complete is non-deterministic. Ikram, Akkawi, and Kessler learned this firsthand building Cavium's multichip coherence interconnect protocol (OCI), where they had to combine formal and simulation tools across discovery, design, modeling, and validation phases, finding both design bugs and holes (missing features) along the way [Design and Verification of a Multichip Coherence Protocol, 2015].

## How it's used in practice

The dominant production pattern today is **Portable Stimulus (PSS)** for stimulus generation combined with a coherency-aware scoreboard. Hamid, Koogler, and Anderson at Breker (working with Cavium) abstracted the test case requirements into a graph-based scenario model that captures all intended cache behavior including the underlying MOESI protocol, then auto-generated self-checking tests runnable on every verification platform — RTL sim, emulation, and post-silicon [Using Portable Stimulus to Verify Cache Coherency in a Many-Core SoC, 2016]. Jang, Kim, and Chung at Samsung/Cadence applied the same PSS recipe (using Perspec) to both coherency and deadlock avoidance for an automotive/mobile SoC with multiple processor cores and multi-level cache hierarchy, configuring it from tables of processor clusters (MO, AP, A72) and memory blocks (DDR0, DDR1, DDR2) [Coherency Verification & Deadlock Detection Using Perspec/Portable Stimulus, 2019]. The newest evolution is hybrid: Xiao, Yao, and Chen at MediaTek combine Perspec for scenario generation, CPU and **CHI VIP** for protocol-accurate stimulus, and a system verification scoreboard to catch both functional bugs and performance issues, with inheritable sequences that let the same test stimuli be reused across projects [A Hybrid Verification Approach for Cache Coherent Systems: Functionality and Performance, 2025].

For UVM-only shops, the ACE extension to UVM has been the workhorse since 2012: Luo, Varghese, and Goel showed how UVM's configuration mechanism enables the reactive sequences and high configurability needed to validate system-level coherency and all cache line state transitions across ACE masters [ACE'ing the Verification of a Coherent System Using UVM, 2012]. Kumar, Mattu, and Nilipour extended that to coherent heterogeneous multiprocessors with optimized power consumption, where the stimulus must be "random, yet coherent" — a constraint the solver has to honor [Ace'ing the Verification of SOCs with Cache Coherent Heterogeneous Multiprocessors Targeted for Optimized Power Consumption, 2016]. Misra, Rao, and Kumar at Samsung showed how a configurable, flexible, portable testbench can achieve at least **5X faster** cache verification at SoC level than traditional CPU-hosted memory-access scenarios [Building Confidence in System level CPU Cache Coherency Verification for Complex SoC's through a Configurable, Flexible and Portable Testbench, 2022]. And for multichip scenarios, Thottathil used PSS to verify CXL — the cache-coherent fabric layered on PCIe that maintains coherency between CPU memory and CXL-attached device memory [CXL Verification using Portable Stimulus, 2024].

## Pitfalls and where the field is heading

The classic pitfall is **deadlock**. Jang et al. walked through a concrete example: a CPU cluster saturates the PCIe RC's non-posted request channel with reads, then can't issue a config write, then a writeback of address A blocks the write channel, then a PCIe endpoint issues a `ReadOnce` for A which triggers a snoop to the CPU that can't proceed because of the outstanding WriteBack — deadlock [Coherency Verification & Deadlock Detection Using Perspec/Portable Stimulus, 2019]. Catches like this require modeling the system at the protocol level, not the unit level. A second pitfall is **concurrent modeling**: when multiple actors can simultaneously modify and read the same memory location, it may not be feasible to predict the precise value a read will observe — Parameswaran built a framework around a "window of uncertainty" that stores all potential write values and prunes incoherent ones over time [Modeling Memory Coherency during concurrent/simultaneous accesses, 2022].

The field is heading in two visible directions. First, **multi-die coherency** through UCIe: Kumar, Kashide, and Srivastava at Samsung built an adaptive VIP subsystem where a UCIe VIP communicates internally with CXS through callbacks, enabling a homogeneous or heterogeneous multi-chiplet SIP to maintain a coherent view of memory across dies [Expedite multi-die coherency verification through adaptive VIP subsystem, 2025]. Second, **coverage-driven closure for CHI Home Nodes**: Rajendran, Soosai, and Dhamanwala built a semi-automated CDV methodology specifically targeting the HN's handling of MOESI semantics across out-of-order Request/Snoop/Response/Data channels [From Specification to Closure: A Semi-Automated Coverage-Driven Verification Methodology for Cache Coherent Home Nodes, 2026]. And underneath all of it, Gordon Allan's 2011 observation still holds: multi-core SoCs are a "time of transition, and not without risk," and shared-memory coherency practice is still being written [Verification Patterns in the Multicore SoC Domain, 2011]. Cache coherency verification isn't getting easier — it's getting broader, more parallel, and increasingly multi-die.
