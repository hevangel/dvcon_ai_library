# Side-Channel and Physical Security Verification

> *"Crypto on silicon doesn't fail because the math is wrong — the math is public and proven. It fails because the chip leaks. Power draw during a multiply, EM radiation off a serdes lane, the precise nanoseconds a memory read takes — each is a side channel, and a patient attacker with an oscilloscope and a few thousand traces can pull your 256-bit key out of any of them. Defending against this is fundamentally different from functional verification: you are not proving the design does what it should, you are proving it does *not* do what it must not, against an adversary who is smarter than your testbench. DVCon's corpus on this is younger and thinner than on functional safety — there is no ISO 26262 equivalent handing you a checklist — but the shape of the problem is becoming clear: threat-model the assets, verify the countermeasures with the same static and dynamic machinery you use for functional bugs, and fold safety fault injection together with security fault injection because the attacker and the cosmic ray exploit the same silicon. So what does pre-silicon physical-security verification actually look like today? Let's dig in."*

## What it is

**Side-channel and physical security verification** is the discipline of verifying that a chip does not leak secret-dependent information through unintended physical channels — power (DPA/CPA), electromagnetic radiation, timing, or fault-injection-induced misbehavior — and that its tamper and access-control countermeasures actually hold under attack. The first principle, articulated in Marvell's recent pre-silicon work, is that "traditional functional verification alone is insufficient to detect subtle security flaws that adversaries may exploit through physical, firmware, or protocol-level attacks" [Security Verification in Practice, 2026]. Where functional verification asks *does it work*, security verification asks *does it betray* — and the threat model, not the spec, drives the verification plan.

The organizing abstraction is **threat modeling** tied to assets. The IEEE P3164 SA-EDI (Security Annotation for Electronic Design Integration) standardization effort formalizes this: "threat modeling systematically identifies vulnerabilities, while secure design principles and features are implemented to counter them throughout the chip's lifecycle," and the standard provides specifications to integrate threat modeling into SoC security design and integration [Threat Modeling for SoC Security Design, 2026]. Once assets (keys, firmware, privileged state) and adversaries (physical, firmware, protocol) are named, countermeasures — masking, randomization, access control, redundancy, sensors — become verification targets in their own right. The security verification task is then to prove those countermeasures hold, and that no information flow violates the asset confidentiality model.

## How it's used in practice

The practical pattern is a **static-plus-dynamic pre-silicon security flow**, run before synthesis. Kumar and Maitra's Marvell framework combines security-focused linting to catch security-sensitive weaknesses in RTL with **dynamic information flow tracking (DIFT)** to ensure asset confidentiality — the same shape as a functional lint-plus-sim flow, retuned for security properties [Security Verification in Practice, 2026]. The discipline borrows directly from the functional world: where functional verification uses coverage to prove requirements were hit, security verification uses DIFT taint propagation to prove secrets never reach untrusted outputs. Physical access control is verified similarly — Wang, Li and Li verify RISC-V **Physical Memory Protection (PMP)**, which restricts shared memory and system resources to privileged agents, using Portable Stimulus (PSS) and Perspec to enumerate the privilege combinations an attacker might try [RISC-V Security Verification using Perspec/Portable Stimulus, 2023].

**Fault injection sits at the safety/security seam.** Sai Kumar, Mazzawi and Mouallem make the case explicitly: automotive chips must counter cyber-security attacks aimed at extracting secret assets *and* meet ISO 26262 safety metrics, and "while determining the Safety Integrity Level for automotive semiconductor hardware, it's also important to consider how that failure can be influenced by adversaries" using fault-injection attack methods [Fault Injection Analysis for Automotive Safety and Security, 2022]. The same fault-campaign machinery that proves a safety mechanism catches a random bit-flip can be re-pointed to model an attacker deliberately injecting a fault to bypass a countermeasure — the difference is intent, not physics. So a modern security verification flow reuses the fault-injection netlist, the emulation platform, and the diagnostic-coverage math, then asks the security question on top.

Where the physical-channel side (DPA/CPA trace capture, EM probes) enters pre-silicon, it does so through **power-aware modeling**: power consumption is the side channel, so power-aware simulation is the verification vehicle. The CPAS Cocotb Power Aware Simulation Framework — built for open-source PA simulation with Python — lets engineers specify power intent and drive domain corruption, retention, and isolation, providing exactly the per-cycle supply-state visibility a leakage analysis needs, without a commercial PA simulator [CPAS: Cocotb Power Aware Simulation Framework, 2024]. Highly configurable IP verification also has to grapple with optional security capabilities (e.g., PCIe DPA — Design Pattern Access in that context) that change the attack surface per configuration, so the security verification has to track the configuration space too [Managing Highly Configurable Design and Verification, 2018].

## Pitfalls and where the field is heading

The central pitfall is **immaturity of the methodology and the gap between pre-silicon and the lab.** Unlike functional safety, there is no dominant standard telling you which artifacts to produce; threat models are still being codified (IEEE P3164 is the active effort) [Threat Modeling for SoC Security Design, 2026]. DPA/CPA in particular are hard to predict pre-silicon — gate-level power leakage depends on parasitics and post-layout behavior that RTL DIFT cannot see — so a chip that looks clean in static security analysis can still leak on the oscilloscope. The second pitfall is **treating safety and security as separate flows**: the same injected fault that defeats a safety mechanism can defeat a security countermeasure, and running two disconnected campaigns wastes effort and misses cross-effects [Fault Injection Analysis for Automotive Safety and Security, 2022]. A third, quieter pitfall is VIP and tool qualification under a security lens — a verification IP that silently misses an illegal access is as dangerous as a functional VIP that silently misses a bug.

The field is heading toward **integrated, threat-model-driven pre-silicon security verification**, borrowing shamelessly from functional and safety flows. The trajectory is visible in three moves: threat modeling formalized as machine-readable annotations integrated into design (SA-EDI) so security properties are first-class RTL citizens [Threat Modeling for SoC Security Design, 2026]; static-plus-DIFT pre-silicon analysis becoming standard practice alongside functional lint [Security Verification in Practice, 2026]; and fault-injection campaigns unifying the safety and security questions on one emulation platform [Fault Injection Analysis for Automotive Safety and Security, 2022]. The honest caveat is that DVCon's coverage of pure side-channel analysis — DPA trace capture, EM emanation modeling, tamper sensor verification — is still sparse; the bulk of the corpus addresses the verification of countermeasures and access control rather than the leakage physics themselves. Expect that to change as automotive, IoT, and AI-accelerator security requirements push physical-channel verification from a lab discipline into the pre-silicon flow.
