# Software-Driven Verification and Firmware Bring-Up

> *"At some point the UVM testbench stops being the real test. The real test is whether Linux boots, whether U-Post enumerates the PHY, whether the bootloader can pull a signed image over PCIe and hand off to the kernel without dropping a single byte. That is software-driven verification, and it has quietly become the longest pole in the tent for SoC teams. Chan and Watt put it bluntly in 2019: Android boot, Linux boot, MISRA-C production firmware — all of it now runs in emulation *before* silicon exists, and the team that did it reported 'the smoothest FW/SW bring up in the company's history for a Rev A device' [How to test the whole firmware/software when the RTL can't fit the emulator, 2019]. The shift is structural: firmware engineers and verification engineers used to meet at tapeout. Now they meet six months earlier, staring at the same emulator, arguing over whether the bug is in the C or the RTL. So what's actually going on under the hood?"*

## What it is

**Software-driven verification** means running real embedded firmware or operating-system code — bootloaders, drivers, bare-metal tests, full Linux — as the stimulus for the DUT, usually on an emulator, virtual platform, or FPGA prototype. Ballance's 2015 paper framed the field precisely: "software-driven hardware verification is growing in importance for verifying interactions between hardware and low-level software in today's complex SoC designs," and the gap was that "similar verification-focused frameworks don't exist to boost productivity in creating embedded software-driven tests" the way UVM did for transaction-level testbenches [Jump-Start Software-Driven Hardware Verification with a Verification Framework, 2015]. The test is no longer a sequence of `uvm_sequence_item`s; the test is a C function that writes memory-mapped registers and reads them back.

The bring-up itself follows a strict sequence. Gummadidala, Sahoo and Kashide describe the boot chain end to end: the BootROM (a small mask ROM or write-protected flash) "is responsible for executing the first code when system is powered-up or reset," fetching bootloader images from external devices, authenticating them with on-chip AES and SHA, and placing them in system RAM [Novel Approach for Verification of Multi Die Booting Using Disruptive Distributed Simulation Methodology, 2025]. Verifying that chain — BootROM, BL1, BL2, BL33, kernel — is the canonical software-driven test, and each stage has its own hazards: a wrong offset in the BootROM can brick every die. Jünger, Weinstock and Leupers make the scale argument: even small embedded systems "execute complex software stacks consisting of millions of lines of code," so the simulator has to be fast enough to reach the interesting state before the calendar runs out [SIM-V Fast, Parallel RISC-V Simulation for Rapid Software Verification, 2022].

## How it's used in practice

The dominant platform is **emulation**, and the dominant pain is that the RTL rarely fits. Chan and Watt's Hybrid Software Simulator (HSWSIM) is the canonical answer: blackbox the unused subsystems, run the production FW/SW on an x86 Linux host, and bridge register accesses to the emulator over PCIe with a TCP mailbox standing in for the chip's native mailbox [How to test the whole firmware/software when the RTL can't fit the emulator, 2019]. The payoff isn't just coverage — they could debug the FW in GDB on the host while the RTL ran in the emulator, and mix "bits and pieces of configuration code in the FW and the VerTB" to localize faults. De Luigi and Ogheri applied the same instinct to a TCL-driven firmware verification environment, borrowing UVM concepts to "reduce test creation and update times in a hardware/software co-design environment" [Integration of modern verification methodologies in a TCL test framework, 2015].

Virtual platforms carry the work earlier in the schedule, before RTL is mature. Jünger et al.'s **SIM-V** targets RISC-V specifically, attacking the "reduced VP simulation performance" that bottlenecks software verification [SIM-V Fast, Parallel RISC-V Simulation for Rapid Software Verification, 2022], and the same group later profiled a "Level 4 vECU" built on QEMU and SystemC TLM for faster ISO 26262 testing of an automotive gateway [Profiling and Optimization of Level 4 vECU Performance for faster ISO26262 Testing, 2024]. Ciaglia, Winkler and Kundrata show the bring-up view from a sensor SoC team: an ARM Cortex-M plus firmware plus co-verification environment, with unified debug across the whole development lifecycle [Unified Firmware Debug throughout SoC Development Lifecycle, 2022]. And Zachariasova et al. show how a reusable UVM skeleton can grow from block-level to "the whole System on Chip (SoC), including the HW-SW co-verification with firmware" without rewriting the env [A UVM Test-bench Skeleton Leveraging the Event Pool and Sequence Layering, 2023]. Formal is creeping in too: Olmos, Sainath and Kunz automate firmware formal verification against ISO 26262-6 software criteria [Automating the Formal Verification of Firmware, 2024], and a companion paper uses MC/DC plus formal to prove unreachable paths in hardware-dependent software [A Novel Approach in Proving Unreachable Paths in Hardware-dependent Software, 2024].

## Pitfalls and where the field is heading

The biggest pitfall is **attribution**. When FW meets RTL in emulation, the FW is often more stable than the RTL, and a failure can sit in either. Chan, Mbaye and Ang dedicated a whole paper to the triage problem: "sometimes it is very hard to determine whether the issue is originated in the software code or the hardware code," and the fix is a deliberate set of SW/HW co-verification utilities plus reuse of the emulation debug flow for post-silicon [Is it a software bug? Is it a hardware bug?, 2022]. A second pitfall is **capacity**: the RTL won't fit the emulator, and blackboxing has its own traps because "blackboxing a block of RTL at compile time might be trivial, but" downstream assumptions about register accesses break [How to test the whole firmware/software when the RTL can't fit the emulator, 2019]. A third is **performance**: a slow VP never reaches the boot stage that matters, which is what drives the QEMU/TLM and parallel-RISC-V work [SIM-V..., 2022; Profiling and Optimization of Level 4 vECU..., 2024].

The field is heading toward earlier, faster, and more formal software verification. Multi-die boot — once a post-silicon lab exercise — is now done pre-silicon with distributed simulation, with BootROM and secure-boot authentication verified before any die is packaged [Novel Approach for Verification of Multi Die Booting..., 2025]. Feasibility studies let teams evaluate a RISC-V core swap against real-time requirements using a virtual prototype, "to detect possible issues early in the replacement process" before committing silicon [Evaluating the feasibility of a RISC-V core for real-time applications using a virtual prototype, 2022]. And LLMs are starting to sit inside the loop: Jose's passive token-accounting work shows continuous verification workflows where LLMs summarize logs and cluster failures, with the operational cost of those calls becoming a tracked metric [Passive Token Accounting For Cost-Aware LLM Assistance In Continuous SoC Verification Workflows, 2026]. The unifying arc is that firmware is no longer the thing you test after the chip — it is the test, and the verification environment has grown to hold it.
