# CI/CD for RTL — Pipelines for Hardware

> *"You've just spent a week on a complex testbench change. You regressed locally, it passed, you're ready to check in. You pull the latest from teammates — and now it doesn't even compile. We've all lived that. JL Gray opened his 2012 DVCon paper with exactly that story and argued that a Continuous Integration server can prevent most of it, and the EDA world has spent the thirteen years since turning that bet into the default. AMD was running 'Autocuration' on its next-gen microprocessor core the same year, dynamically picking the regression subset each commit deserved. By 2025 SDTECH is shipping CI for large-scale SoC design that fuses modern software practice with HPC regression, and Samsung India is wrapping Bamboo around an Automated Regression Framework to keep an IP/SoC database sane. The DevOps playbook won in software; here's the retuned-for-hardware version. Let's dig in."*

## What it is

A **CI/CD pipeline for RTL** is the same construct software teams have used for two decades — a server that watches a version-control repo and, on every change, runs build, lint, and regression jobs, then publishes results — retuned for the realities of hardware. Sprott, Winkelmann and McGregor draw the line that still confuses people: CI is *not* the same as your EDA regression manager. "There is still some confusion between the roles of Continuous Integration and EDA regression tools, when it comes to verification management and test execution," and the two have to be glued together deliberately [A GUIDE TO USING CONTINUOUS INTEGRATION WITHIN THE VERIFICATION ENVIRONMENT, 2014]. CI owns the source tree, the build trigger, and the "is this commit safe to merge?" gate; the regression manager owns test selection, distribution, and coverage merge.

The dominant server in the corpus is **Jenkins**. Ellis's "Before You Finish Your Morning Coffee" papers walk through the setup in careful detail — download the war, run `java -jar jenkins.war`, install the Questa VRM plug-in so Jenkins can "understand code and functional coverage, determine where log files reside, monitor host utilization" — and position the resulting dashboard as the verification team's morning read [Increased Regression Efficiency with Jenkins Continuous Integration, 2016; Increased Regression Efficiency with Jenkins Continuous Integration Before You Finish Your Morning Coffee, 2017]. Liu Wei et al. frame the modern equivalent: a CI system that "leverages both the modern continuous integration practices in software development and the high-performance computing (HPC) environments and existing regression scripts commonly used in chip design" [Continuous Integration in SoC Design: Challenges and Solutions, 2025].

## How it's used in practice

The recurring pattern is **gated check-in models of increasing sophistication**. Dickol's Samsung Austin paper describes three: the "Clean Head" model (small disciplined teams tolerate some churn), the "Gated Check-in" model (more stable, longer integrate times), and the "Parallel Gated Check-in" model (model stability of gated check-in with better throughput, at the cost of setup complexity) [Advanced Usage Models for Continuous Integration in Verification Environments, 2015]. AMD's earlier Autocuration system adds the smart bit: "a dynamic process to determine the appropriate subset of regression test suites that need to be run for each source commit" so compute isn't wasted on irrelevant tests [Autocuration: An Implementation of a Continuous Integration System Employed in the Development of AMD's Next-generation Microprocessor Core, 2012]. That same instinct recurs as Atlassian Bamboo in the Samsung India "ARF" framework, which automates runs and analysis so engineers don't have to read every log [Novel Approach to Automate Design Verification Cycle Using Continuous Integration-Continuous Deployment Platform, 2024].

A second pattern is **end-to-end signoff automation**. PyRDV wires a Python tool that collects requirements from GitLab issues and runs "a CI/CD service to periodically check for sign-off metrics" — pushing traceability itself into the pipeline [PyRDV: a Python-based solution to the requirements traceability problem, 2024]. Lint becomes a pipeline stage too: Venkataramanan et al. integrate slang/pyslang-based SystemVerilog rule checking "into a continuous integration flow" so style and coding-standard violations never reach main [Testbench Lintingopen-source way Using slang/pyslang/PySlint, 2023]. Ayari and Mikhael frame the whole effort as moving integration "from chaos to order" by running jobs in parallel and tracking every step [Functional Verification from Chaos to Order: Using Continuous Integration for Hardware Functional Verification, 2024]. The newest wrinkle is HW-SW co-verification as a pipeline citizen: Hoffmann et al. argue that "Integration between HW and SW leads to disruptions if both flows run in parallel without continuous interaction" and fold co-verification into CI/CD [HW-SW-Coverification as part of CI/CD, 2023].

## Pitfalls and where the field is heading

The classic pitfall is treating CI as just a regression launcher. Sprott et al. warn that the methodology of CI in an EDA environment "is not always obvious" — the gate has to actually block bad commits, the regression subset has to be honest, and the dashboard has to be authoritative [A GUIDE TO USING CONTINUOUS INTEGRATION..., 2014]. A subtler pitfall is debug granularity: when a gated run fails, which line of a large commit is to blame? Hansson and Granath argue that "for large commits it would be even better if we could identify the exact bad lines of code within the commit," and adapt delta debugging to overcome its known issues [Automatic Debug Down to the Line of Code, 2017]. Capacity and flakiness are eternal — Gray notes the operational challenge of "technical and managerial" adoption even on a small project [A 30 Minute Project Makeover Using Continuous Integration, 2012].

The field is heading toward **agentic, AI-aware pipelines**. Choi, Noh and Yim describe a "3-tiered agentic AI regression framework" that splits regression into user, block, and central tiers, each aligned with a verification scope, because conventional monolithic regressions suffer "high latency, limited scalability, and inefficient resource utilization" [A 3-tiered agentic AI Framework for Verification Regression, 2026]. That trajectory — CI as the substrate, AI as the scheduler/triage layer, HPC as the muscle — is where every recent DVCon CI paper is converging.
