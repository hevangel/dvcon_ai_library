# Random Stability, Seeds, and Reproducibility

> *"A test passes on Tuesday and fails on Wednesday. Same RTL, same testbench, same seed — or so you thought. What changed? Maybe the simulator got a patch and its RNG moved. Maybe a thread started winning a race differently. Maybe someone added a `rand` variable upstream and the whole constraint-solving order shifted. This is the random-stability rabbit hole, and it is older than UVM: Bromley's 2011 *First Reports from the UVM Trenches* already flagged it as a real operational risk, and Yehia's 2014 gotchas paper devoted whole sections to "reduce random instabilities." The promise of constrained-random verification is that a seed is a perfect replay key. The reality is that seeds are only as stable as the toolchain, the thread scheduler, and the discipline of the team. So what's actually going on under the hood, and how do you keep a regression reproducible across years?"*

## What it is

A **seed** is the initial value fed to a **pseudo-random number generator (RNG)**; in SystemVerilog, `srandom(seed)` and the `+svseed` plusarg let you (in theory) replay any run bit-for-bit. The seed determines the stream of random values that `randomize()` consumes, which determines which constraint solutions the solver picks, which determines the transactions on the wire. The chain is deterministic *given a fixed tool version* — but the chain is also long, and any link can break it. Nelson's *Objective Functions, Rewinding and Dynamic Seed Manipulation* paper makes the dependence explicit: his loop proposes a seed, runs a slice of simulation, then issues an `ACCEPTED` or `REJECTED` verdict that either commits the seed or rewinds to try another, with accepted seeds "saved in the TCL server and given to other simulators" so a distributed run stays coherent [Improving Constrained Random Testing..., 2017]. The seed is the unit of replay, and the infrastructure around it is what makes replay trustworthy.

The deeper concept is **random stability** — the property that the same seed produces the same result across runs, across machines, and ideally across tools. Andrews and Hristov called this out directly in 2015: the problem with scattering randomization across SystemVerilog, SystemC, and C testbenches is "the lack of random stability between those models," so a bug found in one environment can't always be reproduced in another [Portable Stimulus Models for C/SystemC, UVM and Emulation, 2015]. Their answer was a graph-based stimulus model whose "same model can be used to generate repeatable stimulus in a pure C or SystemC simulation environment, in a SystemVerilog UVM testbench or any other environment" — seed portability as a first-class goal. Yehia framed the same problem from the failure side: random instabilities are the symptom, and "carefully studied and addressed" constraint patterns are the cure [The Top Most Common SystemVerilog Constrained Random Gotchas, 2014].

## How it's used in practice

The most disciplined use of seeds is **feedback-driven replay**. Nelson's rewinding mechanism takes an "Objective Function" (typically a coverage goal) and searches the seed space intelligently rather than blindly, accepting seeds that move toward the goal and rejecting those that don't, with the accepted seeds captured in a replicate file so "the run" can be reproduced exactly [Improving Constrained Random Testing..., 2017]. The same instinct scales to whole regressions: Huang, Shojaei and Zyda's **Smart Regression Planner** treats test parameters and seeds as a blackbox optimization problem, using Bayesian optimization with nightly-coverage feedback to "better explore the input space and accelerate convergence towards coverage" — explicitly noting that conventional flows rely on "increased coverage over time simply through variations in the random seed" [Test Parameter Tuning with Blackbox Optimization, 2022].

The discipline gets harder when the testbench spans languages. Andrews and Hristov show that if random stability can be "achieved across the languages and testbench environments then the results from each model can be compared easily and problems found in one environment can be debugged on any or all of the available design models" [Portable Stimulus Models for C/SystemC, UVM and Emulation, 2015]. Vejlani and Chandran's UVM-plus-Python DSP datapath flow is a case study in the seams that break stability: the Python side and the SystemVerilog side each have their own RNG, and a bug that depends on their interaction only replays if both sides honor the same seed contract [Challenges in UVM + Python random verification environment for Digital Signal Processing datapath design, 2016]. Le and Drechsler's SystemC coverage-driven generator avoids this by keeping randomization inside one framework and feeding uncovered bins back as constraints, so the seed governs the whole stimulus model [Boosting SystemC-based Testbenches with Modern C++ and Coverage-Driven Generation, 2015].

## Pitfalls and where the field is heading

The central pitfall is **silent non-reproducibility**. A simulator upgrade ships a new RNG, the solver now explores the constraint graph in a different order, and a bug that filed itself under seed `12345` simply disappears. Bromley flagged this class of risk in one of the earliest UVM rollout papers, where "unexpected problems" included randomization behaviors that differed across vendors [First Reports from the UVM Trenches, 2011]. Sokorac's ML-driven constraint optimizer at ARM underscores a second pitfall: with "billions of simulation cycles in tens of thousands of tests," no human can spot the seed that mattered, so the regression must record seeds, parameters, and tool versions together or the bug is gone [Optimizing Random Test Constraints Using Machine Learning Algorithms, 2017]. Ambalakkat and Nelson add a third: feedback loops that modify constraints at runtime can leave the simulation "stuck in an infinite loop" when the objective stops improving, because the seed search never accepts [Simulation Runtime Optimization of Constrained Random Verification using Machine Learning Algorithms, 2019].

The field is converging on three answers. First, **graph-based portable stimulus** (PSS and its ancestors) makes the stimulus model the source of truth, so stability lives in the model, not the tool [Portable Stimulus Models for C/SystemC, UVM and Emulation, 2015]. Second, **ML-assisted seed and parameter search** replaces blind nightly fuzzing with directed optimization, turning the seed from a replay key into an explored coordinate [Test Parameter Tuning with Blackbox Optimization, 2022; Improving Constrained Random Testing..., 2017]. Third, regression infrastructure treats seed, tool version, and configuration as one captured artifact — a direction reinforced by Kim, Lee and Cha's post-silicon PSS work, where embedded test software has to reproduce identically across lab and pre-silicon [Post-Silicon Performance Validation Using PSS, 2020]. The dream of bit-exact replay is still alive; the path to it runs through better models, not luckier seeds.
