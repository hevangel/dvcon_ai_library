# Emulation and Prototyping

> *You have a billion-gate SoC and the software team is knocking on your door asking when they can start porting Android to it — six months before silicon exists. Simulation gives you maybe one kilohertz of effective clock. Emulation gives you megahertz. The catch: emulators cost more than a sports car, they are shared across continents, your UVM testbench has to be rewritten to survive synthesis, and "X" propagation is a whole different beast in 2-state hardware. The trade-off has always been debug visibility versus performance — pure simulation sees everything but crawls, pure FPGA prototyping flies but is nearly blind, and the modern answer is everywhere in between. So how did pre-silicon validation grow from a niche accelerator into the engine that brings up Android home screens before tapeout? Let's dig in.*

## What it is

**Emulation and prototyping** are the technologies used to validate a design that is too large, too slow, or too software-dependent to verify in RTL simulation alone. The umbrella covers processor-based emulators (Palladium, Veloce), FPGA-based prototypes, and **hybrid** combinations of the two with virtual platforms. The defining motivation is performance: a software bring-up of an Android home screen that takes around four days on a pure emulator running at a ~1 MHz driver clock is simply not realistic for iterative software development [Hybrid Emulation for faster Android Home screen bring up and Software Development, 2023]. Emulation narrows that gap by orders of magnitude, moving software and system-level workloads into pre-silicon.

The core trade-off is debug visibility versus performance. Pure FPGA prototyping is fastest but offers limited internal visibility; RTL simulation is the most debuggable but slowest; emulation sits between, and hybrid emulation — part virtual prototype (TLM, VDK), part hardware emulator — sits further still [Hybrid Emulation for faster Android Home screen bring up and Software Development, 2023] [Unveiling Advance Hybrid Emulation Methodology for Accelerated Android Home Screen Bring-up and System Level Verification, 2024]. The hybrid split is deliberate: CPUs, memories, and frequently accessed peripherals run on the fast virtual side, while most IPs run on the emulator to start software development against real RTL.

Because emulators are scarce enterprise resources, their utilization is its own engineering discipline. Software testbenches (as opposed to in-circuit emulation with a real target) became dominant precisely because they let emulators be shared remotely across users and time zones, but they raise scheduling problems: virtual emulation jobs are mostly non-pre-emptive, and resource fragmentation within an emulator wastes capacity when a long job holds slots a short job needs [Transparently Checkpointing Software Test Benches to Improve Productivity of SoC Verification in an Emulation Environment, 2018].

## How it's used in practice

Emulation is rarely a drop-in replacement for simulation — it requires real methodology work to port a UVM testbench and to keep the design useful across the migration. **Co-emulation (transaction-based acceleration)** moves the DUT onto the emulator while the testbench stays on the host, exchanging transactions over a speed bridge; the port is non-trivial because simulation's springy debugging and freely available SystemVerilog constructs must be reconciled with what synthesizes in hardware [Challenges and Mitigations of Porting a UVM Testbench from Simulation to Transaction-Based Acceleration (Co-Emulation), 2018]. Open-source co-emulation frameworks are starting to appear — an OFC framework using PYNQ boards connects a UVM-SystemVerilog testbench to FPGA logic over TCP, lowering the barrier to entry [Open-source Framework for Co-emulation using PYNQ, 2021].

The dominant use case is **early software bring-up**. Samsung's hybrid emulation platform splits the mobile-AP design so the ARM-released SystemC fast CPU model runs on the virtual side and the real RTL CPU is black-boxed, allowing Android boot to begin before silicon [Hybrid Emulation for faster Android Home screen bring up and Software Development, 2023] [Early Software Development and Verification Methodology using Hybrid Emulation Platform, 2017]. The same approach accelerates NAND flash verification, where the design mixes RTL, analog behavioral models, and bidirectional transistors that simulation handles poorly [Accelerated Verification of NAND Flash Memory using HW Emulator, 2023]. For ML NPU power and performance workloads, emulation runs the long scenarios that simulators cannot complete in time [Emulation based Power and Performance Workloads on ML NPUs, 2022].

Two recent developments are reshaping the practice. First, **4-state logic emulation** — long thought impractical in hardware — is now real. Native 3-state ('0', '1', 'X') computation in the Palladium Z2 processor with compiler logic transformations adds 'Z', finally enabling power-aware verification on the emulator with proper X-source identification [Innovative 4-State Logic Emulation for Power-aware Verification, 2024]. Second, **gate-level emulation** is being used to attack the weeks-long GLS scenarios that plague SoC signoff, since emulation can run them at speeds simulation cannot reach [Netlist Enabled Emulation Platform for Accelerated Gate Level Verification, 2023]. Synthesizable functional coverage rules now let teams reuse simulation coverage code on the emulator despite vendor syntax differences [Improve emulator test quality by applying synthesizable functional coverage, 2023].

## Pitfalls and where the field is heading

The classic pitfall is the **2-state assumption**. For years emulators ran 2-state logic and verification engineers accepted the trade-off — but power-aware designs expose the gap, because power intent bugs generate Xs that 2-state emulation silently hides. As a result, teams historically limited emulation to power *sequence* checking and ran full power-aware verification in simulation, losing emulation's speed advantage entirely [Innovative 4-State Logic Emulation for Power-aware Verification, 2024]. Native 4-state emulation removes that ceiling.

Debug is the other persistent pain. Data corruption originating in one subblock propagates downstream and traditionally demanded labor-intensive manual waveform analysis. Synthesizable checkers, ad-hoc checkers, and golden-reference checkers are constrained by emulator compatibility, and assertion checkers synthesize poorly — which is why teams are building offline FSDB-based data-integrity debuggers that mine the captured waveforms after the run [Offline FSDB based Data-Integrity Debugger for Sub-System Emulation based Runs, 2025]. Checkpoint/restore of software testbenches is also maturing, enabling pre-emptive scheduling and resource migration so expensive emulator slots are not held hostage by long-running jobs [Transparently Checkpointing Software Test Benches to Improve Productivity of SoC Verification in an Emulation Environment, 2018].

The trajectory is toward **simulation-emulation co-existence** — keeping both alive in one flow rather than migrating wholesale — so that iterative debugging can fall back to simulation when emulation's debug visibility runs out [An Accelerated System Level CPU Verification through Simulation-Emulation Co-Existence, 2022]. The hybrid model continues to absorb more functionality: CPU benchmarks via "gear shift" methodologies that migrate Linux/Android state from the virtual CPU to RTL CPU once boot is complete [Hybrid Emulation for faster Android Home screen bring up and Software Development, 2023], and unified power and performance flows that start measurement early in the design cycle [Emulation based Power and Performance Workloads on ML NPUs, 2021].
