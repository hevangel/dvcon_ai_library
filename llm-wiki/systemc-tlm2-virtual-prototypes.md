# SystemC TLM-2.0 and Virtual Prototypes

> *"Modern SoCs run millions of lines of firmware, and software teams refuse to wait for RTL. The answer is the **virtual prototype** — a fast, untimed or loosely-timed C++ model of the whole SoC, built in SystemC using TLM-2.0 transactions, on which an OS can boot and drivers can be written months before any RTL exists. The original 2009 TLM-2.0 standard was a revelation: it defined an interoperability layer so that an ARM core model from one vendor, a memory controller from another, and a UART from a third could be stitched into one platform. Except, as GreenSocs' Delbergue and colleagues pointed out in 2016, the standard 'has only enabled interoperability for memory mapped bus based protocols' — every interrupt, every serial line, every Ethernet MAC still needs a custom non-interoperable shim. That gap, plus the never-ending tension between loosely-timed speed and approximately-timed accuracy, is what DVCon papers have been arguing about for fifteen years. Let's dig in."*

## What it is

**TLM-2.0** (Transaction Level Modeling, version 2.0) is part of the IEEE 1666 SystemC standard and defines how models exchange transactions. Three roles exist — initiator, target, and interconnect — and a model can host multiple sockets and switch roles dynamically. Two abstraction levels are standard: **Loosely Timed (LT)** uses just two timing points (begin and end of transaction) and is optimized for speed — booting Linux, running driver tests. **Approximately Timed (AT)** breaks each transaction into four phases and is suited for architectural exploration where some cycle accuracy matters [Analysis of TLM-2.0 and it's Applicability to Non Memory Mapped Interfaces, 2016]. The standard's killer feature is the **generic payload**: a transaction object carries a pointer to a byte-array data block, so it can hop initiator-to-target without being copied — a huge speed-up over TLM-1, which copied or passed the transaction object at every hop [UVM and SystemC Transactions -An Update, 2016].

TLM-2.0 also introduced **time decoupling** through "quantums": a model can run ahead of simulator time by a quantum of cycles before synchronizing, which is what makes virtual platforms fast enough for software bring-up. The library was originally C++/SystemC, but the verification community wanted it inside SystemVerilog too. Glasser and Bergeron's 2011 paper documents the **translation of TLM-2.0 into SystemVerilog** for UVM, wrestling with the semantic gaps: SystemVerilog supports only single inheritance where C++ needs multiple, SystemVerilog lacks function templates, and the convenience sockets in TLM-2.0 rely on function pointers that SystemVerilog does not have [TLM-2.0 in SystemVerilog, 2011]. Long and Aynsley follow up with an update on connecting SystemC TLM-2.0 models into UVM through UVM Connect and UVM-ML [UVM and SystemC Transactions -An Update, 2016].

## How it's used in practice

The dominant application is **early software bring-up on virtual platforms**. Jünger, Weinstock, and Leupers built SIM-V, a fast parallel RISC-V simulator at RWTH Aachen, because "contemporary VPs often fail to deliver the" performance needed for complex modern SoCs with millions of lines of firmware [SIM-V Fast, Parallel RISC-V Simulation for Rapid Software Verification, 2022]. With Renesas, the same authors later combined QEMU instruction-set simulators with SystemC TLM-2.0 peripheral models to build virtual ECUs for automotive — "the best of both worlds," getting QEMU's CPU speed with SystemC's peripheral fidelity [Virtual ECUs with QEMU and SystemC TLM-2.0 The Best of Both Worlds, 2023]. Test-equipment teams use the same trick: Barrau, Piccini, and Moreno at Schneider Electric and GreenSocs build two virtual platforms — one for the product, one for the test equipment — and develop TestStand-driven test sequences before any real hardware exists [Acceleration of product and test environment development using SystemC-TLM, 2018].

The second pattern is **bridging TLM-2.0 and UVM** for verification reuse. Dahir, Bluethgen, and Zuralski at Cadence show how the UVM-ML library lets verification teams drop early-developed TLM-2.0 reference models directly into a UVM testbench, avoiding a rewrite once RTL comes in [Using UVM-ML library to enable reuse of TLM2.0 models in UVM test benches, 2018]. Singh, Chopra, and Geishauser at NXP go further: they build the entire verification infrastructure — from subsystem to SoC simulation, emulation, and GLS — around the TLM-2.0 generic payload, so C stimulus and testbench code stay portable across all four platforms [A pragmatic approach leveraging portable stimulus from subsystem to SoC level and SoC emulation, 2019]. And Genov, Leconte, and Verdier use SystemC/TLM-2.0 with their PwClkARCH library to do early power and performance co-estimation on an NXP interconnect [Mixed Electronic System Level Power/Performance Estimation using SystemC/TLM2.0 Modeling and PwClkARCH Library, 2020]. Pavan Kumar, Brar, and Aggarwal at Samsung describe the inverse journey: converting cycle-accurate performance models into functional models usable by software teams, with explicit "pitfalls and key points" to avoid producing a buggy VP [Conversion of Performance Model to Functional Model, 2021].

## Pitfalls and where the field is heading

The deepest pitfall is that **TLM-2.0 only really standardizes memory-mapped busses**. The standard's "generic payload" assumes an address, byte enables, and DMI — concepts that do not exist for UART, I2C, or Ethernet. Vanthournout and Burton at Synopsys put it bluntly: using TLM-2.0 for "interrupt signals, serial protocols, and Ethernet-like protocols was never intended and doesn't work very well," forcing teams to either build custom interfaces (losing interoperability) or fall back on raw `sc_signal` (which has semantics incompatible with TLM) [TLM Beyond Memory Mapped Busses, 2016]. Delbergue et al. propose concrete extensions — a renamed `tlm_memory_mapped_payload`, plus separate serial-payload classes like `tlm_i2c_payload` — and a GreenSerialSocket for UART-style traffic [Analysis of TLM-2.0 and it's Applicability to Non Memory Mapped Interfaces, 2016]. The naming point is sharp: calling the bus payload "generic" misled a generation of engineers into believing TLM-2.0 was broader than it is.

The accuracy-vs-speed tradeoff is the second pitfall. Schuster, Prüller, and Sauer at Cadence lay out the DRAM subsystem case: emulation gets the bandwidth numbers right but is too slow for early exploration; abstract TLM models are fast but "not applicable" downstream; the team has to migrate models between abstraction levels as the design matures [Performance modeling and timing verification for DRAM memory subsystems, 2018]. Bosbach, Junger, and Leupers at RWTH Aachen codify the practical response with a hands-on VCML (Virtual Components Modeling Library) tutorial for efficient loosely-timed modeling [Efficient Loosely-Timed SystemC TLM-2.0 Modeling: A Hands-On Tutorial, 2022]. The trajectory of the field is toward hybrid QEMU-plus-SystemC platforms for software teams, UVM-ML bridges to verification teams, and gradual standardization of non-memory-mapped payloads — so that the next ten years of TLM look less like a bus-only club and more like a true multi-protocol interoperability layer.
