# UVM Phasing and Objections

> *A UVM testbench is a lifecycle. Things boot in a fixed order — build, connect, end_of_elaboration, start_of_simulation — then everyone runs, then everyone shuts down in reverse. **Phasing** is the scheduler that imposes that order, and **objections** are the flags that tell the scheduler "I'm not done yet, don't you dare end the run phase." It sounds simple, and at the textbook level it is: raise an objection when your sequence starts, drop it when you're done, and the test ends when every objection is dropped. In real SoC testbenches the picture is messier. You have embedded cores running their own implicit lifecycle, mid-simulation hard resets that need to pause every agent, drain times that hide race conditions, and an objection mechanism that Edelman charitably calls "always misunderstood." Let's unpack the machinery.*

## What phasing and objections are

UVM divides a testbench's life into **phases** — a top-down set of build/connect/elaboration phases followed by the run-time phases (`reset`, `configure`, `main`, `shutdown`, etc.) and a bottom-down cleanup set. Every component's task-phase method runs concurrently during the corresponding phase, and the phase does not advance until every participant has finished and no objections remain [OVM & UVM Techniques for Terminating Tests, 2011]. Objections are the gate: each component or sequence that wants to keep a phase alive calls `phase.raise_objection(this)` and later `phase.drop_objection(this)`. Once the objection count hits zero (after any configured **drain time**), the phase drains and the scheduler moves on [Without Objection, 2024].

Under the hood, an `uvm_objection` keeps three associative arrays indexed by object handle — `m_source_count`, `m_total_count`, and `m_drain_time` — incremented on raise, decremented on drop, and consulted to decide when to fire the `all_dropped` callback and propagate up the hierarchy [Without Objection, 2024]. The two controlling calls take an optional source object, a description string, and a count that defaults to 1; raising propagates up the hierarchy unless `set_propagate_mode(0)` routes it straight to `uvm_test_top`, and `set_drain_time` lets an object wait a fixed delay after all objections drop before declaring the phase over [uvm_objection — challenges of synchronizing embedded code running on cores and using UVM, 2024]. Recording the history of raises and drops is the mechanism's built-in traceability — invaluable when a test hangs and you need to find the orphaned objection.

## Termination: from stop_request to objections

The history matters because UVM inherited a confusing menu of termination options. Cummings and Fitzpatrick's "OVM & UVM Techniques for Terminating Tests" catalogs the choices: sequence completion, the legacy `global_stop_request` mechanism, and the newer objection mechanism, plus event and barrier constructs for application-specific synchronization [OVM & UVM Techniques for Terminating Tests, 2011]. The crucial interaction is that a single objections-raised thread invalidates every `global_stop_request` in every stop-request thread — meaning `global_stop_request` is effectively dead the moment any component opts into objections. Their recommendation, echoed across the corpus, is to standardize on objections raised at the start of the relevant `run` task and dropped at its end, with the last-dropped objection deciding when the active stage finishes [OVM & UVM Techniques for Terminating Tests, 2011].

Edelman's "Without Objection" goes further, arguing objections are conceptually a synchronization barrier dressed up in phase machinery — raise to enter the barrier, drop to leave it — and that the phasing and objection code becomes "intertwined" in ways that are "problematic to debug and understand" [Without Objection, 2024]. The paper proposes simpler alternatives, including a plain barrier mechanism (citing related work on a simpler end-of-test pattern) and notes that the UVM-internal complexity is often more than the problem warrants. The takeaway is pragmatic: objections are the right default, but for simple synchronization you may be better served by a hand-rolled barrier you can actually read.

## Custom phasing and real-world synchronization

Real SoCs rarely fit the stock phase schedule. The "Global Broadcast with UVM Custom Phasing" work needed mid-simulation hard resets on a PCIe project and built four custom side-band phases running in master-slave relationship alongside the main phase, so that every project-specific component could be notified that a major simulation event was about to occur; sequencers could pause stimulus for a "quiescent" event or end scenarios entirely for a "hard reset," with a phase jump following [Global Broadcast with UVM Custom Phasing, 2014]. Reset-awareness more generally — entering and exiting reset cleanly with in-flight traffic — is one of the most disruptive events a testbench faces, and reset packages have grown up specifically to make "reset anytime" survivable [Reboot your Reset Methodology, 2014][Handling Asynchronous Reset(s) Testing, 2021].

The hardest synchronization problem in the corpus is the SoC with embedded cores running their own lifecycle. NXP's "uvm_objection — challenges of synchronizing embedded code running on cores" points out that the completion of the UVM life cycle (objections) has to be reconciled with an implicit SoC lifecycle defined by resets, logic BIST, clock ramp, and security — and that multiple cores each have independent lifecycles that themselves need synchronization [uvm_objection — challenges of synchronizing embedded code running on cores and using UVM, 2024]. Their solution wraps an `objection_env` per core inside the testbench and exposes a C API (`RAISE_OBJECTION`, `DROP_OBJECTION`, `GET_OPEN_OBJECTIONS`) so embedded code can participate in UVM phase completion; the master core polls open objections, runs health checks, and only then drops its own. Synchronization primitives like UVM events, barriers, and heartbeats fill in the gaps for less exotic cases [De-mystifying synchronization between various verification components, 2016].

## Pitfalls and where the field is heading

The objection mechanism's biggest pitfalls are overuse and silent misuse. Edelman's verdict — "sometimes overused and are always misunderstood" — captures both [Without Objection, 2024]. A forgotten `drop_objection` hangs the test forever; a `raise_objection` issued from a context where propagation has been disabled silently does nothing; mismatched raise/drop counts leave phantom objections. Drain time papers over races but introduces its own: a too-short drain drops the phase while a sequencer is still mid-transaction. The Low Power UVM package work shows the same machinery being bent to power management, with low-power routines executing within agent run phases to sequence power-up/down across multi-core architectures [UVM-based extended Low Power Library package, 2023][Integrating L1 & L2 Cache for multi-Core UVM-based extended Low Power Library Package, 2023]. More recently, the LLM-assisted "Common Task Coverage" methodology measures coverage inside the UVM testbench itself, which only works if phasing and objections are predictable enough that coverage bins can be attributed to specific test segments [An Early Stage Coverage Measurement Methodology, 2025]. The trajectory is toward more deterministic, more debuggable completion — simpler barriers, better tracing, and explicit C-API bridges for the cores that have to live inside the same phase clock as the testbench.
