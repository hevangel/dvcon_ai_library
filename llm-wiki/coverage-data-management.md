# Coverage Data Management and Exchange

> *Run a single test and you have one coverage database. Run a regression and you have thousands. Try to merge them across two simulators, an emulator, and a formal tool — each from a different vendor with its own data model — and you have a data engineering problem pretending to be a verification problem. The DVCon corpus has been remarkably consistent on this point for over a decade: the moment coverage becomes central to signoff, the question stops being "did we hit the bin?" and becomes "can we even assemble a coherent picture of all the bins across everything we ran?" The answer involves a standard almost nobody fully implements, XML files that nobody enjoys writing, and a slow migration toward unified vendor platforms and AI-assisted merge pipelines. Let's dig in.*

## The core problem: many sources, one truth

**Coverage data management** is the discipline of collecting, merging, storing, and exchanging the coverage produced by simulation, formal, emulation, and post-silicon runs so that a single coherent picture of verification progress can be assembled. The reason it deserves its own page is that the merge step is not a solved problem. As El Mandouh et al. observe, "merging of coverage data is getting harder with the increase of today's HW designs' size/complexity as well as the large number of cover targets that required to be captured in the final coverage model such as statement, toggle, branch, FSM, expression, assertion, cover-groups and cross-cover-bins" [Accelerating Functional Verification Coverage Data Manipulation Using Map Reduce, 2017]. Worse, the merge step repeats throughout the verification lifecycle until closure is reached, so any inefficiency compounds.

The structural issue is that coverage is produced by heterogeneous tools with heterogeneous data models. May and Laha put it directly: "coverage databases however they are implemented contain very similar information, at the very lowest basic point it contains counts of defined events. The way these defined events are labeled or arranged within the database with a set of building blocks is defined as the data model" — and every vendor arranges those building blocks differently [Coverage Data Exchange is no robbery…or is it?, 2015]. Functional coverage, because it conforms to the SystemVerilog standard, can mostly be translated between vendor databases. Code coverage has no equivalent standard, so "different vendors implement different data models" and transformations between them are genuinely hard — line coverage vs block coverage may require additional data that simply is not present in the source [Coverage Data Exchange is no robbery…or is it?, 2015].

The Accellera **Unified Coverage Interoperability Standard (UCIS)**, released as version 1.0 in June 2012, is the industry's attempt to fix this. UCIS standardizes coverage data models and uses XML as an exchange format. Full compliance requires supporting all coverage data models and all C API routines defined in the specification, with the binary UCDB (in Mentor's case) storing data internally compliant with the UCIS models and accessible through either the proprietary or the standard API [Coverage Data Exchange is no robbery…or is it?, 2015]. Yehia's earlier UCIS applications paper frames the standard's value bluntly: it exists to help answer "Does it work?", "Am I done?", "What am I missing?", and "How can I improve my productivity?" against "vast amounts of simulation and coverage data" that otherwise cannot be analyzed [UCIS APPLICATIONS, 2013].

## How coverage data flows in practice

The first practical pattern is **XML-mediated exchange between UCIS-compliant tools**. Eickhoff et al. describe a representative VHDL flow: functional coverage is collected during mixed cycle/event-driven simulation using a VHDL extension, a script converts the combined statistics into XML against a predefined schema that "looks like covergroups," and a UCIS conversion utility turns that XML into a coverage database [An Assertion Based Approach to Implement VHDL Functional Coverage, 2014]. The conversion utility reports errors on invalid XML and refuses to produce a database, which makes well-formed XML a hard requirement. May and Laha generalize this to multi-vendor flows: a Data Converter block sits between the source database (e.g., a Synopsys UCAPI reader) and the target (e.g., a Cadence Unicov writer), mapping non-standard additions and reconciling data models such as SystemVerilog covergroup array bins, which may be represented differently by different vendors [Coverage Data Exchange is no robbery…or is it?, 2015].

The second pattern is **accelerating the merge itself**. As designs grow, naive merge becomes a bottleneck. El Mandouh et al. formulate coverage merge as a MapReduce problem: each merge task is associated with keys and values, merge starts from the single coverage database with the most cover items as the base file, and missing items are cloned from source databases — yielding up to 1.8x speedup on large coverage data [Accelerating Functional Verification Coverage Data Manipulation Using Map Reduce, 2017]. They argue for a "flattened unified coverage format" that inherits UCIS storage optimizations while still allowing independent parallel processing — a pragmatic acknowledgement that the standard's binary representation is not optimal for distributed computation.

The third pattern is **unified platform-native coverage** rather than cross-vendor exchange. The 2024 Synopsys Unified Coverage Methodology paper argues that the path forward is a single vendor's tool stack (VSO.ai and friends) unifying coverage across simulation, formal, and emulation platforms, with merging of coverage databases across IP, subsystem, and SoC levels to identify gaps [Unified Coverage Methodology: Accelerated Coverage Closure, 2024]. The 2026 Etabot paper pushes this further with a multi-agent framework that automates the *whole* coverage pipeline — running regressions, parsing text reports, merging a unified coverage database, and exposing the result to both a CLI and an MCP-enabled chatbot [Etabot, 2026]. The pattern is clear: stop trying to exchange and start collecting into one place.

A fourth, more analytical pattern is **mining the merged data**. Farkash et al. treat the merged coverage database as a dataset to be mined for efficiency, using a mathematical model to shift stimulus generation toward hard-to-hit events with a time dimension, achieving 12% reduction in hard-to-hit events and 13% reduction in never-seen events on PowerPC core verification [Mining Coverage Data for Test Set Coverage Efficiency, 2015]. Ikram et al. extend this to SOC protocols with a table-based Functional Coverage Management System that auto-generates coverpoints, transitions, and transaction coverage from protocol specifications [Table-based Functional Coverage Management for SOC Protocols, 2015].

## Pitfalls, gotchas, and where the field is heading

The biggest pitfall is assuming UCIS compliance means automatic interoperability. May and Laha are explicit that "when a vendor supports UCIS users often assume" interchange just works — and it does not, because some third parties have limited or no UCIS API support, and even fully compliant vendors represent the same data differently [Coverage Data Exchange is no robbery…or is it?, 2015]. Any real cross-vendor exchange needs a Data Converter and explicit model reconciliation.

The second pitfall is ignoring the merge cost. A flow that re-merges the entire coverage database on every regression run will spend a surprising fraction of its wall-clock on merge alone; MapReduce or incremental merge strategies are not optional at scale [Accelerating Functional Verification Coverage Data Manipulation Using Map Reduce, 2017]. Practical experience from CROT-style tooling reinforces this: incremental coverage merging per test completion is dramatically cheaper than batch re-merging [Centralized Regression Optimisation Toolkit, 2021, cited across the corpus].

The third pitfall is conflating code coverage from different sources. Because there is no standard for code coverage data models, naive aggregation across vendors can produce numbers that are not even apples-to-oranges — they are apples-to-USB-cables. Functional coverage is safer because SystemVerilog standardizes it [Coverage Data Exchange is no robbery…or is it?, 2015].

The trajectory, as with the rest of the coverage subfield, is toward consolidation and ML. Unified vendor platforms reduce the exchange problem by eliminating it; ML-driven mining (Jayasree's test-selection work, the 3D NAND Flash reinforcement-learning agent that trains from the coverage database) treats merged coverage as training data rather than just a report [Machine Learning for Coverage Analysis in Design Verification, 2021; Stimulus Diversification and Coverage Closure of 3D NAND Flash, 2025]. And agentic frameworks like Etabot are starting to fold coverage data management into a larger autonomous pipeline, where merging is just one step the agent handles without human intervention [Etabot, 2026].

## Grounded in these DVCon papers

- **Coverage Data Exchange is no robbery…or is it?** (2015, DVCon US) — Darron May and Samiran Laha. The canonical treatment of UCIS, cross-vendor exchange, and the Data Converter pattern for reconciling data models.
- **Accelerating Functional Verification Coverage Data Manipulation Using Map Reduce** (2017, DVCon Europe) — Eman El Mandouh, A. Gamal and A. Khaled. MapReduce formulation of coverage merge with up to 1.8x speedup on large datasets.
- **An Assertion Based Approach to Implement VHDL Functional Coverage** (2014, DVCon US) — Susan Eickhoff, Michael DeBole and Tagbo Ekwueme-Okoli. End-to-end XML-schema and UCIS-utility flow for VHDL functional coverage.
- **UCIS APPLICATIONS: IMPROVING VERIFICATION PRODUCTIVITY, SIMULATION THROUGHPUT, AND COVERAGE CLOSURE PROCESS** (2013, DVCon US) — Ahmed Yehia. Early survey of what UCIS unlocks for productivity and analysis at scale.
- **Mining Coverage Data for Test Set Coverage Efficiency** (2015, DVCon US) — Monica Farkash, Bryan Hickerson and Mike Behm. Mathematical model that retargets stimulus toward hard-to-hit and never-seen events using time as a dimension.
- **Table-based Functional Coverage Management for SOC Protocols** (2015, DVCon US) — Shahid Ikram, Jack Perveiler and Isam Akkawi. Automated coverpoint, transition, and transaction generation from table-based protocol specs.
- **Machine Learning for Coverage Analysis in Design Verification** (2021, DVCon Europe) — V Jayasree. ML-based test selection from the coverage database to maximize coverage per simulation second.
- **Unified Coverage Methodology: Accelerated Coverage Closure at SoC and IP level** (2024, DVCon India) — Prateek Jain and Ajay Goyal. Single-vendor unified coverage across simulation, formal, and emulation, with cross-level database merging.
- **Etabot: Multi-Agent Verification Management with Chat-Accessible Midpoint Metrics and Finish-Date Forecasts** (2026, DVCon US) — Zili Fang. Local-first multi-agent framework that automates the entire coverage pipeline end to end.
- **Stimulus Diversification and Coverage Closure of 3D NAND Flash with Artificial Intelligence** (2025, DVCon US) — Goutham Pallela, Peiyao Shi and Srinivas Deshmukh. Reinforcement-learning agent that trains against the coverage database to drive stimulus generation.
- **Practical experience in automatic functional coverage convergence and reusable collection infrastructure in UVM verification** (2014, DVCon Europe) — Roman Wang and Suresh Babu Pusphaparaj. Documents the merge cost as a first-class closure bottleneck.
- **Fully Automated Functional Coverage Closure** (2019, DVCon US) — Manohar Kodi, Sagar Sudam Patil and Ranjith Nair. Automation of the analyze-rerun-merge loop end to end.
- **A UVM Testbench for Checking the Global Convergence of Analog/Mixed-Signal Systems** (2024, DVCon Europe) — Jaeha Kim. Coverage-driven search over random initial states for AMS global-convergence verification.
- **Probing UPF Dynamic Objects: Methodologies to Build Your Custom Low-Power Verification Platform** (2020, DVCon Europe) — Progyna Khondkar. Continuously probing UPF object states for custom low-power coverage collection.
