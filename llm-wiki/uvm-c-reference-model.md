# C/C++ Reference Models in UVM (via DPI)

> *"Every complex algorithmic block — a floating-point unit, a Reed-Solomon FEC, an image-processing pipeline, a crypto accelerator — already has a golden C/C++/MATLAB model that the architect wrote to prove the algorithm before any RTL existed. It is one of the great absurdities of verification that we routinely reimplement that same algorithm in SystemVerilog for the scoreboard predictor. The standard fix is **DPI-C**: call the architect's C model directly from SystemVerilog through the Direct Programming Interface, hand it the same stimulus the DUT just saw, and let the scoreboard compare. It sounds trivial, and it is — until you try to synchronize a stateful C model with a UVM testbench, or measure how much DPI time you are paying per transaction, or realize your HLS-derived C model is itself buggy. DVCon papers since the early 2010s have been cataloguing exactly these problems. Let's dig in."*

## What it is

The pattern is the **golden C reference through DPI-C**. The architect owns a C/C++ reference model used for algorithm prototyping; the verification engineer wraps that model in `import "DPI-C"` functions, exposes them to SystemVerilog, and wires them into a UVM scoreboard's predictor. The scoreboard then compares the C model's expected output against the DUT's actual output on every transaction. As Sean Little of Verus Research puts it, the predictor "is often implemented using a low-level language such C or C++ and utilizes the SystemVerilog direct programming interface (DPI)" — and this "golden reference implementation provides a source of truth" for self-checking constrained-random testbenches [A Survey of Predictor Implementation using High-Level Language Co-simulation, 2025]. For arithmetic datapaths in particular, the architect's C model is essentially free to reuse, and reimplementing it in SystemVerilog risks both bugs and divergence from the spec.

The pattern generalizes to **any high-level language**. Little's survey reviews the trade space of C/C++, Python (via cocotb), and MATLAB (via MathWorks HDL Verifier) as predictor languages, and offers a custom C++ API called HALA that lets "nearly arbitrary functions be called directly from the HDL simulation tool" [A Survey of Predictor Implementation using High-Level Language Co-simulation, 2025]. At the C++/SystemVerilog boundary, Koyyalagunta, Zhang, and Anees built **CVM**, a library that bridges the two languages with unified communication, configuration management, logging, and topology handling across the boundary — making mixed-language testbenches "more maintainable, reusable, and efficient" [CVM -A Library for Unified C++ and SystemVerilog Testbench Development, 2025]. Where the reference model lives in SystemC TLM-2.0 from an early virtual prototype, UVM-ML is the bridge: Dahir, Bluethgen, and Zuralski show how to "enable reuse of TLM2.0 models in UVM test benches" so the same model serves both software bring-up and RTL verification [Using UVM-ML library to enable reuse of TLM2.0 models in UVM test benches, 2018].

## How it's used in practice

For **datapath verification**, the C reference through DPI is table stakes. Aluri and Mehta at Texas Instruments build an end-to-end golden reference for a mixed-signal RF SoC by composing MATLAB DSP block models, wreals for the analog front-end, and a UVM metric-driven verification layer with constrained randomization, mixed-signal assertions, and coverage [Advanced Functional Verification Methodology Using UVM for complex DSP Algorithms in Mixed Signal RF SoCs, 2014]. Burgoon and Havlik at Microsoft use the same pattern to verify HLS-generated RTL: the HLS input C++ becomes both the design source and the predictor, and the testbench confirms the synthesized Verilog matches it [UVM for HLS: An Expedient Approach to the Functional Verification of HLS Designs, 2018]. Vurukutla, Ranganathan, and Bilaye at Samsung India built an "elegant scoreboard eco-system" for a CMOS image-sensor SoC using UVM callbacks and parameterization so that the image-processing predictor stays composable across multiple pipeline blocks [An Elegant scoreboard eco-system deploying UVM Callbacks, Parameterization for Multimedia designs from Imaging perspective, 2023].

For **register-traffic synchronization**, Mehta at onsemi describes a particularly clean pattern: integrate DPI-C calls directly into UVM **RAL adapters**, so the C model updates in real time as the testbench writes registers — "significantly reducing the manual effort typically required by UVM predictors and scoreboards" [Real-Time Synchronization of C model with UVM Testbench, 2025]. The same instinct extends to non-deterministic designs, where Parizy and Iwashita at Fujitsu show that a golden reference has to model the legal non-determinism (e.g. packet reordering) explicitly, or the testbench will report false errors that are really "an early misunderstanding of the specs by the verification engineer" [Getting Rid of False Errors when Verifying LSI Designs Including Non-Determinism, 2011].

## Pitfalls and where the field is heading

The biggest pitfall is that **simulation-based C-through-DPI cannot reach verification completeness**. Kakde, Gosavi, and Bagavathiappan at Cadence put it directly: "Simulation-based approaches like DPI or scoreboarding suffer from challenges of achieving verification completeness" for datapath designs, and "the means of verifying this equivalence is shifting from simulation to formal gradually" thanks to better commercial solvers and the exhaustive nature of formal proof [Out of The Box Techniques for Data-Path Verification, 2025]. Puri, Eranki, and Jampana at Intel reach the same conclusion for AI-style matrix-multiply units (DPAS): "there remains a potential gap when the specification model itself is not entirely dependable," and they use formal verification to sign off rather than relying on a C-DPI predictor alone [Raising the Bar: Achieving Formal Verification Sign-Off for Complex Algorithmic Designs, with a Dot Product Accumulate Case Study, 2023]. Sequential equivalence checking is the heavyweight variant: Pouarz and Agrawal at ARM describe a partnership with Mentor to prove formal equivalence of FMUL, FMA, FDIV, and FSQRT blocks against a reference model — citing the $475M Pentium FDIV bug as motivation [Efficient and Exhaustive Floating Point Verification Using Sequential Equivalence Checking, 2017].

The second pitfall is **performance and tooling around DPI itself**. Little's measurements are sobering: a MATLAB-based HALA co-simulation on Linux took 54 seconds end-to-end versus 85.6 seconds for a Python cocotb run, but Windows pushed HALA to 110 seconds — DPI overhead is real and platform-dependent. The HDL Verifier from MathWorks "suffers from the mindset that all problems should be solved using their products" and is "not well suited to modeling concurrent hardware" [A Survey of Predictor Implementation using High-Level Language Co-simulation, 2025]. The trajectory is C/C++-DPI for everyday scoreboards, with formal equivalence checking taking over for mathematically critical blocks (FPU, crypto, ML datapaths), and unified libraries like CVM smoothing the language-boundary tax. The field has stopped asking *whether* to reuse the architect's C model and started asking *how* — and the answer is increasingly "through DPI for sim, through formal for sign-off."
