# Formal Connectivity Checking

> *Take a modern SoC and count the wires. Pad-to-pad muxing, reset distribution, clock trees, analog-IP pin connections, fuse straps, interrupt routing — the number reaches hundreds of thousands, and at integration time every single one of them has to land on the right flip-flop at the right polarity. For decades, the answer was a forest of directed simulation tests, run once, regression-checked weekly, and trusted on faith. Then someone asked the obvious question: why are we sampling this with simulation when the property "pin X is wired to pin Y" is exactly the kind of thing formal can prove exhaustively? Formal connectivity checking was born, and within a few years it had replaced miles of directed tests and exposed bugs simulation had been silently missing. The tooling still has rough edges — debugging counterexamples by hand is the new bottleneck — but the case for the methodology is closed. Let's dig in.*

## What connectivity checking proves

A **formal connectivity check** verifies that signal paths in an SoC are wired per the specification, exhaustively, by exploring the mathematical representation of the design rather than sampling it with directed tests [Formal Verification of Connections at SoC-level, 2018]. The standard workflow has two parts, summarized in the Synopsys/Marvell "Connectivity and Beyond" paper. A **structural check** confirms a physical directional path exists from source to destination, that source and destination bit widths are equal, and that the number of flip-flops between them matches the specified delay. A **functional check** then writes an SVA assertion confirming the source and destination ports behave coherently — for example, that a reset source actually drives every intended reset-bearing flip-flop [Connectivity and Beyond, 2019]. Modern formal connectivity apps (such as VC Formal's CC application) accept the connectivity specification in flexible formats — tcl commands, CSV, Excel files — and infer these checks automatically [Formal Verification of Connections at SoC-level, 2018].

Why this matters is best illustrated by what simulation cannot do. A directed test that triggers a watchdog reset mid-simulation and checks downstream propagation proves only that the flip-flops the test happened to inspect got reset — without exhaustively verifying propagation to every intended flip-flop, "simulation-based watchdog reset verification is incomplete, and bugs may still sneak into the design, causing system failures in lab testing and require a silicon re-spin to fix" [Formal Verification of Connections at SoC-level, 2018]. The same argument applies to padmux connectivity, reset schemes, and any other massively parallel wiring property: formal is exhaustive where simulation is statistical. Cadence's "Connecting the Dots" paper makes the scalability case directly — past practice tested "some arbitrarily chosen subset of such connections using the Verilog force/observe methodology," whereas formal finds many more connectivity issues earlier, with fewer verification resources, and is inherently exhaustive [CONNECTING THE DOTS: APPLICATION OF FORMAL VERIFICATION FOR SOC CONNECTIVITY, 2014].

## From one-off checks to a repeatable SoC workflow

The early adopters used connectivity checking as a one-time sanity check; the mature practice embeds it in the integration flow. The ST-Ericsson work separates connectivity checking from the rest of subsystem verification deliberately, because "the connectivity verification should be run very early in the subsystem verification process. Checking such things as clocks and resets early is crucial since problems in these areas can block large parts of the overall verification task" [Using Formal Verification to Exhaustively Verify SoC Assemblies, 2013]. The Synopsys/Marvell workflow goes further: designers author connectivity specifications at full-chip and partition level, the specs auto-generate connectivity checks on the evolving RTL, and a weekly formal-based regression ensures connectivity remains intact as the chip evolves. The same workflow verifies completeness of the specification itself through **fault injection verification**, and reuses the formal results to generate toggle coverage, saving time at integration [Connectivity and Beyond, 2019].

The Qualcomm work pushes automation further with a tool that "automatically detects mismatches between the RTL and the specification during every spec release" at both core and SoC levels [Framework for Automated Connectivity Checks for core and SOCs, 2024]. Core-level formal connectivity verification runs in minutes and covers domains like memory redundancy, interrupt control, fuse configuration, and complex power-reduction mechanisms. The SoC layer defines a formal syntax and semantics for specifying connectivity rules, then auto-checks them. Infineon's recent work shows the same logic tightening coverage signoff: automated formal connectivity checks can "greatly decrease the sign-off time" for automotive microcontrollers where TTM pressure is severe [Functional Coverage Sign-off assisted by Formal Connectivity, 2024]. And for memory subsystems with huge state space and frequent IP releases, connectivity-check automation is one of the explicit best practices alongside split-based property solving and engine-parameter optimization [Experience of using Formal Verification for a Complex Memory Subsystem Design, 2020].

## Beyond plain wiring: analog IPs, conditional paths, and debug

Connectivity checking has grown well past the original "source wired to destination" check. The pattern catalog now includes **one-to-one** connectivity (structural path plus functional coherence plus the assertion that neither side is connected to any other port — a check the basic connectivity app cannot make and that requires formal security verification or reachability analysis to complete) [Connectivity and Beyond, 2019]. **Analog IP integration** is a critical extension: as more functionality packs into SoCs alongside digital blocks, "a rigorous static and conditional connectivity verification among the digital and analog IPs is of equal importance in the SoC integration verification process," and "an incorrect connection to an analog IP can prove fatal and cost a silicon re-spin" [SoC Verification of Analog IP Integration through Automated, Formal-Based, Rule-driven Spec Generation, 2018]. The hardest sub-problem there is generating a valid connectivity specification for analog IPs in the first place, which formal-based rule-driven spec generation tackles.

The remaining bottleneck is **debugging counterexamples**. When a connectivity check fails, the formal tool emits a counterexample trace, and routing that trace to the actual miswire is currently "manual and time-consuming" — among the most tedious steps in formal connectivity workflows [ConnChecker: Automated Root-Cause Analysis for Formal Connectivity Check via Graph, 2026]. ConnChecker attacks this with a graph-based perspective that integrates the formal tool's structural and functional dependency graphs with the counterexample report, automatically categorizing failures into three analysis flows and localizing failure points. Evaluated on two industrial SoCs, it achieved up to 80% reduction in debugging time, especially for complex cases. The trick is segment-level reverse analysis — checking each component-to-component segment of a failed path rather than the full path, which is both more informative and far faster. As connectivity checking scales to chiplet and multi-die UCIe systems, that kind of automated root-cause analysis is what will keep the methodology economical.
