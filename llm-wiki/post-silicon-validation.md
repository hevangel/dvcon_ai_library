# Post-Silicon Validation in the Lab

> *"Here is the strangest fact about modern chip development: the most expensive, least observable stage of the whole project is the one we run last. In simulation you have full visibility into every flop, every signal, every cycle; you can stop time and replay. On a tester you have whatever scan decided to expose and whatever debug hooks the architect remembered to add. Suckert, Khaikin, and Vazhayil summarize the pain: 'the lack of a systematic flow from pre-silicon design verification to silicon validation in either a lab bench environment, or an Automated Test Equipment (ATE) environment, creates inconsistency, inefficiency, and correlation issues' [Accelerating Device Sign-off through a Unified Environment, 2025].

> And yet post-silicon is where the corner cases actually live. PVT corners that simulators approximate, supply noise patterns your power model never predicted, multi-gigabit SerDes links that only fail in a 40-degree chamber — these are bugs no regression will ever find. Yadav et al. put it crisply: 'SoC Software bring-up and its validation are usually done at post-silicon stage, which can affect time to market a product, and cost of silicon re-spin. It is also difficult to debug hardware/software design bugs at post-silicon level because of less RTL design visibility' [Hybrid Emulation for faster Android Home screen bring up, 2023].

> The good news is the field has stopped treating the lab as an art and started treating it as an engineering problem. Portable Stimulus makes tests travel from sim to silicon, AMS V&V reuse gets you to one-day bring-up, formal steps in as an unlikely post-silicon debug weapon. Let's open the hood on what 'validation in the lab' actually means today."*

## What it is

**Post-silicon validation** is the work of proving that the chip you taped out actually behaves like the chip you simulated. It has two main theaters. The first is the **lab bench**: bring-up boards, oscilloscopes, logic analyzers, protocol analyzers, and the host software that drives real workloads through real silicon. The second is the **ATE (Automated Test Equipment)** flow, where the same device runs high-volume manufacturing tests on a production tester. The two are different worlds — different tools, different teams, different formats — and a recurring theme across DVCon papers is that this separation is the root cause of correlation pain.

Underneath the theaters sits the post-silicon validation triad: **functional validation** (does it do what the spec says), **electrical validation** (does it work across voltage, temperature, process), and **performance validation** (does it hit the frequency, latency, throughput targets). Vasu, Venkatesh, and Maitra argue that performance 'is the critical source of competitive advantage for modern SOCs and performance targets needs to be validated on top of the functionality,' and that the sheer number of master/slave/bus-width/packet-size/clock-speed combinations 'quickly gets overwhelming' [Media Performance Validation in Emulation and Post Silicon Using Portable Stimulus Standard, 2021]. Validation is not just one more test; it is a different verification problem with much less visibility.

What makes post-silicon hard is the **observability gap**. Timmanagoudar et al. note that 'in most cases the pre silicon testcases cannot be [directly] re-used in post silicon functional validation' — the interfaces, timing, and access mechanisms differ — and so the work of bridging them is itself an engineering project [Analog Mixed Signal Verification and Validation(V&V) Methodology, 2024].

## How it is used in practice

The dominant pattern today is **portable test content via PSS**. Suckert, Khaikin, and Vazhayil's unified environment lets DV teams 'directly execute tests on silicon as well as enable collaboration with SV and TE teams by sharing test content,' with well-defined APIs 'for controlling test execution on silicon and for packing test content to enable seamless portability between teams' [Accelerating Device Sign-off through a Unified Environment, 2025]. The same PSS model drives pre-silicon simulation, post-silicon bench, and ultimately ATE vector patterns for high-volume manufacturing. Vasu's media performance work is an earlier cut of the same idea: PSS as the portable medium that 'overcomes all the limitations, manual efforts done by the validation teams' [Media Performance Validation in Emulation and Post Silicon Using Portable Stimulus Standard, 2021]. Singh, Aggarwal, and Prabha even use virtual prototyping to validate PSS models *themselves* before silicon arrives [Adopting Accellera's Portable Stimulus Standard, 2021].

For software bring-up specifically, the lab is moving **left** via hybrid emulation. Yadav et al. describe Samsung's hybrid emulation for Android home screen bring-up, motivated by the need for a high-speed SoC model 'months ahead of silicon availability' since FPGA-based emulation alone is too slow for full software stack bring-up [Hybrid Emulation for faster Android Home screen bring up, 2023]. The advanced version of that methodology uses co-model channels to push the Android home screen up at speeds FPGA emulation cannot reach [Unveiling Advance Hybrid Emulation Methodology, 2024]. Chan and Watt tackle the inverse problem — running the full FW/SW on a blackboxed RTL in emulation via a Hybrid Software Simulator (HSWSIM), with 'kill switch' logic in post-silicon software so the same binary still runs on emu [How to test the whole firmware/software when the RTL can't fit the emulator, 2019].

On the AMS side, the lab is the only ground truth. Wang's chip-level AMS regression methodology runs 30+ scenarios from a single programmable Verilog-AMS testbench in under 10 hours, 'which enables regular sign-off check within a day' [Chiplevel Analog Regressions in Production Analog-Mixed-Signal Simulation, 2021]. Bose et al. extend UVM with FFT-based analysis for DSP audio IPs, where 'traditional score-boarding techniques for data integrity checks are necessary but not sufficient to validate performance' [Addressing Challenges in Verification of DSP based Audio IPs, 2021]. Dhok and Paulraj close the loop with silicon bring-up by pre-verifying RADAR bitfield settings so the SW API team gets verified block configurations rather than guessing [Automotive RADAR Bitfields Verification to support Validation of Silicon bring-up, 2023].

## Pitfalls and where the field is heading

The biggest pitfall is **re-debugging what you already debugged**. Pre-silicon testcases do not run unmodified on silicon, and re-writing them by hand burns the schedule. The unified-environment and AMS V&V papers above are the field's answer. The second pitfall is the **bug that does not reproduce in sim**. Handover, Ayari, and Yeung point out that post-silicon bugs 'happen deep in functional operation under unusual combinations of events and scenarios' — exactly the kind of state-space corners that simulation misses and formal excels at, so they reach for 'deep sea fishing' formal flows as a post-silicon bug-hunting radar [Formal Verification Experiences: Silicon Bug Hunt with 'Deep Sea Fishing', 2020].

A subtler pitfall is the **emulator/silicon speed mismatch**. Chan et al. note that 'the silicon is 10 times faster than the emulation platform. Any time out delays in the software testcase should be configurable so that the test will not run forever in the emulation platform' [Is it a software bug? Is it a hardware bug?, 2022]. Assumptions baked into software timeouts work on silicon and break in emu. The reverse is also true: emulation platforms black-box analog blocks that silicon exposes, so post-silicon software needs a kill switch to avoid hanging the AXI bus on emu.

The third pitfall is **getting to silicon without a plan for AMS**. Simulation acceleration can mask problems; Chan, Vandegriend, and Shneydor describe the methodology for porting complex multi-language designs to acceleration, achieving '67x speed' on a UVM-e testbench [A Methodology to Port a Complex Multi-Language Design and Testbench for Simulation Acceleration, 2015]. But what works in acceleration is not automatically what works in the lab — AMS interfaces, analog models, and timing all shift.

The field is heading in three directions. First, **unified PSS-driven DV/SV/TE environments** that share test content across the whole signoff arc, with defect coverage derived from the PSS model itself [Accelerating Device Sign-off through a Unified Environment, 2025]. Second, **formal as a post-silicon debug tool**, reproducing lab bugs as cover properties that exercise the formal state space rather than rebuilding simulation testbenbons [Formal Verification Experiences, 2020]. Third, **shift-left of post-silicon bring-up itself** — software stacks booting on hybrid emulation and virtual prototypes so that the lab does the unknown-unknown work rather than the known-unknown work. Sinha and Christie's autonomous CDC/RDC assumption validation is part of this push: never let a lab failure trace back to an unverified signoff assumption [A step towards Zero Silicon Bugs using Assertion based Assumption Validation, 2020]. The lab is becoming just another execution target — slower, noisier, but finally part of the same flow.
