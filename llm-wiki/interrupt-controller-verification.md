# Interrupt Controller Verification (GIC, PLIC, IOAPIC)

> *"Interrupts are the chip's nervous system — the mechanism by which every peripheral, every timer and every software-triggered event pokes a CPU and says 'deal with me now.' Get the controller wrong and the symptoms are ugly: missed keystrokes, dropped packets, priority inversion that freezes the UI, or worst of all a system that wakes a powered-down core at exactly the wrong moment. The verification problem has compounded steadily. ARM's GIC alone juggles Shared Peripheral Interrupts (SPIs), Private Peripheral Interrupts (PPIs) and Software Generated Interrupts (SGIs), each with its own priority, target affinity and masking rules, and Samsung's 2023 work on multi-chip 3D-ICs pushed the problem across a die boundary — two GIC-600s chattering over AXI-stream cross-die interfaces, each supporting 256 SPIs, dynamically routing interrupts to whichever core happens to be awake and free [A Generic Verification Methodology for Chip to Chip Interrupt Handling in a Multi-Chip SoC (3DIC), 2023]. Microsoft went the other direction, arguing that an interrupt controller is small and self-contained enough to be the perfect target for end-to-end formal verification with no UVM testbench at all [End to End Formal Verification Strategies for IP Verification, 2017]. So what does it actually take to verify the thing that decides who gets poked, and when? Let's dig in."*

## What it is

An **interrupt controller** accepts level (and sometimes edge) interrupt inputs and routes them to a destination — a CPU core, a cluster, or a flag register — applying priority, arbitration, target affinity and masking along the way. The canonical families are ARM's **GIC** (GIC-600 and the virtualization-capable GICv3/v4), RISC-V's **PLIC/ACLINT** (and the newer AIA/APLIC), and x86's **APIC/IOAPIC**. They all centralize logic that would otherwise be spread across the SoC. Microsoft's reference INTC 'accepts level interrupt inputs, and routes them to the interrupt flag register and bit specified in the routing configuration registers, where that bit of the interrupt flag register is then set,' producing an interrupt any time the flag register is nonzero, with both input and output interrupts individually maskable [End to End Formal Verification Strategies for IP Verification, 2017].

The richer controllers split their interfaces by role. Samsung's GIC-600 talks to its processor cluster over the AXI-stream **iri/icc** channels and to the peer GIC over the **icdr/icrd** cross-die channels, each carrying packets with the interrupt ID, priority and target cluster/core; an integrated GIC monitor watches icc and iri continuously, and the AXI-stream `tdest` reveals which core actually serviced the interrupt [A Generic Verification Methodology for Chip to Chip Interrupt Handling in a Multi-Chip SoC (3DIC), 2023]. In the OS-aware co-emulation world the same role is played by a **GIC BFM/BIM** transactor that converts host-side transactions to bit signals and preserves interrupt-driven memory coherency between CPU and target IP [OS-aware IP Development Methodology, 2019].

## How it's used in practice

Two camps dominate, and they map onto the size of the controller. The **formal-first** camp treats the interrupt controller as the ideal IP for end-to-end formal: it is small, it is self-contained, and 'formally verifying a portion of the design helps to reduce the coverage space for the UVM testbench' even when UVM remains elsewhere in the flow [End to End Formal Verification Strategies for IP Verification, 2017]. Microsoft's methodology verifies the INTC and a crossbar purely formally, with no constrained-random scaffolding at all.

The **simulation- and emulation-first** camp handles the cases formal cannot reach — system-level routing, power interactions and software bring-up. Samsung's SystemVerilog environment has the IP owners functionally generate SPIs and PPIs while the GIC-600 continuously monitors the SV environment for interrupt ID, priority and target; ISR descriptors are fetched from DRAM (pointed at by `ISR_DESCRPTOR_BASE_ADDR`) and can be copied to the stack so the processor services interrupts in the shortest possible time [A Generic Verification Methodology for Chip to Chip Interrupt Handling, 2023]. The interesting features all live at the seams: the **Interrupt Routing Mode** register lets the GIC dynamically pick a target based on workload and power state, overriding the static router-programmed target; an inter-chip **low-power wake request** can turn a core on through the PMU handshake when an interrupt is routed to a cluster that is asleep; and a **Routing Table owner (RT owner)** on one die owns a programmable set of SPIs (bounded by `SPI_MIN` and `SPI_BLOCKS`) that it can forward to the other die once the cross-die connection is established [A Generic Verification Methodology for Chip to Chip Interrupt Handling, 2023]. Coverage of all these IRQ categories is a recognized line item in subsystem test plans — Qualcomm's video-subsystem testbench enumerates 'various categories of IRQs' alongside GPIO, AXI, FuSa, clock-controller and debug-subsystem scenarios [Scalable Test bench Architecture and Methodology for Faster Codec and Computer Vision Scenario Verification, 2022], and a reusable Modular Plug and Play Skeleton Structure (MPPSS) is one answer to keeping IRQ verification portable across SoCs [A novel approach to standardize reusable Modular Plug and Play Skeleton Structure (MPPSS), 2022].

## Pitfalls and where the field is heading

The hardest bugs are **power-state interactions and cross-chip races**. In Samsung's flow, 'when all the processor cores in a chip are busy or are in low power state and interrupt occurs to both the chips at the same time,' inter-chip routing must either pick a live core on the other die or generate a wake request and walk the PMU/cluster handshake to turn a core on — and any race here manifests as a lost, duplicated or out-of-priority interrupt, exactly the symptoms that escape directed tests and only surface under realistic traffic [A Generic Verification Methodology for Chip to Chip Interrupt Handling, 2023]. This is the class of bug where pure simulation under-covers and where formal-on-the-leaf-controller cannot reach; the practical answer is a hybrid where formal nails the leaf routing logic and a coverage-driven multi-threaded simulation/emulation environment exercises the power and cross-die seams [End to End Formal Verification Strategies for IP Verification, 2017].

Where is the field heading? Controllers are growing **virtualization extensions** (virtual interrupts, virtual CPU interfaces), more cores per cluster, and more die crossings as 3D-IC and chiplet designs push interrupt routing through TSVs and UCIe links. The verification space multiplies with each axis: priority, affinity, masking, virtualization and power state all interact, and the combinatorics dwarf what a human-directed plan can enumerate. The recurring industry instinct — build a generic, reusable methodology so the same IRQ verification harness survives a port from a single-die SoC to a multi-die 3D-IC [A Generic Verification Methodology for Chip to Chip Interrupt Handling, 2023] — is the right one, and it leans increasingly on portable stimulus, emulation and OS-aware co-verification to hit the latency-sensitive corner cases that decide whether a real workload boots cleanly.
