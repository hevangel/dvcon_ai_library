# Formal Verification for Security and Trust

> *Here is the unsettling premise of hardware security: your chip is built from third-party IPs you did not write, fabricated in a foundry you do not control, and shipped to customers you will never meet. Any of those touchpoints could insert a hardware trojan, leak a key through a side channel, or leave a privilege-escalation hole open. Simulation cannot catch these because it checks intended behavior — security bugs live in the unintended paths you never thought to test. Formal verification, by contrast, is built for negative proofs: "no unprivileged master can ever read this secret register." That is why the security community has embraced formal as its workhorse for confidentiality, integrity, and trojan hunting. Let's see how they actually do it.*

## The CIA triad as a property specification

The organizing framework for most formal security work is the **CIA triad** — confidentiality, integrity, and availability — recast as properties a design must satisfy. Confidentiality ensures sensitive data is accessible only to authorized parties; integrity guarantees critical data remains unaltered during transport or processing; availability keeps the system operational against denial-of-service [Formal Verification + CIA Triad: Winning Formula for Hardware Security, 2023]. Because SoCs contain multiple masters (cores, accelerators, devices) with unequal privileges, formal verification that the design satisfies these properties becomes a systematic way to detect and mitigate security risks.

The triad alone is too coarse to drive a real flow, so practitioners refine it into taxonomies. A ten-category hardware security classification aligned to the **Common Weakness Enumeration (CWE)** drives systematic property generation, with strategic abstraction and relaxed constraint handling to keep proofs tractable [Uncovering Hardware Vulnerabilities: Formal Verification for Security-Focused Negative Testing, 2025]. The flow integrates both **Security Path Verification (SPV)** and Formal Property Verification (FPV), treating security as a negative-testing problem. A scalable methodology formalizes the security requirements, constructs use-case scenarios, and builds a meaningful test suite that can be reused across platforms [Securing Silicon: A Scalable, Platform-independent Hardware Security Verification Methodology, 2024]. Even SoC address maps get this treatment, since an incompletely verified map is both a functional-safety and a security hole [Achieve Complete SoC Memory Map Verification, 2015], and error-handling paths that fail to report faults can expose denial-of-service vulnerabilities [Accelerating Error Handling Verification of Complex Systems, 2022].

## Hunting hardware trojans and untrusted IPs

Trojan hunting is where formal security earned its reputation. Integrated circuits increasingly include third-party IPs that could contain **hardware trojans** inserted at the RTL or gate level, and traditional pre-silicon verification has little chance of detecting them because it targets intended use cases, not deliberately hidden functionality [An Automated Pre-silicon IP Trustworthiness Assessment for Hardware Assurance, 2020]. The gold standard is an independent, trusted IP model that can be formally compared against the RTL — but such models are rarely available outside critical IPs like RISC-V cores. The proposed workaround is an IP trustworthiness assessment that needs no trusted model: it scans the RTL for suspicious logic, validated on real-world MIL/Aero IPs (SpaceWire, RISC-V Taiga, LEON3) seeded with trigger-and-payload trojans from Aerospace's catalog [An Automated Pre-silicon IP Trustworthiness Assessment for Hardware Assurance, 2020].

The trojan threat has followed the industry into machine-learning hardware. Neural-network accelerators are themselves vulnerable to trojan attacks that perturb classification results, and formal verification offers a way to detect malicious behavior inserted into otherwise well-trained designs [Hardware Trojan Design and Detection with Formal Verification to Deep Neural Network, 2021]. The same CWE-driven lens now applies to AI-generated RTL: when LLMs produce SystemVerilog, formal verification can categorize each generated design as vulnerable or CWE-free, exposing the security weaknesses that generative models bake in [All Artificial, Less Intelligence: GenAI through the Lens of Formal Verification, 2024]. Across all of these, the shared lesson is that security verification must reason about what the design could do, not what it is specified to do.

## Information flow, taint, and scaling security proofs

Trojan detection is one face of the problem; **information flow tracking** is the other. Security requirements can be formalized as taint-propagation properties — proving that sensitive data cannot leak toward unwanted interfaces — and this is the basis of dedicated formal security-path applications born from real chip-development needs [Checking security path with formal verification tool, 2014]. A RISC-V low-power processor flow shows how broadly formal security reaches: beyond functional correctness, it covers architectural verification, lockstep checks for functional safety, X-issues from low-power design, and security, finding bugs in already-taped-out cores while establishing bug absence through exhaustive proofs [Formal verification of low-power RISC-V processors, 2019].

The persistent challenge is **scale**. Code review and formal verification involve significant manual effort, and scalability suffers as design size and complexity grow [Securing Silicon, 2024]. Modern answers combine formal with complementary techniques: simulation and formal methods together, with security coverage measured as part of the sign-off strategy [Effective Methodologies to Accelerate Security Verification, 2026]; symbolic execution for embedded software in frameworks like Symex that target safety, security, and dependability [Minimally Intrusive Safety and Security Verification of Rust RTIC Applications, 2025]; and pragmatic mixes where simulation and formal complement each other to hit the verification objective [Making Security Verification "SECURE", 2018]. Where trusted reference models exist, end-to-end formal proof of components like floating-point dot-product systolic units also underpins the security story by guaranteeing the silicon matches a trusted spec [Achieving End-to-End Formal Verification of Large Floating-Point Dot Product Accumulate Systolic Units, 2024].

- **Minimally Intrusive Safety and Security Verification of Rust RTIC Applications** (2025, DVCon Europe) — Pawel Dzialo, Ivar Jönsson and Malte Münch. Symbolic-execution-based verification extending Symex toward machine-code-level guarantees.
- **Accelerating Error Handling Verification of Complex Systems: A Formal Approach** (2022, DVCon US) — Bhushan Parikh, Peter Graniello and Neha Rajendra. Formal error-handling verification to close denial-of-service exposures in Smart NICs.
- **Effective Methodologies to Accelerate Security Verification** (2026, DVCon US) — Lee Anthony Grajo, Ponnambalam Lakshmanan and Anders Nordstrom. Combining formal and simulation security verification with coverage-driven sign-off.
- **Making Security Verification "SECURE"** (2018, DVCon US) — Subin Thykkoottathil and Nagesh Ranganat. How simulation and formal methods complement each other for security sign-off.
- **Checking security path with formal verification tool: new application development** (2014, DVCon US) — Julia Dushina, Saumil Shah and Joerg Mueller. The STMicroelectronics-driven formal app proving sensitive data cannot leak to unintended interfaces.
- **Achieving End-to-End Formal Verification of Large Floating-Point Dot Product Accumulate Systolic Units** (2024, DVCon US) — Emiliano Morini, Bill Zorn and Disha Puri. Trusted-reference-model proofs that anchor the security story for ML hardware.
