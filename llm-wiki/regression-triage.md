# Regression Triage and Root-Cause Automation

> *"Picture the scene: it is 9 a.m., the nightly regression finished, and 200 tests failed. Of those 200, maybe 12 are real new bugs and the rest are duplicates, environment hiccups, or known issues from yesterday. The triage engineer's job is to figure out which is which — and to route each cluster to the right owner before lunch. Gordon Allan calls triage 'that part of the design/verification process where failing test results from a regression run are prepared for analysis, categorized, dispatched to available resources where the real debug takes place,' and warns that 'this activity can be a productivity drain, poorly executed, leading to iteration and waste.' Sean Safarpour went further in 2012 and called failure triage 'the neglected debugging problem' — important, challenging, and mostly ignored by the verification community. Fourteen years later it is no longer neglected: Random Forest classifiers assign owners, LLMs cluster logs, and multi-agent systems feed run outcomes straight back into the next triage decision. The 200-failure morning is still real, but the human in the loop is shrinking. So how does an automated triage pipeline actually work, and where does the human still have to sit?"

## What it is

**Triage** is the initial phase of debug where a large set of failing tests is analyzed, grouped by the likelihood of sharing a root cause, and routed to the rightful owner — fast, before anyone wastes time debugging the wrong thing. Allan distinguishes it sharply from the medical-emergency sense of the word: 'triage of regression failures in microelectronic design verification has one important difference to triage of medical issues... Those scenarios involve random one-off occurrences... there is no concept of repetition, or grouping, that can inform the triage process' [Evolution of Triage, 2016]. In chip verification, by contrast, the same bug surfaces across many tests, and recognizing that repetition is the whole game. He identifies multiple kinds of triage activity — triage to determine resource focus, to identify systemic failures, to deduce common root causes from symptom data — and notes that good triage 'can provide a head start on that debug activity when there are many failing tests.'

The technical core is the **signature**. Safarpour, Qin and Yang frame the whole problem around it: 'most failure triage is performed using an error message from failing checkers or assertions,' which 'typically provides better than random prediction' but is imprecise, and 'the lack of information about the bug source is the primary drawback of just using error messages' [Failure Triage, 2012]. The fix is to enrich the signature — combining error messages with state-transition traces, propagation paths, and root-cause-analysis tool output to 'more accurately group similar failures together.' Vikramsimhan, Narayanaswamy and Sadasivam make the operational case for the same enrichment: a typical debug engineer 'had to glance through hundreds of known errors and failure signatures day after day, before hitting the important new failure signature that could potentially turn into RTL bug,' with bugs 'silently remaining in the RTL for many weeks' from lack of bandwidth [Pre-Silicon Debug Automation using Transaction Tagging and Data-Mining, 2014].

## How it's used in practice

The modern triage pipeline runs **transaction tagging, data-mining, and ML classification**. Vikramsimhar et al.'s transaction-tagging approach instruments the regression so that 'with manual' triage replaced by automation, the engineer stops scrolling log files and instead lets the system cluster and surface the new bugs. A decade later this same instinct has matured into ML-driven owner assignment. Shi and Mathur's Random-Forest-based system 'not only predicts the correct owner of a testcase failure but also assigns the failure signature autonomously, thereby significantly reducing the time and manual labor currently involved' [Automating Regression Triage in Design Verification Using AI-Based Random Forest Models, 2025]. Sai, Gupta and Sathakath make the parallel move on the *prioritization* axis — instead of just bucketizing, their ML 'assigns debug priorities' so the team chases the failures most likely to be real design bugs first [Exploring Machine Learning to assign debug priorities, 2023].

The pipeline also has to handle **scale and cost honestly**. Noh, Choi and Yim observe that 'while regression automation pipelines reduce manual execution, they remain largely linear and execution-centric: failure and coverage signals are often siloed, so a human manager must interpret and relay them,' which 'increases turnaround time and creates persistent bottlenecks when designs or verification environments change' [Multi-Agent Orchestration for Autonomous Regression Management, 2026]. Their 3-tiered agentic framework structures regression into user, block, and central tiers — each 'aligned with a distinct verification scope' — to fix the monolithic-regression scalability problem [A 3-tiered agentic AI Framework for Verification Regression, 2026]. And once LLMs enter the loop, a new operational concern surfaces: Jose's Passive Token Accounting argues that continuous regressions generate 'tens of thousands of logs; each LLM call, however small, accumulates into non-trivial cloud bills,' and 'traditional EDA infrastructure has no native notion of LLM cost,' leaving verification leads unable to answer what the triage bot actually cost [Passive Token Accounting, 2026].

## Pitfalls and where the field is heading

The first pitfall is that **triage quality is bounded by signature quality**, and signatures are still hard. The same root cause can produce wildly different error messages depending on stimulus; conversely, the same error message can come from different bugs. Allan's prescription is that 'a good test environment will add value to the failure analysis process... by recording meaningful observations and data in a way that the triage engineer can observe commonality of symptom, and possible commonality of root cause' — i.e. instrumentation has to be designed in, not bolted on. Without it, even the best classifier is sorting noise.

The second pitfall is **post-silicon scale**, where triage inherits the slowness of one-chip-per-cycle. Kallimatada, Sunkari and Kapchits describe data-center RMA triage: 'traditional debugging methods, reliant on physical access and intrusive' techniques fail at scale, motivating their 'remote and probeless debug methodology' [Remote and Probeless Debug Methodology for Data Center Silicon Debugs, 2025]. Vemulapatti and Datta attack a related human problem: in large SoC projects the debug knowledge lives in a few heads, so when a DV engineer 'new to a reused block, encounter test failures and must rely on colleagues with prior experience,' delays compound across time zones — their experience-driven debug-assistance tool captures that tribal knowledge [Accelerating Debug with Experience-Driven Insights, 2025].

The trajectory is unmistakable: **triage is becoming an autonomous agent loop**. Chung, Cha and Kim's Smart Sanity Regression 'emphasizes workflow-level orchestration rather than individual AI techniques, unifying change-impact analysis, intelligent testset optimization, failure' handling into one end-to-end flow [A Novel Fast Regression, 2026]. Kashide, Chinni and Srivastava report that 'over all verification effort can take up to 65% of whole design cycle,' with debug over 50% of verification effort, and respond with a full AI/ML regression flow [A Novel AI-ML Regression Flow for SoC verification, 2025]. The human triage engineer isn't disappearing — Allan is right that triage 'can only be done well by people' when it comes to judgment — but the routing, clustering, and prioritization that used to eat the morning are now machine work. What's left for the human is the harder part: deciding what the cluster actually means.
