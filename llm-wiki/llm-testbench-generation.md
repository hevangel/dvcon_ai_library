# LLMs for Testbench Generation

> You have spent the better part of a decade memorizing `uvm_config_db` incantations, and now a chatbot claims it can write your testbench for you in twenty seconds. It sounds absurd, and often is — but something real is happening here. A modern large language model has ingested more SystemVerilog than any human will read in a lifetime, and it can produce an AMBA APB3 agent that, on a good day, actually compiles. The deeper question is no longer "can it write code?" but "can it write *correct* verification code, and how would we even know?" That second question is what makes this the most watched, most hyped corner of DVCon right now. So let's dig in.

## What it is and how we measure it

**LLM-based testbench generation** is the practice of prompting a large language model — proprietary (GPT-4o, Gemini, Claude) or open (Llama, Mistral, Gemma) — to emit SystemVerilog and UVM scaffolding, sequences, scoreboards, or even entire verification IPs from natural-language specifications or existing RTL. The output is then fed into the same simulator and coverage flow a human-written testbench would use, so the model is judged on the only metrics that matter in verification: does it compile, does it close coverage, does it catch bugs.

The hard part is the judging. VerilogEval and RTLLM established open benchmarks for RTL *design* generation, but testbench generation lagged until **VerifLLMBench** laid out a structured methodology for benchmarking UVM testbench output across line, branch, toggle, and assertion coverage on small DUTs like accumulators and FSMs [VerifLLMBench, 2025]. The benchmark wraps each model iteration behind preprocessor macros (`\`ifdef GPTt1`, `\`elsif Geminit4`) so the same top-level harness can swap in testbenches from different LLMs without touching the testbench structure. The early finding is blunt: in the absence of designer-authored assertions, assertion coverage is 0% on every DUT, which makes the metric useless until the LLM is also asked to generate assertions — a hint that benchmarking only the testbench body understates the problem.

The benchmark effort also makes the model hierarchy explicit. Proprietary models such as ChatGPT-4o tend to dominate coverage metrics, often reaching near-perfect line coverage on simple accumulator and FSM designs [VerifLLMBench, 2025]. Open-source alternatives trail, and **Generative AI based RTL Code Generator** shows that fine-tuning a sub-7B-parameter model on a custom Verilog instruction dataset can close much of that gap against GPT-3.5, despite being one to three orders of magnitude smaller [Generative AI based RTL Code Generator, 2024].

## How teams are putting LLMs to work

The most production-oriented uses do not ask the model to write an entire testbench from scratch. They ask it to do the parts humans hate. **Requirements Recognition for Verification IP Design Using Large Language Models** fine-tunes GPT-2 to extract verification requirements from a protocol spec like M-PHY 4.1, hitting Precision 0.618 and Recall 0.874 — worse than a senior engineer, but the model never gets bored and the labels feed downstream VIP construction [Requirements Recognition for Verification IP Design Using Large Language Models, 2024]. **GAIL-V** argues that the entire verification organization needs a structured framework for *where* Gen-AI fits — planning, debug, stimulus generation — rather than ad hoc experiments, and offers a taxonomy for assessing each insertion point [GAIL-V, 2025].

Other work goes after the human-in-the-loop bottlenecks directly. **A New Approach Of Hardware Verification Through Natural Language Queries** lets engineers ask questions of the design and verification environment in plain English, turning an LLM into a query interface over EDA artifacts [A New Approach Of Hardware Verification Through Natural Language Queries, 2024]. **Using Aider to build a VIP with UVM-SV and PyUVM** is the most candid field report in the set: it walks an AI pair-programmer (Aider) through generating an AMBA APB3 VIP in both SystemVerilog/UVM and Python/cocotb+PyUVM, and reports honestly on what the assistant gets right and where it produces syntactically broken or functionally wrong code [Using Aider to build a VIP with UVM-SV and PyUVM, 2025]. **Large Language Model for Verification: A Review and Its Application in Data Augmentation** surveys the full landscape — requirement engineering, coverage closure, formal, debugging, functional safety, code completion — and then demonstrates prompt-driven generation of design *variants* and matching verification code, with measurable productivity gains over hand-authoring training data [Large Language Model for Verification, 2024].

A second wave targets the regression itself. **A Large Language Model-Based Framework for Enhancing Integrated Regression** attacks test prioritization, log overload, and data-availability gaps in nightly regression, while **An Early Stage Coverage Measurement Methodology** defines a Common Task Coverage (CTC) scheme whose bins are derived from design metadata by an LLM, enabling coverage measurement before any simulation has run [A Large Language Model-Based Framework for Enhancing Integrated Regression, 2025][An Early Stage Coverage Measurement Methodology, 2025].

## Pitfalls, hallucinations, and where this is heading

The cheerleading papers are easy to find; the cautionary ones are more useful. **All Artificial, Less Intelligence: GenAI through the Lens of Formal Verification** is a punch to the gut: the authors generate 60,000 SystemVerilog designs across four LLMs, run formal verification against ten Common Weakness Enumerations (CWEs), and report how often the LLM-emitted RTL is silently vulnerable [All Artificial, Less Intelligence, 2024]. The lesson generalizes — an LLM that writes plausible-looking verification code can also write plausible-looking *bugs*, and a testbench that compiles is not a testbench that finds anything.

There are also gaps the field has not closed. Open-source models still trail proprietary ones on raw UVM fluency, and fine-tuning small models remains expensive despite promising results [Generative AI based RTL Code Generator, 2024]. Hallucinated class names, misused factory overrides, and confidently-wrong phase usage are routine. Debugging is the other frontier: **FVDebug** points the same class of models at *understanding* failures, automating root-cause analysis across waveforms, RTL, and design intent when formal properties trip [FVDebug, 2026]. The trajectory is clear — models that generate verification are starting to consume their own output, and the line between author and auditor is blurring.

## Grounded in these DVCon papers

- **VerifLLMBench: An Open-Source Benchmark for Testbenches Generated with Large Language Models** (2025, DVCon US) — Nishanth Somashekara Murthy, Eldon Nelson and Sachin S. Sapatnekar. The first open benchmark and methodology for evaluating LLM-generated UVM testbenches across line, branch, toggle, and assertion coverage.
- **Generative AI based RTL Code Generator** (2024, DVCon India) — Hareesh Perumal S, Gandem Kranthi Kiran and Pathak Vishnu Dutt. Fine-tunes a sub-7B-parameter model on a custom Verilog instruction dataset to rival GPT-3.5 at a fraction of the size.
- **FVDebug: An LLM-Driven Debugging Assistant for Automated Root Cause Analysis of Formal Verification Failures** (2026, DVCon US) — Yunsheng Bai, Ghaith Bany Hamad and Chia-Tung Ho. An LLM system that fuses waveforms, RTL, and design intent to automate formal-failure root-cause analysis.
- **Requirements Recognition for Verification IP Design Using Large Language Models** (2024, DVCon US) — S. S. Zalivaka. Fine-tunes GPT-2 to extract verification requirements from protocol specifications, with measured precision and recall on M-PHY 4.1.
- **GAIL-V: Generative AI Leveraged -Verification** (2025, DVCon Europe) — Sriram Madavswamy and Daniel Larkin. A systematic framework for assessing where and how generative AI fits across the hardware verification lifecycle.
- **A New Approach Of Hardware Verification Through Natural Language Queries** (2024, DVCon India) — Priya Aggarwal, Samuel Katapur and Parth Bhatia. Uses LLMs as a natural-language query interface over EDA verification artifacts.
- **Large Language Model for Verification: A Review and Its Application in Data Augmentation** (2024, DVCon US) — Dan Yu, Eman El Mandouh and Waseem Raslan. A literature review of LLMs across verification tasks plus a data-augmentation demonstration generating design and verification-code variants.
- **Breaking barriers in Advanced Multi-Chiplet AI SoCs using scalable UCIe and Boot Verification and Emulation techniques** (2025, DVCon India) — Harshal Kothari, Eldin Ben Jacob and Ayush Agrawal. Multi-die SoC verification context in which LLM-assisted flows are increasingly being deployed.
- **All Artificial, Less Intelligence: GenAI through the Lens of Formal Verification** (2024, DVCon US) — Deepak Narayan Gadde, Aman Kumar and Thomas Nalapat. Formally verifies 60,000 LLM-generated SystemVerilog designs to catalog Common Weakness Enumerations.
- **Unleashing the Power of Whisper for blocklevel verification in high performance RISC-V CPU** (2024, DVCon US) — Chenhui Huang, Yu Sun and Joe Rahmeh. An ISS-plus-UVM framework that translates designer-described scenarios into block-level stimulus.
- **Using Aider to build a VIP with UVM-SV and PyUVM** (2025, DVCon Europe) — André Winkelmann and Damir Ahmetovic Ignjic. A candid field report on using an AI pair-programmer to generate an AMBA APB3 VIP in UVM-SV and PyUVM.
- **A Large Language Model-Based Framework for Enhancing Integrated Regression** (2025, DVCon US) — Jin Choi, Sangwoo Noh and Seonghee Yim. Uses LLMs to attack test prioritization, log overload, and data availability in integrated regression.
- **An Early Stage Coverage Measurement Methodology For Common Features Of System-On-Chip Verification, Using Design Metadata And Large Language Models** (2025, DVCon US) — Myeongwhan Hyun, Jaehyeok Lee and Jin Choi. Defines Common Task Coverage with LLM-derived bins for pre-simulation coverage measurement.
