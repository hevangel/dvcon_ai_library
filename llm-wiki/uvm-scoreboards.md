# UVM Scoreboards and Predictors

> *Here is the question every UVM testbench ultimately answers: did the DUT produce the right output? The driver pumps in stimulus, the monitor watches the pins, but neither of them knows whether the result on the output port is correct — they only know what happened. The scoreboard is the referee. It collects actual transactions from the DUT, computes the expected result through some reference model, and compares the two. When they match, you have a self-checking testbench; when they don't, you have a bug to chase at 2am. Despite the conceptual simplicity, fifteen years of DVCon papers argue the scoreboard is where teams quietly under-invest, then hit "spaghetti code along the way to work around" the limitations they never anticipated. So how do you build one that scales, and where do the reference models live? Let's dig in.*

## The scoreboard's role and the reference-model question

A UVM scoreboard is the component — typically a `uvm_scoreboard` subclass connected to monitor analysis ports via `uvm_tlm_analysis_fifo` — responsible for **self-checking**: comparing the DUT's observed behavior against an expected behavior computed from a reference. Gordon Allan's foundational "Architectural Considerations for Scoreboard Design" lays out the core tension: as DUTs grow more convoluted in algorithm or more software-configurable in function, naive scoreboard architectures break, and project teams "hit limitations, creating spaghetti code along the way to work around them" [Part 1 of 2 - Architectural Considerations for Scoreboard Design, 2012]. The remedy is to equip teams up front with a toolbox of architectural elements rather than letting each project rediscover them.

The first architectural choice is where the reference model lives. Two patterns dominate. In the **inline-model** pattern, the reference is computed separately from the scoreboard and the scoreboard is reduced to a like-for-like comparator of expected versus observed; this is appealing because it keeps the scoreboard simple. In the **bound-model** pattern, the model is treated as an element plugged into the scoreboard, so the scoreboard owns both the model and the comparison logic [Part 1 of 2 - Architectural Considerations for Scoreboard Design, 2012]. The bound pattern tends to win as DUTs get more complex, because the model and the comparison logic end up needing shared state that a clean separation cannot express. The Samsung image-sensor work makes this concrete: each image-processing sub-block gets its own scoreboard fed by a C reference model, with the scoreboard class itself staying generic and the per-block packing and comparison logic pushed into callbacks [An Elegant scoreboard eco-system deploying UVM Callbacks, Parameterization, 2023].

## Frameworks, scalability, and architectural separation

Because most teams rebuild scoreboards from `uvm_scoreboard` each project, several papers argue for shared frameworks. The SyoSil "Versatile UVM Scoreboarding" library is the canonical example, designed around three properties: scalability, architectural separation, and connectivity to foreign environments [Versatile UVM Scoreboarding, 2014]. Architecturally the scoreboard can simultaneously interface and compare any number of models — RTL design models, timed or untimed reference models in SystemVerilog, SystemC, or Python, and even physical devices like FPGA prototypes or ASICs [Versatile UVM Scoreboarding, 2015]. The comparison engine keeps separate DUT and REF queues per port, optionally mirroring input queues purely to aid debugging, since "this will not add value to the performed checks, but will greatly aid the debug situation, as the queues will present both input and output DUT/REF traffic" [Versatile UVM Scoreboarding, 2014]. The reported payoff is roughly 15% code reduction versus building from scratch, with setup possible in under a day even for complex designs [Versatile UVM Scoreboarding, 2015].

The framework approach also addresses a recurring pain: integrating foreign reference models. Self-contained SystemC/TLM virtual prototypes are notoriously hard to fold into a UVM scoreboard as an "expect" function, so a well-separated architecture makes room for them [Versatile UVM Scoreboarding, 2014]. The same separation is what lets DPI-C bridges synchronize a C model with the UVM testbench in real time: by integrating DPI-C functions into the UVM Register Abstraction Layer adapters, the predictor can update dynamically as bus traffic flows, "significantly reducing the manual effort typically required by UVM predictors and scoreboards" [Real-Time Synchronization of C model with UVM Testbench, 2025]. When the reference model is written in MATLAB or Python rather than C, the same pattern applies with a different bridge [A Survey of Predictor Implementation using High-Level Language Co-simulation, 2025].

## Pitfalls: resets, multi-language environments, and reuse

The corpus flags several practical traps. The first is **on-the-fly reset**: when the DUT is reset mid-operation, the scoreboard must halt its checks and return to a known initial state, otherwise it raises spurious mismatches. OVM and UVM both offer mechanisms to propagate reset into monitor, driver, and scoreboard, but UVM's reset-aware phase machinery makes this far cleaner than in OVM [OVM & UVM Techniques for On-the-fly Reset, 2012]. The second trap is the **multi-language reference model**. For a modern CPU, an accurate reference model is the usual practice, but as CPU performance work continuously modifies the design, replicating those modifications in the reference is error-prone and risks imitation; an adaptive scoreboard methodology that performs truly functional verification of the CPU core sidesteps this [Novel Adaptive CPU Scoreboard Methodology for a Multi-language environment, 2022].

A third pitfall is **scoring latency** in high-speed serial systems. Building a TLM-based reference model that supports multiple design standards (PCIe, USB, DP) in a single PHY is increasingly hard, and traditional post-processing requires the entire test to finish before results are visible. The "Breaking the Wait" paper offers a customizable real-time post-processing scheme that lets users see intermediate results during execution at user-defined granularity [Breaking the Wait, 2026]. SVA and scoreboards are also commonly used in isolation rather than in concert; bridging them through `uvm_config_db` lets control events and informational parameters flow bidirectionally, which quickens debug [Calling All Checkers, 2021].

The fourth and most strategic trap is **vertical reuse**. When verification environments are reused bottom-up from block to subsystem to SoC, the reference models must compose hierarchically — and that composition is rarely automatic. Geishauser et al. argue the vertical reuse of reference models is the key to scaling random verification against designs whose complexity formal methods alone cannot reach [Vertical Reuse of Reference Models in UVM, 2025]. The lesson across the corpus: treat your scoreboard and predictor as architecture, not boilerplate, because every level of integration will stress-test the assumptions you baked in at block level.

## Grounded in these DVCon papers

- **Part 1 of 2 - Architectural Considerations for Scoreboard Design** (2012, DVCon US) — Gordon Allan. Foundational treatment of scoreboard architecture, including the inline vs bound reference-model patterns.
- **Versatile UVM Scoreboarding** (2014, DVCon Europe) — Jacob Andersen, Peter Jensen and Kevin Steffensen. Reusable scoreboard framework emphasizing scalability, architectural separation, and foreign-model connectivity.
- **Versatile UVM Scoreboarding** (2015, DVCon US) — Jacob Andersen, Peter Jensen and Kevin Steffensen. US-paper companion with success stories and the ~15% code-reduction metric.
- **An Elegant scoreboard eco-system deploying UVM Callbacks, Parameterization for Multimedia designs from Imaging perspective** (2023, DVCon Europe) — Chakravarthi Devakinanda Vurukutla, Sahana Ranganathan and Devendra Satish Bilaye. Generic scoreboard with per-block callbacks parameterizing reference models for an image-sensor pipeline.
- **OVM & UVM Techniques for On-the-fly Reset** (2012, DVCon US) — Muralidhara Ramalingaiah and Boobalan An. Mechanisms for halting and resetting scoreboard checks mid-test in OVM and UVM.
- **Novel Adaptive CPU Scoreboard Methodology for a Multi-language environment** (2022, DVCon India) — Pooja Madhusoodhanan, Saya Goud Langadi and Labeeb K. Adaptive scoreboard for CPU verification that avoids error-prone reference-model imitation.
- **Breaking the Wait: Customizable, Real-Time Post-Processing for Data Integrity Verification in SerDes Systems** (2026, DVCon US) — Chandana K N and Suresh Gandhi S. Real-time post-processing scoreboard for multi-standard SerDes PHYs.
- **Calling All Checkers: Collaboratively Utilizing SVA In UVM Based Simulation** (2016, DVCon US) — Hui K. Zhang. Bridges SVA and scoreboards via `uvm_config_db` for bidirectional control and debug info sharing.
- **Doing Funny Stuff with the UVM Register Layer: Experiences Using Front Door Sequences, Predictors, and Callbacks** (2017, DVCon US) — John Aynsley. Practical treatment of the UVM register predictor and its interaction with front-door sequences.
- **Efficient and Exhaustive Floating Point Verification Using Sequential Equivalence Checking** (2017, DVCon US) — Travis W. Pouarz and Vaibhav Agrawal. Uses SEC against a reference model for FPU blocks — a scoreboard-equivalent for arithmetic.
- **SystemVerilog FrameWorks Scoreboard: An Open Source Implementation Using UVM** (2011, DVCon US) — Ambar Sarkar. Open-source UVM scoreboard utility filling the pre-standard gap.
- **Wrapping Verilog Bus Functional Model (BFM) and RTL as Drivers in Customized UVM VIP Using Abstract Classes** (2015, DVCon US) — Roman Wang and Thomas Bodmer. VIP wrapping pattern that supplies the monitor/scoreboard traffic in active or passive mode.
- **Vertical Reuse of Reference Models in UVM** (2025, DVCon Europe) — Joachim Geishauser, Ciro Ceissler and Leo Tran. Argues reference models must compose hierarchically to support bottom-up UVM reuse.
- **A Survey of Predictor Implementation using High-Level Language Co-simulation** (2025, DVCon US) — Sean Little. Survey of predictors implemented in MATLAB/Python/C++ via DPI rather than pure SystemVerilog.
- **Real-Time Synchronization of C model with UVM Testbench** (2025, DVCon US) — Kirtan Mehta. DPI-C functions in RAL adapters for real-time synchronization of C reference models with UVM.
