# UVM Reuse — Vertical and Horizontal

> *The Holy Grail of UVM is reuse, and like the real Holy Grail it is sighted often and captured rarely. The promise is seductive: build your testbench once at the block level, then magically carry it up through subsystem and SoC integration (vertical reuse), and across from one project to the next (horizontal reuse). When it works, the engineering time saved is enormous — a 200M-gate ASIC's system testbench built by recursively importing lower-level testbenches, new system-level testcases written in under 20 lines of code, system-level bugs debugged by simply enabling the module UVC monitors in passive mode. When it doesn't work, you inherit a tower of fragile abstractions that breaks the moment a parameter changes. So how did the practitioners actually pull it off? Let's dig in.*

## What vertical and horizontal reuse mean

**Vertical reuse** is the reuse of a verification environment across the hierarchy of integration — block to subsystem to SoC within a single project. The argument for it is economic: given the size and complexity of modern ASICs and SoCs, building a full system-level environment from scratch is impractical, and the only realistic way to scale verification is to import lower-level testbenches into the system testbench so that "changes in lower level testbenches propagate automatically to the system level testbench" [Maximize Vertical Reuse, Building Module to System Verification Environments with UVM e, 2013]. **Horizontal reuse** is the reuse of verification components from one project to the next — typically VIPs and the environment infrastructure that wraps them [Highly Configurable UVM Environment for Parameterized IP Verification, 2015].

The two directions interact. A self-adapting parameterized IP UVC — one that updates itself automatically as design parameters like port protocol, port number, or internal logic change — can be reused vertically because its bind method separates verification code from RTL, and horizontally because the whole IP Module UVC can be carried to a new project with UVM factory overrides like `set_type_override_by_type()` and `set_inst_override_by_type()` swapping in extended packets [Highly Configurable UVM Environment for Parameterized IP Verification, 2015]. The same logic extends to register-layer standardization: the UVM 1.0 `UVM_REG` base classes were the first time the three major vendors aligned on a single register layer implementation, and that alignment was explicitly motivated by enabling horizontal and vertical reuse [Registering the standard: Migrating to the UVM_REG code base, 2012].

## How vertical reuse is actually built

The PMC-Sierra paper, proven on a 200M-gate ASIC, lays out a concrete framework with three enhancements to the base UVM System UVC architecture: recursive import of subsystem and module testbenches, a common configuration control so the system testbench can export its configuration to lower-level testbenches (letting lower-level engineers recreate and debug failed system scenarios), and plug-and-play integration that lets system verification engineers focus on system-level issues without being overloaded by lower-level operational details [Maximize Vertical Reuse, Building Module to System Verification Environments with UVM e, 2013]. A standardized **testflow** with procedural hooks — configure the device, start traffic, wait for stability, an empty method hook for testcase stimulus, graceful termination, post-simulation checks — gives every level a common execution skeleton.

The measurable benefits are substantial. The same paper reports system-level testcases written in under 20 lines of code by importing two subsystem testcases and constraining them for coherent traffic, plus dramatically faster system-level debug turnaround because the module UVCs' internal monitors can be enabled in passive mode to localize a bug [Maximize Vertical Reuse, Building Module to System Verification Environments with UVM e, 2013]. The dependency-injection design pattern extends this to power-aware tests, allowing a single testbench structure to flex across power-aware and non-power-aware scenarios [Using Dependency Injection Design Pattern in Power Aware Tests, 2021]. The common thread is OOP discipline: flexible architectures that let a single testbench support unit-level, top-level, system-level, and encrypted-model integration all from the same code base [Testbench flexibility as a foundation for success, 2021].

## Pitfalls and the limits of automation

The first hard truth, stated bluntly in the NXP paper's title, is that **"Reuse doesn't come for free"** — the same level of RTL reuse enabled by CoReUse and the Reuse Methodology Manual has simply not been achieved for verification IPs, subsystems, and SoCs, even with SystemVerilog and UVM providing a solid framework [Reuse doesn't come for free - learnings from a UVM deployment, 2016]. Vertical reuse requires deliberate up-front architecture; the easiest pitfall is to start coding with the expectation of a simplistic environment and hit limitations later.

The second pitfall is methodology mismatch. The UVM e framework above leans on Aspect Oriented Programming (AOP), but SystemVerilog does not support AOP, and many of the module-to-system UVC features in e have to be reimplemented with design patterns in SV — feasible but "less convenient as it requires more up front planning" and access to the module UVC source code in case the system engineer must modify it [Maximize Vertical Reuse, Building Module to System Verification Environments with UVM e, 2013]. Code review matters: a 30% simulation performance improvement came from rewriting a dozen lines of bad code in that same project.

The third pitfall is the **boundary of automation**. As SoCs integrate more diverse and software-driven components, vertical reuse is increasingly being captured as Portable Stimulus Standard **Portable Models (PMs)** that combine abstract scenario definitions with realization-layer bindings to design interfaces. Bardonek et al. apply a static-analysis toolchain to a real-world SoC and show that there are real limits to how much of the integration can be auto-generated from PMs — the boundaries depend on the diversity of the components and the realization layer's expressiveness [Exploring the Limits of Vertical Reuse Automation in PSS-Driven SoC Verification, 2025]. Coherency and deadlock verification on automotive and mobile SoCs illustrate the same point: PSS tools like Perspec shorten verification of these areas substantially, but they do not eliminate the need for carefully authored scenario intent [Coherency Verification & Deadlock Detection Using Perspec/Portable Stimulus, 2019]. The Python-based `pyuvm` reimplementation of IEEE 1800.2 even asks whether a different language substrate would make reuse easier [Verification Learns a New Language, 2021]. Vertical reuse, in other words, remains less a solved problem than a continuously renegotiated contract.

## Grounded in these DVCon papers

- **Maximize Vertical Reuse, Building Module to System Verification Environments with UVM e** (2013, DVCon US) — Horace Chan, Brian Vandegriend and Deepali Joshi. Framework with recursive import, common configuration control, and testflow proven on a 200M-gate ASIC.
- **Exploring the Limits of Vertical Reuse Automation in PSS-Driven SoC Verification** (2025, DVCon Europe) — Petr Bardonek, Alessandra Dolmeta and Marcela Zachariášová. Static-analysis toolchain exposing the practical limits of auto-generating vertical reuse from PSS Portable Models.
- **Vertical Reuse of Reference Models in UVM** (2025, DVCon Europe) — Joachim Geishauser, Ciro Ceissler and Leo Tran. Argues reference models must compose hierarchically to support bottom-up UVM reuse.
- **Highly Configurable UVM Environment for Parameterized IP Verification** (2015, DVCon US) — HongLiang Liu and Karl Whiting. Self-adapting AMBA-fabric UVM environment with Ruby scripts for both vertical and horizontal reuse via factory overrides.
- **Using Dependency Injection Design Pattern in Power Aware Tests** (2021, DVCon Europe) — Mehmet Tukel, Luca Sasselli and David Guthrie. Dependency injection as the reuse lever for power-aware test scenarios.
- **Ultimate Shift Left: Unleash the Power of UVM Virtual LAB Methodology upon SoC Verification** (2018, DVCon US) — Roman Wang. vLAB methodology supporting reusability, scalability, and flexibility for IP/SoC verification.
- **Reuse doesn't come for free - learnings from a UVM deployment** (2016, DVCon Europe) — Sumeet Gulati, Srinivasan Venkataramanan and Azhar Ahammad. Lessons learned from mobile-audio-chip UVM deployment; reuse falls short of RTL-domain CoReUse.
- **Registering the standard: Migrating to the UVM_REG code base** (2012, DVCon US) — Sachin Patel, Amit Sharma and Adiel Khan. The UVM_REG standardization that first enabled horizontal and vertical register-layer reuse.
- **Reuse of System-Level Verification Components within Chip-Level UVM Environments** (2021, DVCon Europe) — Diego Alagna, Marzia Annovazzi and Alessandro Cannone. Brings system-level verification components into chip-level UVM to find bugs early and shorten bug lead time.
- **Testbench flexibility as a foundation for success** (2021, DVCon Europe) — Ana Sanz Carretero, Katherine Garden and Wei Wei Cheong. OOP-based coding methodology letting a single UVM testbench support all integration levels.
- **Verification Learns a New Language: - An IEEE 1800.2 Implementation** (2021, DVCon US) — Ray Salemi and Tom Fitzpatrick. Introduces `pyuvm`, a Python implementation of IEEE 1800.2, questioning the language substrate for UVM reuse.
- **Advantages of using UVM/System Verilog IEEE standards to Verify Complex Probabilistic Constellation Shaping Design** (2020, DVCon US) — Nipun Bhatt. Demonstrates UVM/SV reuse mechanisms — config classes, SV-Interfaces, DPI, TLM — across module to full-chip levels for a coherent DSP ASIC.
- **Coherency Verification & Deadlock Detection Using Perspec/Portable Stimulus** (2019, DVCon US) — Moonki Jang, Jiwoong Kim and Hyerim Chung. Uses PSS and Perspec to shorten verification of cache coherency and deadlock avoidance on multi-core SoCs.
