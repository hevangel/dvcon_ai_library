# VIP Integration and Reuse

> *"The dream of verification IP is simple: a team writes a perfect UVM agent for AXI once, packages it, and every future project drops it in instead of rewriting driver code. The reality, as every DVCon audience knows, is that 'reuse' is a four-letter word. The agent was written for a 64-bit data width, your new SoC needs 512-bit. The legacy Verilog BFM has years of stability but speaks a different dialect than UVM. The third-party VIP works at IP level but its built-in shared-memory model fights your in-house one at SoC level. And the moment you go chiplet, you're integrating pre-verified dies from different vendors over UCIe and reuse means something totally new. The DVCon corpus on VIP integration is, at heart, fifteen years of engineers fighting back against the forces that make a 'reusable' component into a one-project component — and winning, sometimes, with parameterization, abstract base classes, DPI bridges, and metadata standards. So what actually makes a VIP drop in cleanly, and what breaks the moment you try? Let's dig in."*

## What it is

A **verification IP (VIP)** is the reusable UVM component — agent, driver, monitor, sequences, coverage — for one protocol interface, and **integration** is the act of stitching VIPs together into a block, subsystem, or SoC testbench. The first load-bearing concept is **parameterization**. Liu and Whiting's AMD AMBA fabric environment shows why: "a parameterized IP is configurable … the design parameters can be port protocol, port number, port name and internal logic," and these "significantly affect verification environment infrastructure including test bench connections, drivers, monitors, stimulus sequences and functional coverage." Their answer is a "highly configurable" environment with `IP_PREPROCESS`, `IP_TEST_BENCH`, and `IP_MODULE_UVC` stages that "update[s] itself automatically according to AMBA design parameters," driven by a Ruby script [Highly Configurable UVM Environment for Parameterized IP Verification, 2015]. Reuse, in other words, begins at configuration time.

The second concept is the **interface UVC versus the legacy BFM**. Wang and Bodmer observe that "UVM verification IP (VIP) usually stands for a specific standard protocol interface UVM verification component (iUVC), and could be easily reused," but that "there may be no available UVM VIP for a particular bus protocol, and an engineer has to develop t[heir own]." Their solution wraps a Verilog BFM (or RTL) as a UVM driver through abstract base classes with concrete APIs bridging BFM and design-under-verification, so "we reuse the IP level UVM sequences and customized UVM VIP on the SoC level" [Wrapping Verilog Bus Functional Model (BFM) and RTL as Drivers in Customized UVM VIP Using Abstract Classes, 2015]. The VIP is the unit of reuse; the wrapper is what makes legacy assets behave like one.

## How it's used in practice

The dominant practice is **vertical and horizontal reuse through active/passive configuration**. Liu and Whiting lay out the cleanest rule set: at IP level "driver agent, monitor and protocol checker … all work in active mode," and "when AMBA SVT VIP is reused to SoC level, driver agent is configured to work in passive mode … monitor and protocol checker work[s] in active mode." Register-model sequences "can be directly reuse[d] from IP level to SoC level" because the key is just "implement[ing] register adapters for different protocols" [Highly Configurable UVM Environment for Parameterized IP Verification, 2015]. Wang and Bodmer extend the same idea across the IP-to-SoC handoff — replacing the master IP RTL with a dummy stub, running the VIP active to drive the slave, then flipping it passive to collect coverage and check protocol timing once the real master arrives [Wrapping Verilog Bus Functional Model (BFM) and RTL as Drivers in Customized UVM VIP Using Abstract Classes, 2015]. Jain et al. push reuse up the stack with "a configurable verification environment with multiple VIPs and … connectivity to System-C drivers to reuse System-C unit tests with UVM SoC environment," letting verification "skip block level details of each VIPs/IPs and focus more on communication/interface between IPs" [Responding to TAT Improvement Challenge through Testbench Configurability and Re-use, 2014].

The next set of practices concerns **sharing models and crossing language boundaries**. Wang et al.'s shared system memory model (SMM) work is the cautionary tale: "different teams … deploy different SMM per different requirements using different languages," and the model has to live across "UVM IP stand-alone, UVM ComboWhacker, virtual FPGA, and SoC full chip," so the in-house SMM and the VIP built-in SMM have to be made to interoperate [The Art of Portable and Reusable UVM Shared System Memory Model Verification Methodology across Multiple Verification Platforms, 2015]. Crossing into Python, Wang et al. (Infineon) "create an application programming interface (API) as a wrapper around the SV-VIPs and use DPI-C to achieve transaction-level communication," adding a custom `PythonControlledRunTime` phase so a Python testbench can drive an SV-VIP and get control back — letting cocotb/pyuvm reuse the entire established SystemVerilog VIP ecosystem [Enable Reuse of SystemVerilog Verification IPs in cocotb/pyuvm, 2024]. And the structural lever for all of it is metadata: Karppa et al. weave PSS intent into an IP-XACT flow so "each of these standards can inc[orporate] the other" — IP-XACT characterizes the block, PSS specifies the verification intent, and the SoC-assembly tool generates both [Building Portable Stimulus Into Your IP-XACT Flow, 2018].

## Pitfalls and where the field is heading

The standing pitfall is that reuse has to be engineered, it doesn't happen by default. Gulati et al. put the title bluntly — "Reuse doesn't come for free" — observing that "the same level of reuse has not yet been achieved on the verification of these IPs … as on the design," and that even with "SystemVerilog and UVM … provid[ing] solid framework," real reuse on mobile audio chips required deliberate methodology work [Reuse doesn't come for free -learnings from a UVM deployment, 2016]. Shaarawy et al. hit a related wall on audio/video interfaces (HDMI, DisplayPort): "shrinking time-to-market and the increasing complexity" forced them to a "unified framework … based on UVM yet can" extend across protocols, with "customizable testing mechanisms … for different profiles" [An Efficient Verification Framework for Audio/Video Interface Protocols, 2015]. Tukel et al. show that even testbench architecture patterns matter — they apply dependency injection to keep power-aware tests reusable across low-power SoC variants [Using Dependency Injection Design Pattern in Power Aware Tests, 2021].

Where the field is heading is **chiplet-scale VIP reuse and scenario-driven integration**. Singh and Bajaj argue that UCIe "provides a modular and efficient approach to building complex systems by quickly assembling pre-verified off-the-shelf components," but that "it is important … to discuss the verification challenges and plan necessary changes to meet the verification execution and quality" — reuse is now happening at the die boundary, not just the IP boundary [Beyond Boundaries: Overcoming Chiplet Verification Challenges, 2024]. Kothari et al. take it further on multi-chiplet AI SoCs, where "integration of pre-verified IPs, sub-systems, and partially verified chiplets using multiple" interfaces forces new scalable-UCIe and boot-verification techniques on emulation [Breaking barriers in Advanced Multi-Chiplet AI SoCs using scalable UCIe and Boot Verification and Emulation techniques, 2025]. Hamid and Tibboel et al. show the complementary shift: PSS lets you "mimic the structure of the software" to verify an LTE switch before production SW exists [Use of Portable Stimulus to Verify Task Dispatching and Scheduling Functions in an LTE Switch, 2017], and an efficient requirements- and scenario-driven flow where "Metric-Driven and Constraint Random approaches should be" combined for top-level automotive verification [An efficient requirements-driven and scenariodriven verification flow, 2017]. The VIP is no longer just an agent you drop in; it is a node in a graph of pre-verified, metadata-described, multi-platform-reusable intent — and the integration problem is becoming how to assemble that graph, not how to write one more driver.
