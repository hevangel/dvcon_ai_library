# UVM Callbacks

> *Before the factory made type overrides feel clean, UVM inherited a hook mechanism from OVM and VMM: the **callback**. You define a callback class with virtual methods, register callback instances on a target component with `uvm_register_cb`, and at well-marked spots in the component's code you call back into whatever the user wired up — injecting errors, mutating transactions, overriding register behavior, plugging in a per-block reference model. It is the **observer pattern** in SystemVerilog clothing. Modern UVM code is often told to prefer the factory, but callbacks never went away: they live on in legacy VIPs, in the register layer's field hooks, and in any scoreboard that wants per-block customization without subclassing the whole component. So when do you actually reach for a callback? Let's dig in.*

## What callbacks are

A UVM callback is a small class derived from `uvm_callback` whose virtual methods are the hooks a component promises to call. The component declares a typed callback pool via `uvm_callbacks#(target_type, callback_type)`, and at runtime users call `uvm_register_cb` (macro form) or the typed `add`/`delete` methods to attach callback instances to specific component instances. When the component reaches a hook point it iterates the registered callbacks and invokes the relevant method, letting each one observe or mutate behavior without the component knowing the concrete subtype. This is straight observer pattern, and it predates the factory override as UVM's primary reuse lever [Design Patterns in Verification — see also].

In the register layer specifically, callbacks are how the model accommodates behavior the stock `uvm_reg` classes cannot express. Aynsley's "Doing Funny Stuff with the UVM Register Layer" treats register callbacks as one of three pillars — front-door sequences, the predictor, and callbacks — showing how to associate callbacks with whole registers or individual fields to define special behaviors the standard documentation does not fully spell out [Doing Funny Stuff with the UVM Register Layer, 2017]. The pattern is the same in hierarchical register schemes, where an enabler register gates banks of lower-level registers: a custom `uvm_reg_predictor` extension combined with field-level callbacks decides whether a predict call should be ignored based on the enabler's state, letting the model mirror the gating without subclassing every register [Modeling a Hierarchical Register Scheme with UVM, 2017].

## How callbacks are used in practice

The corpus shows callbacks deployed in three broad roles. First, as **error and scenario injection** in the register layer: Pai and Polineni's "Obscure face of UVM RAL" uses a callback plus the UVM extension mechanism to handle error transactions correctly, restoring the register model's mirror values that stock RAL would zero out on a `UVM_NOT_OK` response — the same generic, reusable recipe the authors recommend extending to any communication protocol [Obscure face of UVM RAL, 2017]. Second, as **sequence-level customization**: the "Keeping Your Sequences Relevant" paper treats user-overridable callbacks as one of several mechanisms sequences expose for building complex scenarios, alongside sequencer locking and grabbing, and then layers in mixins and the visitor pattern to compose behaviors with minimal code [Keeping Your Sequences Relevant, 2017].

Third, and most elaborately, as the **customization spine of a reusable scoreboard framework**. The Samsung "Elegant scoreboard eco-system" work builds a generic scoreboard whose per-block behavior is parameterized and then delegated to per-block callback classes registered with `uvm_register_cb`. The callback class exposes virtual methods like `pack_input_data`, `pack_output_data`, `pack_flag_data`, `run_ref_and_compare`, and `reset_sb`, and each image-processing sub-block supplies its own callback implementation that wires in the appropriate reference model and comparison logic [An Elegant scoreboard eco-system deploying UVM Callbacks, Parameterization, 2023]. The pattern lets one generic scoreboard serve many blocks — composition over inheritance, exactly the design-pattern argument the corpus returns to repeatedly. Even multi-methodology VIP development, dating back to the original UVM 1.0 era, leaned on callbacks alongside factory overrides and sequencer APIs to deliver reusable scenario libraries [From the Magician's Hat, 2011].

## Callbacks vs factory, and the modern verdict

The persistent question is when to use a callback versus a factory override. The short answer drawn from the corpus: use the factory when you want to replace an entire component or transaction wholesale, and use a callback when you want to inject small, optional behaviors at well-defined hook points without disturbing the rest of the component's logic. The scoreboard framework makes the trade-off concrete — a per-block callback is far lighter than subclassing the generic scoreboard for each block, and it composes cleanly when a block needs several customizations [An Elegant scoreboard eco-system deploying UVM Callbacks, Parameterization, 2023]. The same logic holds in the register layer, where field-level callbacks express per-field quirks that would be absurd to model by overriding the entire `uvm_reg` class [Doing Funny Stuff with the UVM Register Layer, 2017].

There are real costs. Callbacks are typed-pool machinery that can be hard to debug — a callback that fails to register silently does nothing, and tracing which callback instance fired requires understanding the typed `uvm_callbacks#(T,CB)` lookup. The composition story is also weaker than it looks: stacking multiple callbacks on one hook point means implicit ordering, and the visitor-pattern and mixin techniques the "Keeping Your Sequences Relevant" paper advocates are partly a reaction to those limits [Keeping Your Sequences Relevant, 2017]. Modern guidance, reflected across the corpus, is to prefer the factory for whole-object substitution and reach for callbacks where the hook is genuinely a point customization — register field quirks, scoreboard per-block logic, legacy VIP extension points. The callback is not dead; it is just no longer the first tool you reach for.
