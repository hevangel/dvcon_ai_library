# Cocotb — Python-Driven Verification

> *"UVM is powerful, but it is also the only place in modern engineering where we routinely write complex, object-oriented software in a language originally designed to describe flip-flops. Ray Salemi and Tom Fitzpatrick made that point bluntly in their 2021 DVCon paper: 'One has to wonder why we are writing this complex software using a language intended to describe RTL in an event-driven simulator.' Their answer was `pyuvm`, a Python implementation of IEEE 1800.2, and they are not alone — Infineon, AMD, Cadence, and a string of European university teams have spent the last five years pushing Python onto the simulator through **cocotb**, a coroutine-based library that lets you drive any HDL simulator from Python. The pitch is irresistible: 35 keywords, the entire scientific Python ecosystem, and no SystemVerilog to learn. The catch, as Gadde et al. measured at Infineon Dresden, is that Python-Cocotb is slower than SV-UVM, sometimes a lot, and that you give up a few language niceties like native tristate. So what is Python-driven verification actually good at, and where does it hurt? Let's dig in."*

## What it is

**Cocotb** (Coroutine-based Cosimulation TestBench) is an open-source Python library that connects a Python testbench to any HDL simulator through the simulator's VPI/VHPI/FLI interface. The testbench is written entirely in Python as a set of `async` coroutines that `yield` on simulator events; the simulator still owns time and the design. There is no UVM in vanilla cocotb — no sequencer, no factory, no phasing. To get UVM back, you reach for **pyuvm**, Salemi and Fitzpatrick's Python implementation of IEEE Spec 1800.2, which reimplements UVM features including the factory, TLM FIFOs, and `config_db` using Python language tricks [Verification Learns a New Language: -An IEEE 1800.2 Implementation, 2021].

What makes Python verification attractive is the language itself. Gadde, Kumari, and Kumar point out that Python's "35 keywords (v3.7)" and "ease of integration with other languages" lower the onboarding cost, and that open-source libraries like `cocotb-coverage` and `PyVSC` provide constrained randomization and functional coverage without a SystemVerilog license [Effective Design Verification -Constrained Random with Python and Cocotb, 2023]. Cieplucha and Pleskacz extend the same idea with a set of base classes that add coverage and constrained-random mechanisms directly on top of Cocotb, leveraging "Python language features" to make advanced object-oriented verification environments easier to set up [New Constrained Random and Metric-Driven Verification Methodology using Python, 2017].

## How it's used in practice

The most common pattern is a **layered drop-in for a small IP**. Donga, Jentzsch, and Mottok built two functionally equivalent environments for a UART core with an APB interface — one in SystemVerilog UVM, one in cocotb + pyuvm — and compared them head-to-head. Their conclusion is that pyuvm with cocotb is "particularly useful when quick iterations or runtime adjustments are needed during verification," thanks to Python's dynamic, adaptable nature [Evaluating the Usability of pyuvm with cocotb for UART Verification, 2025]. Gadde et al. did the same across three DUTs (32-bit ALU, I2C master-slave, 16-bit ADC) on three simulators (Xcelium, Questa, Verilator) and found that "coverage results obtained were similar" to SV-UVM, but run-time scales worse as transactions grow — the VPI/VHPI hop is "typically slower and less tightly integrated than the direct interaction between SystemVerilog-UVM and the simulator" [Effective Design Verification -Constrained Random with Python and Cocotb, 2023].

Two specialized use-cases stand out. First, **reusing SV VIPs from Python**: Wang, Dworzak, and Grinschgl at Infineon combine DPI-C and Python `ctypes` to call existing SystemVerilog Verification IPs from a cocotb/pyuvm testbench, so teams adopting Python do not have to abandon their accumulated SV-VIP catalog [Enable Reuse of SystemVerilog Verification IPs in cocotb/pyuvm, 2024]. Second, **power-aware simulation on open-source tools**: Alsawi, O'Reilly, and Hughes at AMD built CPAS, a Cocotb Power Aware Simulation Framework that uses a Python frontend to express UPF-style power intent, integrates Yosys for design introspection, and is the first practical way to run power-aware sim without a commercial license [CPAS: Cocotb Power Aware Simulation Framework, 2024]. Python also shows up where math is the bottleneck: Coulter offloads Ethernet Reed-Solomon FEC computation to third-party Python libraries rather than reimplementing the algorithm in SystemVerilog [Offloading Complex Mathematical Computations in SystemVerilog Testbenches, 2025], and Vejlani and Chandran use Python's signal-processing packages to do frequency-domain scoreboard checks inside a UVM testbench [Challenges in UVM + Python random verification environment for Digital Signal Processing datapath design, 2016].

## Pitfalls and where the field is heading

The biggest pitfall is **performance**. Every Python-to-simulator hop is more expensive than a native SystemVerilog call, and Gadde et al. measured run-time growing super-linearly with transaction count for Python-Cocotb versus SV-UVM. There are also language gaps: Cocotb "lacks native support for pull-up/pull-down signals and tristate logic," forcing teams to wrap the DUT in HDL just to model an I2C SDA line [Effective Design Verification -Constrained Random with Python and Cocotb, 2023]. Debug visibility is also weaker — Cocotb starts from a `TOPLEVEL` HDL entity rather than a SystemVerilog top testbench, which "hinders the debugging capabilities of the testbench signals" compared to SV-UVM. Banerjee, Singla, and Shantha at Google run into similar limits on GLS bring-up and built PEGV, a Python-empowered GLS vehicle, to compensate [Python empowered GLS Bringup Vehicle, 2023].

The trajectory is clearly toward Python as a peer of SystemVerilog, not a replacement. Gadde et al. followed up their cocotb paper with a PyUVM-focused study using PyVSC for constraints, reporting "expedited test development" but flagging the same performance tax [Towards Efficient Design Verification -Constrained Random Verification using PyUVM, 2024]. Joshi, Shettar, and Saha at Samsung show Python also entering the AI-debug stack — they pair deep-learning models and Python scripts alongside SystemVerilog UVM to assist with testbench bring-up and root-cause analysis [AI Driven Advanced Debugging in SoC Design Verification, 2026]. And Little's survey of high-level-language co-simulation reframes the choice as a trade space: cocotb, MathWorks HDL Verifier, and the custom HALA API each have distinct monetary cost, simulator support, and debugging ergonomics, and the right answer depends on which axis you can least afford to lose [A Survey of Predictor Implementation using High-Level Language Co-simulation, 2025].
