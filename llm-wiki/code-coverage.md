# Code Coverage (Line, Branch, Toggle)

> *Code coverage is the metric you get for free — flip a switch in the simulator and it counts which lines ran, which branches were taken, which signals toggled. That freeness is also its trap: it is seductively easy to chase 100% line coverage and conclude the design is verified, when all you have actually shown is that the code executed. DVCon authors have been unpacking this nuance for years, especially in low-power designs where instrumented power logic warps every line number, in HLS flows where SystemC tools can't even measure toggle coverage, and in safety-critical firmware where ISO 26262 demands MC/DC and 100% is genuinely mandatory. So what does code coverage actually measure, and where does it stop being useful? Let's dig in.*

## The core metrics and what they actually measure

**Code coverage** measures the percentage of design source code exercised by a set of tests, broken down by structural metric. The taxonomy is stable across the corpus. **Line (statement) coverage** records which executable statements were hit. **Branch coverage** records whether each conditional edge was taken — as Edelman's primer puts it, if "line 90 was never true, so no branch was taken," branch coverage fails even when line coverage passes [COVERGATE: Coverage Exposed, 2020]. **Condition/expression coverage** goes deeper: for an expression like `A & B`, condition coverage requires that each input can *control* the output and that the output goes to both 0 and 1 — if B is always zero, A is not covered regardless of how often it toggles [COVERGATE: Coverage Exposed, 2020]. **Toggle coverage** records 0->1 and 1->0 transitions on individual signals, and is the workhorse metric for synthesizable RTL because it tells you whether a register or port has been exercised in both directions.

Expression coverage deserves special attention because it is "one of the most complex and least understood types of code coverage" [Supercharge Your Verification Using Rapid Expression Coverage, 2014]. Verma and Warmke argue that expression coverage effectively builds a truth table for each boolean expression and counts how often each row matches; an expression is fully covered only when all of its individual cases have been observed [Supercharge Your Verification Using Rapid Expression Coverage, 2014]. This is the bridge to **MC/DC (Modified Condition/Decision Coverage)**, the much stricter metric mandated by DO-178B for airborne software and by ISO 26262 for automotive safety-critical code. The same paper proposes "Rapid Expression Coverage" as a scalable MC/DC-compliant methodology, treating MC/DC compliance as a question of measuring the right expression cases efficiently [Supercharge Your Verification Using Rapid Expression Coverage, 2014].

The relationship between these metrics is hierarchical. Branch subsumes line; condition subsumes branch; expression subsumes condition; MC/DC sits on top and is the hardest to fully achieve. This matters because signoff criteria differ by domain: a multimedia IP may be happy with line + branch + toggle, while an automotive firmware must hit MC/DC under a safety standard [A Novel Approach in Proving Unreachable Paths in Hardware-dependent Software, 2024].

## How code coverage is used in practice

The standard pattern is: enable code coverage in the simulator, run the regression, look at the holes, and either add tests to fill them or formally prove they are unreachable. The "prove unreachable" half is where simulation and formal cooperate. Goldberg et al.'s case study on the IP8000 crypto engine applied formal unreachability analysis first to refine coverage results — separating truly unreachable targets from those merely not-yet-hit by random simulation — and then used simulation on the remaining data-dependent blocks of the 3DES engine [Shaping Formal Traces without Constraints, 2012]. The lesson generalizes: a flat "uncovered" list is not actionable until you know which items are reachable.

A second recurring theme is that **code coverage must be measured at the right level of abstraction**. Chandrapandiyan et al.'s work on High-Level Synthesis shows that SystemC coverage tools (Gcov/Lcov, Bullseye) cannot measure toggle, FSM, or full condition coverage — and that the SystemC code coverage "reliability factor" is suspect because, for example, an array indexed once may report 100% statement coverage without exercising all indices [Achieving Faster Code Coverage Closure using High-Level Synthesis, 2021]. Their solution is a hybrid methodology that closes what it can at SystemC and finishes toggle/FSM at the RTL level before sign-off [Achieving Faster Code Coverage Closure using High-Level Synthesis, 2021].

Low-power designs introduce a particularly nasty wrinkle. When power-aware simulation instruments the RTL — adding isolation, retention, and power-state logic — every line number shifts and every coverage metric is contaminated. Bhargava et al. document the failure modes systematically: line coverage counts newly inserted power branches, branch coverage inherits the problem, FSM coverage gets spurious extra states (the famous "xx" power-off state), and toggle coverage on instrumented logic is meaningless [Unveil the Mystery of Code Coverage in Low-Power Designs, 2018]. Tu et al. make the parallel case for UPF: traditional RTL coverage is incomplete for a design with a power-management part described in UPF, so power-aware coverage of the UPF itself is needed, debugged through a "Power Domain Hierarchical Tree" [UPF Code Coverage and Corresponding Power Domain Hierarchical Tree for Debugging, 2015].

## Pitfalls, gotchas, and where the field is heading

The biggest pitfall is treating code coverage as a quality metric rather than an exercise metric. As Ellis and Jain summarize, code coverage "doesn't ensure the design works correctly, it merely shows that the code you've written was executed" [Unraveling the Complexities of Functional Coverage, 2018]. The cure is pairing it with functional coverage: code coverage catches code you forgot to exercise, functional coverage catches behaviors you forgot to model. They are complementary, not substitutes.

The second pitfall is mixing coverage from different verification engines without understanding the semantics. Eslinger et al. warn specifically that "blindly combining functional coverage from constrained-random simulations and formal analysis can fool the end-user into believing that they have made more progress... when neither is the case" [How to Avoid the Pitfalls of Mixing Formal and Simulation Coverage, 2022]. The same caution applies when mixing code coverage from power-aware and non-power-aware runs.

The third is domain-specific: microcode and processor trace. Yu et al. note that standard coverage tools have nothing to say about microcode completeness, requiring an assertion-based coverage checker that monitors PC changes around branch instructions [Metric Driven Microcode Verification, 2024]. Trace-based coverage on RISC-V (Nexus trace) is its own subfield because the coverage source is a non-intrusive trace stream, not the simulation itself [Implementing and Verifying RISC-V Nexus Trace Compliant Trace Encoder, 2025].

The trajectory is toward ML-assisted coverage analysis and earlier closure. Jayasree formulates code-coverage test selection as a machine-learning problem, predicting the optimal test subset for higher coverage in shorter simulation time [Machine Learning for Coverage Analysis in Design Verification, 2021], and Buggy et al. accelerate randomized testing by parametrizing constraints and using local RTL structure to predict which parameters will toggle hard-to-hit coverpoints [Accelerated Coverage Closure by Utilizing Local Structure in the RTL Code, 2021]. The structural metrics themselves are not changing — but the way we close them is becoming data-driven rather than elbow-grease-driven.

- **Supercharge Your Verification Using Rapid Expression Coverage as the Basis of a MC/DC-Compliant Coverage Methodology** (2014, DVCon US) — Gaurav Kumar Verma and Doug Warmke. Treats expression coverage as the foundation for scalable MC/DC-compliant signoff.
- **Achieving Faster Code Coverage Closure using High-Level Synthesis** (2021, DVCon Europe) — Surendhar Thudukuchi Chandrapandiyan, Preetham Lakshmikanthan and Ashwani Aggarwal. Hybrid SystemC+RTL methodology for closing code coverage in HLS flows.
- **Unraveling the Complexities of Functional Coverage: An advanced guide to simplify your use model** (2018, DVCon US) — Thomas Ellis and Rohit Jain. Articulates why code coverage alone is insufficient and how functional coverage complements it.
- **UPF Code Coverage and Corresponding Power Domain Hierarchical Tree for Debugging** (2015, DVCon US) — Shang-Wei Tu, Tom Lin and Archie Feng. Extends code coverage to the UPF power-intent description with a hierarchical debug tree.
- **Unveil the Mystery of Code Coverage in Low-Power Designs: Achieving Power Aware Verification Closure** (2018, DVCon US) — Madhur Bhargava, Durgesh Prasad and Pavan Rangudu. Catalogues how power-aware instrumentation corrupts line, branch, FSM, and toggle coverage.
- **Shaping Formal Traces without Constraints: A Case Study in Closing Code Coverage on a Crypto Engine Using Formal Verification** (2012, DVCon US) — David N. Goldberg, Adriana Maggiore and David J. Simpson. Uses formal unreachability analysis to refine code coverage holes before simulation.
- **COVERGATE: Coverage Exposed** (2020, DVCon US) — Rich Edelman. Accessible primer on line, branch, condition, and expression coverage with worked examples.
- **Metric Driven Microcode Verification: Navigating Microcode Coverage Complexities** (2024, DVCon US) — Seungyeon Yu, Damin Son and Tony Gladvin George. Assertion-based coverage for microcode via PC-change monitoring.
- **Efficient Coverage Optimization with Formal-Guided Testcase Generation in UVM Verification** (2025, DVCon Europe) — Yu-Shien Shen, Yean-Ru Chen and Yu-Tung Chen. FGTSO framework that integrates formal and simulation to target critical design regions.
- **A Novel Approach in Proving Unreachable Paths in Hardware-dependent Software** (2024, DVCon Europe) — Bryan Olmos, Wolfgang Kunz and Djones Lettnin. MC/DC plus formal verification for unreachable-path analysis under ISO 26262.
- **How to Avoid the Pitfalls of Mixing Formal and Simulation Coverage** (2022, DVCon US) — Mark Eslinger, Joseph V Hupcey III and Nicolae Tusinschi. Why naive merging of formal and simulation coverage misleads.
- **Implementing and Verifying RISC-V Nexus Trace Compliant Trace Encoder for High Performance Cores** (2025, DVCon India) — Sajosh Janarthanam, Rahul Behl and Sharanesh R. Non-intrusive Nexus trace infrastructure for debug, profiling, and code coverage.
- **Machine Learning for Coverage Analysis in Design Verification** (2021, DVCon Europe) — V Jayasree. ML-based test selection to maximize code coverage per unit simulation time.
- **Accelerated Coverage Closure by Utilizing Local Structure in the RTL Code** (2021, DVCon Europe) — Rhys Buggy, Gokce Sarar and Guillaume Shippee. Parametrized constraints with signal-subgraph analysis to toggle hard-to-hit coverpoints.
