# Constrained-Random Verification (CRV)

> *"Here's the central bet of modern hardware verification: write the rules once, hand them to a solver, and let the solver find corners your brain never would. That's constrained-random verification, and since roughly 2010 it has been the default way we exercise an RTL block. The promise is seductive — a few well-chosen constraints replace thousands of directed tests, and the solver will dutifully probe the back-alleys of the state space that a human would skip. The reality, as a decade of DVCon papers will tell you, is that the solver is also lazy, the constraints are a leaky abstraction, and closing the last 10% of coverage by random alone 'will have difficulty exercising all possible combinations in a timely fashion' [Optimizing Design Verification using Machine Learning Doing better than Random, 2021]. So teams spend their days steering — biasing constraints, tuning seeds, layering ML on top — to make random less random where random is being too random. Let's dig into how that loop works and where it breaks."*

## What it is

A **constrained-random testbench** declares legal combinations of stimulus as SystemVerilog `constraint` blocks, then calls `randomize()` to generate a stream of transactions that obey them. The point, as Little puts it, is to "eliminate data that does not need to be tested" — you encode what *cannot* happen, and the solver freely explores everything that *can* [A Survey of Predictor Implementation using High-Level Language Co-simulation, 2025]. A well-written testbench also decides pass/fail on its own, which makes it "well suited for automated regression testing because it does not require anyone to manually interpret complex waveforms" [A Survey of Predictor Implementation using High-Level Language Co-simulation, 2025]. The self-checking testbench plus a "golden reference" predictor (often a C/C++ model called through DPI) is what turns random noise into a coverage signal.

CRV is the engine behind coverage-driven verification. Rathi and Chandran note that at the **block level** "CRV is a standard approach … to hit multiple known and unknown scenarios, uncover corner cases and find critical design bugs," but "is not widely used … for system level" because the solution space explodes [System-Level Random Verification: How it should be done, 2019]. Kannan and Kim hit the same wall on a 5G-NR link: "the overwhelming complexity lies not only in understanding the system level requirements, but also in creating valid constraints," which they tame with a multi-staged decomposition that maps spec to SystemVerilog constraints [Creating 5G Test Scenarios, the Constrained-Random way, 2023]. CRV is powerful precisely because the solver does the combinatorics; it is expensive precisely because the combinatorics grow faster than the design.

## How it's used in practice

The first hard practice is **error injection inside CRV**. Ridgeway and Nguyen argue the ideal — "a single 'good' test and a single 'good with error injection' test" — is "rarely possible," and that teams retreat to "directed error-injection tests" that "cripple functional cross coverage potential and are not indicative of real world use cases" [Error Injection in a Subsystem Level Constrained Random UVM Testbench, 2018]. Their fix is a parameterized UVM leaf-test scheme where the good test and the error test stay independent but share the random environment, so cross coverage survives. The second hard practice is **system-level topology**: Qin et al. observe that "because the system information used in the test environment is not comprehensive enough, many scenarios still need to be tested by the directed tests" — disabling specific datapaths, mocking missing IPs — so they generate the topology info structure from a JSON precursor that one script can render into SystemVerilog/UVM, SystemC, or C++ for emulation [Graphical Topology Info Structure for Constrained Random Verification in SoC/Subsystem Tests, 2019].

The third practice is **steering**. Allara and Brognara bolt CDCRV onto SW-driven tests so that C-driven directed tests inherit random coverage [Bringing Constrained Random into SoC SW-driven Verification, 2013]. And increasingly, steering is automated: Ambalakkat and Nelson train linear regression and a neural net to "modify randomization constraints during simulation runtime … to predict useful stimulus" [Simulation Runtime Optimization of Constrained Random Verification using Machine Learning Algorithms, 2019]; Roy et al. wrap the same idea in Bayesian optimization with GBRT models for both offline and live online flows [Dynamically Optimized Test Generation Using Machine Learning, 2021]; and Huang et al.'s Smart Regression Planner treats the test's knobs themselves as a blackbox the optimizer tunes against nightly coverage [Test Parameter Tuning with Blackbox Optimization: A Simple Yet Effective Way to Improve Coverage, 2022].

## Pitfalls and where the field is heading

The standing pitfall is redundancy. Hughes et al. put it bluntly: "the redundancy inherent in constrained-random generation means that it can take many months and considerable manual effort to achieve 100% functional coverage for large and complex blocks" [Novelty-Driven Verification: Using Machine Learning to Identify Novel Stimuli and Close Coverage, 2021]. Blackmore et al. attack exactly this with unsupervised anomaly detection — surfacing "unusual or novel behaviour" so the solver stops re-hitting already-covered bins [Novelty-Driven Verification: Using Machine Learning to Identify Novel Stimuli and Close Coverage, 2021]. A second pitfall is stimulus portability: Andrews and Hristov note that "constrained random stimulus is mostly confined to SystemVerilog testbenches," that SystemC's SCV "has not been widely adopted," and that maintaining "independent stimulus models" across sim, emulation, and post-silicon is the real tax [Portable Stimulus Models for C/SystemC, UVM and Emulation, 2015] — the motivation behind PSS.

The field is clearly moving from "write constraints, pray" toward "write constraints, close the loop." Le and Andrews show graph-based stimulus models catching bugs "one or more orders of magnitude" faster than plain CRV [Efficient Bug-Hunting Techniques Using Graph-Based Stimulus Models, 2016]; Gopalkrishna et al. argue PSS is the only sane way to get constrained-random "at system level, [where] embedded software … result[s] in use of languages and platforms with limited constrained-random capabilities" [DVCon India 2023 TITLE OF PAPER Tackling the verification complexities of a processor subsystem through Portable stimulus AUTHOR 1 Name: Vivek Gopalkrishna Organization: Analog Devices, 2023]; and the ML-steering papers above are converging on a closed loop where coverage feedback rewrites the constraints for you. CRV isn't going away — it's being wrapped in a feedback controller.
