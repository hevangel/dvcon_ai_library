# ML for Coverage Closure

> *Constrained-random verification promises that, given enough time, the solver will eventually exercise every legal combination. On a modern SoC "enough time" is geological, so the dream quietly dies somewhere around 85% coverage and a team of engineers takes over from there. The DVCon corpus from 2021 onward describes a quiet revolution: instead of humans steering the constraints, machine learning does. The techniques range from the modest (cluster last night's stimuli, pick the cluster that moved coverage most) to the genuinely science-fictional (a reinforcement-learning agent that trains against a model of the design, then drops into the real DUV and drives stimulus straight at the holes). So how do you actually use ML to close coverage, and where does it stop working? Let's dig in.*

## The core idea: treat coverage closure as a learning problem

The shared insight across the corpus is that the coverage-closure loop — pick stimulus, run, observe coverage, repeat — is a feedback loop, and feedback loops are exactly what machine learning is good at. The differences between papers are mostly in *what* is being learned and *how* the feedback is structured.

The simplest framing is **test/seed selection**. Jayasree formulates the problem as: given an initial coverage database of basic test cases, use ML to predict which subset maximizes coverage percentage per unit simulation time, and analyze feature impact on both coverage and runtime [Machine Learning for Coverage Analysis in Design Verification, 2021]. This is essentially classical regression test selection, lifted by ML feature analysis. Shah et al.'s AFCML goes a step further: classify tests into groups by their randomized variables, cluster stimuli within each group using K-means++ on coverage-related features, then train a model to predict whether each candidate stimulus will hit its target — reporting 49% improvement in transaction efficiency within a UVM framework [AFCML, 2025].

The more ambitious framing is **constraint/parameter optimization**. Huang et al. note that "constrained random verification in industrial settings involves parameterized tests" whose parameters "are typically set when the test is first written, and seldomly varied later," and formulate test-parameter configuration as a blackbox optimization problem. Their Smart Regression Planner (SRP) uses Bayesian optimization with nightly-regression coverage as feedback to automatically reconfigure tunable parameters toward higher coverage [Test Parameter Tuning with Blackbox Optimization, 2022]. Roy et al. push the same idea into live online flows: Bayesian optimization with gradient-boosted regression trees dynamically rewrites randomization constraints during the run, in both batched offline and live online modes [Dynamically Optimized Test Generation Using Machine Learning, 2021]. The shared claim is that the parameter space is too high-dimensional for a human to reason about, so the human's job is to expose the knobs and let an optimizer search them.

The most aggressive framing is **reinforcement learning over the coverage signal itself**. Pallela et al.'s 3D NAND Flash work trains an RL agent with several deep neural networks coupled with a gradient-ascent approach to determine stimulus settings that maximize unit coverage bins; the agent trains against a model of the DUV in iterations and is then deployed on the real design to generate the best stimulus [Stimulus Diversification and Coverage Closure of 3D NAND Flash, 2025]. The feedback loop is explicit: "from the coverage database to the RL agent and from the RL agent to stimulus generation." This is closed-loop coverage closure as a learned policy, not just a one-shot predictor.

## How ML-assisted closure is used in practice

The production patterns cluster into three families, mirroring the spectrum above. First, **regression-level ML** that decides what to run next. Jayasree's test selection, AFCML's stimulus prioritization, and Baek et al.'s SDC verification work all sit here. Baek et al. combine heatmap visualization to find verification gaps with ML optimization of the regression test suite, achieving a 63% reduction in regression testing time while pushing SDC coverage to 100% for timing exception paths [Enhancing SDC Verification in SoCs, 2025]. Jain and Goyal's unified methodology generalizes this to multi-platform flows, applying AI/ML across simulation, formal, and emulation to identify over-constraints and provide root-cause analysis for SystemVerilog CRV testbenches [Unified Coverage Methodology, 2024].

Second, **stimulus-generation ML** that decides what each individual test should look like. Kumar et al. describe "AI-accelerating coverage closure using intelligent stimulus generation" for SoC bus matrices that can carry close to a million coverage bins — a regime where brute force constrained random has no chance [AI-accelerating coverage closure, 2025]. Hughes et al.'s foundational "Doing better than Random" argues that purely random approaches "will have difficulty in exercising all possible combinations in a timely fashion" and that constrained-random "often relies on extensive expertise to guide the DV environment"; their ML approach aims to replace that expertise with learned steering [Optimizing Design Verification using Machine Learning, 2021]. Gogri et al. provide a systematic comparative study of ML-guided generation strategies, noting that prior work typically restricted itself to one or two approaches and that the recent progress in ML had not yet been absorbed by the field [Machine Learning-Guided Stimulus Generation for Functional Verification, 2020].

Third, **predictive coverage modeling** that learns the mapping from stimulus to coverage and uses it to fill specific holes. Kim et al.'s work on reaching 100% functional coverage explicitly defines the closure challenge as cross coverage holes, uses a Python-based coverage agent to predict the configuration most likely to fill the next hole, and runs it — iterating until closure, with explicit strategies to handle the persistent case where "predictions continue to fail and the coverage rate either barely increases or doesn't increase at all" [Reaching 100% Functional Coverage, 2025, cited across the corpus]. Jain and Jain extend the predictive idea to failure-mode prediction more broadly, using Decision Trees to predict input-stimulus outcomes and address coverage gaps while also modeling timing, power, and logic failure modes [Leveraging AI/ML Models for Enhanced VLSI Design and Verification, 2024].

## Pitfalls, gotchas, and where the field is heading

The first and most predictable pitfall is **data quality**. Every ML approach in the corpus depends on a clean, merged coverage database as its training signal; garbage in, garbage out applies with full force. This is why so many of the ML papers are downstream of — and quietly dependent on — the coverage data management work (UCIS, MapReduce merge, unified databases). A poorly merged or incompletely collected coverage database trains a confidently wrong model.

The second pitfall is **prediction failure on the long tail**. Kim et al. are unusually honest about this: even with model-accuracy strategies, there are persistent holes where "predictions continue to fail and the coverage rate either barely increases or doesn't increase at all, even with the number of regression tests" [Reaching 100% Functional Coverage, 2025]. The lesson is that ML is not magic — the tail is where ML's value is highest but also where it most often stalls, and hybrid flows (ML plus directed tests, ML plus formal unreachability analysis) are usually what finally closes the last percent.

The third pitfall is **over-trusting the model**. A model trained on past regressions encodes the constraints of those regressions; if the testbench has an over-constraint, the model will faithfully learn to never hit the impossible bin and report progress on everything else. Unified methodologies that explicitly use ML to "identify over-constraints affecting coverage closure" are responding to exactly this failure mode [Unified Coverage Methodology, 2024].

The trajectory is clear from the recency of the papers. The 2024-2025 wave treats ML not as an experimental add-on but as the default closure engine, and the 2026 papers on agentic regression fold coverage closure into a larger autonomous loop where the ML agent not only predicts but also runs, observes, and re-plans. The boundary between "ML for coverage" and "ML for regression" is dissolving — both are becoming instances of the same closed-loop optimization. What stays constant is the dependence on a trustworthy coverage database as the loss function; if the signal is wrong, no amount of model capacity saves you.
