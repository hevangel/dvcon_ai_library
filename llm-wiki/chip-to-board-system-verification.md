# Chip-to-Board System Verification

> *"Here is a sentence that has ruined many a launch: 'The chip passed, the board passed, the system doesn't work.' Verification engineers know the chip down to the bit. PCB designers know the board down to the via. Nobody owns the seam — the place where the chip's I/O meets the package, the package meets the PCB trace, the PCB trace meets the connector, and the connector meets another chip's I/O. Bhatnagar and Fricano describe the seam bluntly: tests get rewritten at every level because 'the test stimulus is often re-written to work in the top level UVM environment or in C to run on the processor at the chip level,' and then 'the effort to create tests verifying the startup/configuration and basic mode operation of blocks is repeated for actual silicon testing as new tests are required for the test platform or to run on an evaluation board' [Product Life Cycle of an Interconnect Bus, 2019].

> The cost of that rewrite is not just hours; it is bugs. Each translation between UVM, C, evaluation-board test, and ATE pattern is a chance to introduce a mismatch that looks like a defect in somebody else's territory. And the system itself is now bigger than a single die — chiplets, multi-die packages, signal-integrity budgets that span two boards. Singh and Bajaj note that the Universal Chiplet Interconnect Express 'offers high-bandwidth, low-latency, power-efficient, and cost-effective on-package connectivity' and is a 'paradigm shift in semiconductor design' [Beyond Boundaries: Overcoming Chiplet Verification Challenges, 2024].

> So what does verification look like when the unit of integration is no longer a chip but a system-on-board, or a system-in-package? That is the question this page answers — and the answer turns out to be PSS for portable stimulus, scoreboards that travel from IP to SoC to board, formal for address-map correctness, and LLMs for measuring whether you actually covered anything. Let's trace the seam."*

## What it is

Chip-to-board system verification is the work of proving that **the chip, in its package, on its board, in its system**, behaves correctly. It is the level above SoC integration: where the DUT is not a single RTL block but a PCB populated with chips, connectors, power supplies, and the analog reality of signal integrity, power delivery, and thermal coupling. The verification problem has three flavors. The first is **system-level functional verification**: the chip boots the OS, the OS drives the network stack, the network stack moves packets across the board. The second is **chiplet / multi-die verification**: die-to-die connectivity, UCIe PHY behavior, the bundling of multiple chiplets into a single package. The third is **post-silicon board verification**: bring-up boards, ATE, the lab work that catches what simulation could not.

Underneath all three is the same pain: **test content does not travel**. At the IP level you write UVM sequences; at the SoC level you write C tests for the processor; at the board level you write Python or lab-equipment scripts; on ATE you write vector patterns. Each rewrite breaks traceability and introduces 'frequent false bugs' [Product Life Cycle of an Interconnect Bus, 2019]. The whole chip-to-board sub-discipline is, in a sense, the search for a portable abstraction that survives the level changes.

A second theme is **scoreboard reuse**. Once you have a scoreboard that can check transactions at the IP level, the same logic should be able to check transactions at the system level. Edelman, Ardeishar, and Sarup make this case with 'multi-level transaction level monitoring, scoreboarding and coverage collection' that uses 'intelligent monitors' to make high-level transactions visible to lower-level components [Panning for Gold in RTL Using Transactions, 2011].

## How it is used in practice

**Portable Stimulus (PSS)** is the dominant medium for making test content travel. Bhatnagar and Fricano trace the life cycle of an interconnect bus fabric from SystemC performance modeling through UVM-based IP verification, C-based SoC tests, post-silicon evaluation-board tests, and ATE patterns — all sourced from a generic PSS-based traffic generator that provides 'horizontal re-use (simulation, emulation, board level, tester etc.)' as well as vertical reuse from IP to SoC [Product Life Cycle of an Interconnect Bus, 2019]. Fitzpatrick and Ballance add a key insight about results checking: PSS is declarative while results checking is platform-specific, so 'different levels of verification and validation environments have different needs when it comes to results checking' — block-level wants detailed scoreboards, SoC-level wants per-operation pass/fail [Results Checking Strategies with Portable Stimulus, 2019].

For **chiplet / multi-die systems**, the new sub-discipline is UCIe verification. Singh and Bajaj list three challenges: efficient performance analysis and 'D2D scoreboards to ensure system-level transaction integrity is verified'; automotive-grade UCIe PHY verification where 'the margin of error is negligible' and SNR/BER must be proven; and the broader execution-quality question of how to verify a multi-die assembly as a single system [Beyond Boundaries: Overcoming Chiplet Verification Challenges, 2024]. The system-level portable tests developed there 'can be easily run on multiple engines and topologies, promoting reuse.'

For **subsystem-level verification** that has to cross the chip-to-board seam, two patterns recur. Ahammad and Murthy describe a scalable testbench for video codec and computer-vision scenarios across categories 'like GPIO, various categories of IRQs, a verity of automotive requirements like FUSA, a bunch of AXI related functionalities' [Scalable Test bench Architecture and Methodology for Faster Codec and Computer Vision Scenario Verification, 2022]. Vurukutla et al. present a scoreboard ecosystem for image-sensor multimedia designs that uses C reference models and is reusable across IP, sub-system, and SoC environments, with emulation as a parallel path 'to meet the timelines' once simulation times scale into days [An Elegant scoreboard eco-system deploying UVM Callbacks, 2023]. The pattern is the same: build the scoreboard once, run it everywhere.

## Pitfalls and where the field is heading

The biggest pitfall is **measuring the wrong coverage**. Hyun, Lee, and Choi point out that conventional coverage schemes are 'typically constrained to post-simulation measurement,' which means you find out what you covered only after the run is over — useless for steering. Their Common Task Coverage (CTC) methodology defines coverage bins from design metadata and uses an LLM to assist, 'enabling early-stage coverage application' with a Vue.js dashboard showing heat maps [An Early Stage Coverage Measurement Methodology For Common Features Of System-On-Chip Verification, 2025]. Without that kind of measurement, system-level coverage tends to be aspirational.

The second pitfall is **losing scoreboard fidelity at scale**. Dančak shows that even for AMS, a UVM SystemVerilog testbench can 'use standard UVM components as-is by encapsulating all the analog-specific contents' so that the chip-to-board AMS work does not fork a separate methodology [A UVM SystemVerilog Testbench for Analog/Mixed-Signal Verification, 2022]. K N and Gandhi attack the multi-protocol SerDes case directly: building TLM reference models for PCIe, USB, and DP in a single PHY is 'increasingly challenging,' and their customizable real-time post-processing lets users see intermediate data-integrity results during the run rather than waiting for end-of-test [Breaking the Wait, 2026].

The third pitfall is **address-map and NoC correctness at system level**. Soosai et al. describe a 'scalable formal verification framework for NoC system address map configurations' because 'each SAM configuration represents a unique operational scenario' — and a single misrouted address at the board level can silently corrupt packets across the system [Scalable Formal Verification Framework for NoC System Address Map Configurations, 2026]. This is a clear case where the chip works, the board works, and the system silently does not.

The field is heading toward three convergences. First, **LLM-assisted coverage** that measures system-level verification intent early, not just after the run [An Early Stage Coverage Measurement Methodology, 2025]. Second, **chiplet-aware unified methodologies** that treat the multi-die package as the new board and verify D2D, PHY, and system-level transactions in one portable flow [Beyond Boundaries, 2024]. Third, **flexible, OOP-grounded testbench architectures** like Sanz Carretero et al.'s, which let 'a single UVM testbench adapt and support all levels of integration (unit-level, top-level, system level, encrypted simulation model level, etc.)' so that last-minute DUT architectural changes do not break the verification tree [Testbench flexiblity as a foundation for success, 2021]. The chip-to-board seam is being erased one portable abstraction at a time.
