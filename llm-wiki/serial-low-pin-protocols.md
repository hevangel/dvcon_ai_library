# Serial Low-Pin-Count Protocols — I2C, SPI, UART, CAN-FD

> *"They are the smallest protocols in your SoC and the easiest to dismiss. I2C is two wires, SPI is four, UART is three, and the whole lot fit on a single page of the datasheet. But here is the dirty secret of every tapeout post-mortem: most of the bugs that escaped pre-silicon and shipped in real silicon came from these little interfaces. Clock stretching on I2C, multi-master contention on SPI, an octal-SPI DDR NAND flash that suddenly wants 8 bits at double data rate with a brand-new data strobe pin — these are the corners where constrained-random stimulus runs out of gas. Winbond and Cadence walked through exactly that Octal DDR problem at DVCon Japan 2024 because the automotive industry demanded it. At the other end of the spectrum, Mihir Donga and his colleagues at OTH Regensburg asked the heretical 2025 question: do we even need SystemVerilog to verify a UART anymore, or can pyuvm with cocotb do it just as well? So let's dig in to why these tiny protocols punch so far above their pin count."*

## What it is

A **serial low-pin-count protocol** moves data one bit at a time (or a few bits in parallel) over a handful of wires, instead of an entire word over a wide parallel bus. **SPI** is full-duplex master/slave with a chip-select per slave — fundamentally point-to-point once a slave is selected [Analysis of TLM-2.0 and it's Applicability to Non Memory Mapped Interfaces, 2016]. **I2C** is a multi-master, multi-drop two-wire bus with a 7-bit (or 10-bit) address byte. **UART/RS-232/RS-485** is a serial byte stream with start, stop, and optional parity bits — and, crucially, it is not memory-mapped, so the standard TLM-2.0 generic payload fields like `address`, `byte_enable`, and `dmi` "don't make sense" for it [Analysis of TLM-2.0 and it's Applicability to Non Memory Mapped Interfaces, 2016]. **CAN and CAN-FD** add differential signaling, bit stuffing, and arbitration for automotive networks.

The unifying feature is that the **bus is not memory-mapped**, which immediately breaks the assumptions of UVM RAL and TLM-2.0. The GreenSocs team showed that TLM-2.0's generic payload only really fits memory-mapped bus protocols; for SPI, UART, I2C, and CAN you need either a custom extension to the standard (their `GreenSerialSocket` and `GreenPayload` for UART) or an explicit TLM **transactor** that abstracts the low-level pin wiggling up to OSI layer 3 [Analysis of TLM-2.0 and it's Applicability to Non Memory Mapped Interfaces, 2016]. The same gap exists at the UVM layer: Darko Tomušilović noted that standard UVM RAL cannot describe SPI-style bit-resolution access or complex buffer access — you have to extend it [Extending UVM Register Abstraction Layer for Verification of Register Access via Serial Bus Interface, 2016].

## How it's used in practice

In production, the prevailing pattern is to wrap a serial controller in a **UVM agent** that translates the protocol's quirks into normal sequence items, then layer RAL register access on top. Shariff, Sekar, and Reddy demonstrated exactly this pattern using Cadence VIP for both PCIe and SPI: an adapter sequence sits above the RAL model, and only minor RAL model modifications were required to achieve finer-granularity register sequences over a serial link [UVM Sequence Layering for Register Sequences, 2023]. Tomušilović's SPI extension adds the missing bit-resolution and buffer access while staying **passive** — the monitor never injects traffic, which is critical because it preserves testbench reusability [Extending UVM Register Abstraction Layer for Verification of Register Access via Serial Bus Interface, 2016].

The protocol itself keeps mutating, which is what makes it interesting. The automotive industry pushed serial NAND flash from a 1-bit slow SPI interface to 2-bit, then 4-bit, and now **Octal SPI with double data rate** and a brand-new Data Strobe (DS) output pin that qualifies read data at maximum DDR frequencies [New Serial NAND Flash Octal Double Data Rate Feature Its Verification Challenges and Solution for the Automotive Application Space, 2024]. At the same time, verification methodology is being reinvented: Donga, Jentzsch, and Mottok built two functionally equivalent verification environments for the same UART-with-APB IP — one in classic SystemVerilog UVM, one in **pyuvm with cocotb** — and compared them head-to-head, finding the Python path viable for lightweight or academic settings even if SV-UVM remains the industry standard [Evaluating the Usability of pyuvm with cocotb for UART Verification, 2025]. And for safety-critical serial peripherals, the new hybrid pattern is to run an RTL emulator of the SPI controller against a virtualized CPU through a transaction-level interface, enabling **fault injection campaigns** (stuck-at-zero and stuck-at-one on critical control and data signals) before silicon exists [Pre-Silicon Verification of Software Safety Mechanisms A Hybrid Approach with SPI and NVDLA Case Studies, 2025].

## Pitfalls and where the field is heading

The biggest pitfall is treating these protocols as trivial. Continental's experience co-simulating SPI-enabled ASICs with their software drivers for fault injection is a reminder that hardware and software verification historically happens in isolation, and that bugs that cannot be fixed in software after fabrication can cost a re-spin [Hardware/Software Co-Simulation of SPI enabled ASICs and Software Drivers for Fault Injection and Regression Tests, 2014]. The system-level cost of an underspecified serial controller is real: deadlocks in the FIFO/VC dependency graph between a serial slave and the rest of the SoC can escape formal verification at unit level and only manifest as elusive system hangs [Mechanism to Generate FIFO VC Dependency Graph and Its Application to System Level Deadlock Verification, 2021].

Where is the field heading? Three directions are visible in the corpus. First, the **broadening of the serial interface itself** — Octal DDR SPI is the leading edge, but the same pressures (bandwidth at manageable clock speeds) are driving everything from CXL over PCIe to multi-gigabit SerDes. Second, the **Pyhonization of verification** — pyuvm with cocotb is no longer a curiosity, and it competes directly with SV-UVM for IPs as mainstream as a UART. Third, the rise of **hybrid RTL-plus-virtualized-CPU** environments that let safety-critical serial IPs be exercised by real software stacks and real fault lists well before silicon. Tiny protocols, huge aggregate risk — and the DVCon community keeps coming back to them because the cost of getting one wrong is measured in respins, not patch releases.

## Grounded in these DVCon papers

- **New Serial NAND Flash Octal Double Data Rate Feature Its Verification Challenges and Solution for the Automotive Application Space** (2024, DVCon Japan) — Vishal Gulati, Anil Gupta and Sharvil Tushar Jani. Walks through the verification challenges of moving serial NAND flash to 8-bit Octal SPI at double data rate with a new Data Strobe pin for automotive use.
- **Analysis of TLM-2.0 and it's Applicability to Non Memory Mapped Interfaces** (2016, DVCon Europe) — Guillaume Delbergue, Mark Burton and and Bertrand Le Gal and Christophe Jego. Argues TLM-2.0's generic payload only fits memory-mapped buses, and proposes extensions and transactors for SPI, UART, I2C, CAN, RS-232, RS-485.
- **Evaluating the Usability of pyuvm with cocotb for UART Verification** (2025, DVCon Europe) — Mihir Ashvinbhai Donga, Eyck Jentzsch and Prof. Dr. Juergen Mottok. Side-by-side comparison of a SystemVerilog UVM testbench versus a pyuvm-with-cocotb testbench for an APB-UART IP.
- **Pre-Silicon Verification of Software Safety Mechanisms A Hybrid Approach with SPI and NVDLA Case Studies** (2025, DVCon Europe) — Moustafa Nabil, Ahmed Saied and Ahmed Makram. Couples an RTL SPI controller emulator with a virtualized CPU through a TLM interface to run pre-silicon fault injection campaigns.
- **UVM Sequence Layering for Register Sequences** (2023, DVCon India) — Muneeb Ulla Shariff, Sangeetha Sekar and Ravi Reddy. Demonstrates layered adapter sequences over RAL for PCIe and SPI to reach finer register-access granularity.
- **Extending UVM Register Abstraction Layer for Verification of Register Access via Serial Bus Interface** (2016, DVCon Europe) — Darko Tomušilović. Extends UVM RAL with bit-resolution access and complex buffer access for SPI-style serial register interfaces, in a passive, reusable way.
- **Hardware/Software Co-Simulation of SPI enabled ASICs and Software Drivers for Fault Injection and Regression Tests** (2014, DVCon Europe) — Elias Kyrlies-Chrysoulidis, Andreas Plange and Thomas Gürtler. Continental's co-simulation flow for SPI ASICs and their drivers, oriented toward safety-critical automotive fault injection.
- **Mechanism to Generate FIFO VC Dependency Graph and Its Application to System Level Deadlock Verification** (2021, DVCon US) — Debarshi Chatterjee, Chad Parsons and Siddhanth Dhodhi. Nvidia method for catching elusive system-level deadlocks, including those involving peripheral FIFO/VC dependencies.
