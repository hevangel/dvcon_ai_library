# Agile Hardware Development and Continuous Verification

> *"Hardware people have been quietly jealous of software for about twenty years. Software teams ship daily, regress on every commit, and treat their backlog as a living document; hardware teams hand off RTL in milestones measured in months, run a nightly regression, and pray the spec doesn't change. The Agile Manifesto landed in 2001 and reshaped software entirely — iterative increments, continuous integration, behavior-driven development — but for years it felt transplanted only as ceremony. That changed when engineers noticed two things. First, the artifact that kills projects isn't bad RTL, it's 'incorrect or misunderstood' specifications — William L. Moore cites that over 40% of ASIC bugs trace back to specification gaps. Second, Jenkins and CI servers were already good enough to run regressions before you finish your morning coffee, as Thomas Ellis put it in 2017. So agile verification isn't two-week tapeouts; it's the mindset — living specs, continuous regressions, verif embedded in the dev loop, and HW/SW co-verification that runs continuously rather than at 'major milestones.' Let's unpack what that actually looks like on a real chip."

## What it is

**Agile verification** imports the software-agile playbook — iterative increments, continuous integration, behavior-driven development — and rewrites it for hardware flows. The defining move is treating the **specification as a living, executable artifact** rather than a frozen Word document. Moore's *Bathtub* library writes Gherkin scenarios (the `Given`/`When`/`Then` notation from Cucumber) directly in SystemVerilog, mapping each behavior to a UVM virtual sequence and executing it against the DUT. The result is 'true living documentation — executable specifications that are always accurate, accessible, and up-to-date' [Gherkin Implementation in SystemVerilog Brings Agile Behavior-Driven Development to UVM, 2024]. The whole point is that when the behavior changes, the spec changes with it, and the spec *is* the test.

The second pillar is **iterative increments with quantitative measurement**. Rangan, Kantamneni and Dalal's A3V flow contrasts the rigid 'requirements-driven flow' (RDF) — with its 'fixed priorities on project tasks which may hinder progress when struck with complex bugs' — against agile's task division into 'small phases where task execution is sequential in nature' with 'continuous value addition' [Agile Approaches to ASIC Verification (A3V), 2022]. They apply A3V to a memory-IP verification use case (clock frequency variation, RAM/ROM selection, SCAN/MARCH/READONLY algorithms, sequential vs concurrent access) and frame the difference as: RDF progress is 'non-iterative and non-linear, concluded only at the final stage,' while agile delivers 'iterative and incremental progress at every stage ensures continuous assessment of project status.'

## How it's used in practice

Continuous integration is the engine that makes any of this real. Ellis, writing first at DVCon Europe 2016 and again at DVCon US 2017, makes the case plainly: 'Continuous Integration is a practice which has been widely, and successfully used in the software realm for many years,' and deploying Jenkins 'not only provides a way to automate the running of jobs, and collection of results' but yields 'a cleaner repository, with less integration headaches' [Increased Regression Efficiency with Jenkins Continuous Integration, 2016; Increased Regression Efficiency with Jenkins Continuous Integration Before You Finish Your Morning Coffee, 2017]. The hardware retuning is mostly about test runtime — sim regressions are slow, so the CI loop has to be intelligent about what to run.

That intelligence has converged on **ML-driven regression selection** inside the CI loop. Singla, Jindal and Sangaiyah's ML-based regression accelerator 'figures out the fragile tests which break frequently and prioritizes running those over stable tests,' reducing the 'tests to run' set significantly without compromising regression quality [ML based regression accelerator, 2024]. Girdhar and Badam's DeltaCov takes the same instinct to stimulus quality: during early project churn, 'any silent degradation in the stimulus generation can cause verification holes,' so DeltaCov monitors deltas continuously rather than waiting for nightly coverage analysis [DeltaCov: Automated Stimulus Quality Monitoring System, 2021]. The pattern is the same — make the feedback loop tighter than nightly.

The third pattern is **continuous HW/SW co-verification**. Hoffmann, Nair, Ni and Grischgl argue that 'integration between HW and SW leads to disruptions if both flows run in parallel without continuous interaction,' and that 'many organizations lack the tooling to trigger an immediate test to validate a firmware on an up-to-date hardware or hardware model' [HW-SW-Coverification as part of CI/CD, 2023]. Their CI/CD pipeline collapses the design/verif/firmware handoffs into a continuous stream, mirroring Schirrmeister, Fabbre and Hinson's 'pre-silicon continuum for concurrent SoC and software development and verification for safety and security critical systems' built on a certified RTOS [Safety and Security Aware Pre-silicon Concurrent Software Development, 2020].

## Pitfalls and where the field is heading

The honest pitfall is that **reuse doesn't come for free**, and agile makes the reuse tax visible. Gulati, Venkataramanan and Ahammad, reflecting on a UVM deployment for mobile audio chips, observe that while 'SystemVerilog and UVM has provided solid framework to build test benches,' the 'same level of reuse has not yet been achieved on the verification of these IPs' as on the RTL side — the fast turn-around times of consumer chips expose the gap [Reuse doesn't come for free -learnings from a UVM deployment, 2016]. Agile cadence also collides with verification depth: deadlock and livelock bugs, the hardest class, are 'extremely difficult to detect with RTL simulation' and need formal to 'differentiate between situations where your system is truly locked up vs a case where the right stimulus hasn't come along' [Using Formal to Prevent Deadlocks, 2020; Deadlock Verification For Dummies, 2020]. CI pipelines that only run simulation will systematically miss these.

The field is heading toward **agile practices applied beyond RTL**. Khondkar's UPF dynamic-object probing lets engineers 'continuously probe ON, OFF status of power domains' and 'populate cover-bins with coverage data from unconventional power state transitions' — bringing agile coverage feedback to low-power verification [Probing UPF Dynamic Objects, 2020]. Singh's work on gate-level simulation shows the same CI discipline being applied to GLS at 10nm-28nm, where 'longer run times, high memory requirements, and a growing set of GLS applications' force continuous optimization [Addressing Renewed Gate Level Simulation Needs for 10nm-28nm and Below, 2016]. Even pipeline-design strategy (Grubor, 2018) and multi-die SoC data-driven design (Roy and Kapila on Altera Agilex, 2024) adopt the iterative, increment-driven cadence. The takeaway is simple: two-week tapeouts are a myth, but the agile mindset — living specs, tight feedback loops, embedded verif — is now how chips actually get shipped.
