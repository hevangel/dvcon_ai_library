# RISC-V Processor Verification

> *RISC-V walks in and breaks every assumption you had about processor verification. With a proprietary ISA, you got one golden model from the vendor and a compliance suite they blessed. With RISC-V you have a hundred cores from a dozen sources, a spec that intentionally leaves room for custom extensions, and a `README` that may or may not match the RTL. The flexibility that makes the ISA beautiful is exactly what makes it a verification nightmare — every team rolls their own pipeline, their own CSRs, their own exceptions, and you have to prove each one matches the unprivileged spec. The DVCon corpus on RISC-V is essentially a decade of teams re-inventing how to verify a CPU in public, and it has produced an unusually rich playbook. Let's dig in.*

## What makes RISC-V verification different

The core challenge is **combinatorial diversity**. There are more than a hundred RISC-V implementations, ranging from non-pipelined microcontrollers to superscalar out-of-order cores, each configurable across extensions, pipeline depths, cache organizations, and CSR sets [A Comprehensive Verification Platform for RISC-V based Processors, 2020]. Verifying any one of them therefore has two halves: prove the implementation is **compliant** with the ISA, and prove it is **correct** in the parts the ISA leaves open. The open ecosystem has responded with shared collateral — most notably the OpenHW Group's **CORE-V-VERIF** UVM environment, which has evolved through multiple processor projects into a robust, reusable testbench with increasingly mature reference-model integration [The Evolution of RISC-V Processor Verification, 2023].

The compliance half leans on public test suites (`riscv-tests`, `riscv-compliance`, `riscv-torture`) plus random instruction generators like **RISCV-DV**, while the correctness half almost always comes down to a **step-and-compare** flow against an instruction set simulator (ISS) reference model [A Comprehensive Verification Platform for RISC-V based Processors, 2020]. The community converged on the **RVVI-API** — a standard set of functions that a processor verification IP and its testbench must implement — so that reference models, coverage collectors, and checkers can interoperate regardless of which core is under test [The Evolution of RISC-V Processor Verification, 2023]. Compliance testing is the "positive" axis; the equally important "negative" axis covers exceptions, illegal instructions, and fault injection, where the open **RISCV-DV** generator has been extended with configurable exception scenarios [An Extension to RISC-V Test Generator, 2024].

## How teams build the flow in practice

The dominant architecture is **UVM around a reference ISS**, often with emulation in the back pocket for full-system workloads. Codasip and Mentor's early collaboration paired UVM with a **golden predictor model** and a configuration layer to tame the variability of RISC-V cores, mixing simulation and emulation to cover both compliance and corner-case behavior [UVM-based Verification of a RISC-V Processor Core, 2018]. NVIDIA Networking took the same approach for an RV64IMACBNSU core, encapsulating a reference model in SystemVerilog and C and running a Specman-based step-and-compare flow with co-debug [RISC-V Processor Verification: Case Study, 2021]. Where performance matters, teams are squeezing the generators: an Embedded UVM (eUVM) port of RISCV-DV using multicore parallelism now produces over a million constrained-random instructions per second, a 100x speedup over the original SystemVerilog implementation [Crafting a Million Instructions/Sec RISCV-DV, 2024].

Block-level work gets creative because the load/store and MMU blocks are the hardest microarchitectural units in a high-performance CPU. One team wrapped the open-source **Whisper** ISS with RISC-V assembly and a UVM testbench so RTL designers can describe a scenario and have it translated into block-level stimulus, gaining granularity that a full-core flow cannot reach [Unleashing the Power of Whisper, 2024]. For performance exploration rather than correctness, a hybrid out-of-order model switches at runtime between a fast functional ISS and a detailed performance model, enabling microarchitectural what-if analysis [Design and development of a Hybrid Out-of-Order RISC-V Processor Model, 2025]. And programmable analysis DSLs like **WAL** let teams benchmark and compare open-source and commercial cores across hundreds of configurations on a level playing field [Programmable Analysis of RISC-V Processor Simulations using WAL, 2022].

## Hard corners: debug, exceptions, and stress beyond compliance

ISA compliance is necessary but nowhere near sufficient. Two of the hardest non-compliance areas are **debug unit verification** and **stress testing**. NXP's debug-unit work shows why: the debug module must be verified against a multitude of core configurations, mixed pipeline states, and external stimuli — interrupts, debug exceptions, bus faults — all while random debug requests land mid-simulation, and random instruction streams run inside debug sessions with varying control settings [Random Testcase Generation and Verification of Debug Unit for a RISC-V Processor Core, 2023][Verification Methodology for Debug Unit of a Superscalar RISC-V Processor, 2024]. The superscalar variant compounds this with deeper pipelines and richer configuration spaces.

Stress testing pushes the core past what compliance suites reach, targeting **data hazards, branch prediction, and resource contention** [Bridging RISC-V Core Verification and PSS, 2025]. The **Portable Stimulus Standard (PSS)** has emerged as a natural fit here, because the same abstract stress scenario can be re-targeted from a single-cycle in-order core to a complex out-of-order superscalar without rewriting the stimulus. Faster checkers also help: a register-change-dump methodology avoids the heavyweight step-and-compare overhead for many functional classes, streamlining the loop [No gain without RISC, 2023]. The pattern across these papers is that RISC-V verification is not one problem — it's compliance, correctness, debug, exceptions, and stress, each with its own best technique, and the mature flow is the one that knows which lever to pull where.
