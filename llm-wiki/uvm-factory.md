# UVM Factory and Overrides

> *You write a testbench once and you want to reuse it a thousand different ways. The driver that pumps AXI today should become a driver that injects errors tomorrow, the sequence that walks address space should become one that stress-tests back-to-back transactions, and you do not want to touch the env code to make it happen. That is the promise of the **UVM factory**: a polymorphism engine that lets one test swap a driver, monitor, or sequence by registering a type override, and the rest of the testbench is none the wiser. It is also one of the hardest pieces of object-oriented programming for newcomers to internalize, because SystemVerilog UVM makes you ask for objects indirectly through `type_id::create()` instead of just constructing them. So how did we get here?*

## What the factory is

The factory is a registry of types. Every `uvm_component` and `uvm_object` that wears the `uvm_component_utils` or `uvm_object_utils` macro gets a proxy — a `type_id` typedef plus a registry class — that lets the factory construct instances of that type by name [Easier UVM for Functional Verification by Mainstream Users, 2011]. When a sequence asks for a transaction with `transaction::type_id::create(name)`, the factory consults its override table; if no override is registered, you get a plain `transaction`, but if `transaction` has been overridden by `extended_transaction_priority`, that is what gets built instead [Easy Testbench Evolution Styling Sequences and Drivers, 2023]. The pattern is the classic Gang-of-Four **factory method** with a string-keyed, runtime-mutable twist [Reuse doesn't come for free, 2016].

The factory exists because real UVM code wants polymorphism without recompilation. The build phase constructs the component hierarchy top-down: each component's `build_phase` calls `create()` for its children, so a single `set_type_override` issued from a test propagates through the whole tree before any `new()` actually fires [Easier UVM for Functional Verification by Mainstream Users, 2011]. The same mechanism is reused inside sequences to mint transactions. Without it, every test variant would require either a forked testbench or a tangle of conditional inheritance; with it, the testbench stays as a stable base class and the test does the overriding [Easy Testbench Evolution Styling Sequences and Drivers, 2023].

## How overrides are used in practice

The two override flavors are **type overrides** and **instance overrides**. A type override rewrites every construction of a given type across the entire testbench; an instance override rewrites only the construction rooted at a specific component path. Edelman and Nishizawa's "Easy Testbench Evolution" walks through the full spectrum in a single paper: a base test, then a simple extended class that overrides driver and sequence by type, then an instance override that swaps only the drivers under `e1` and `e2`, and finally a combined override of driver, sequence, and transaction to support out-of-order completion [Easy Testbench Evolution Styling Sequences and Drivers, 2023]. The driver, often thought of as a static testbench fixture, becomes "a specialized driver per simulation" once the factory is in play.

This same lever unlocks testbench scalability on highly parameterized DUTs. The "Rockin' the polymorphism" paper shows that when a DUT is scalable, configurable, extensible, and parameterized, the testbench can only match those characteristics by leaning heavily on polymorphism — including an innovative use of the string-based factory to choose among a family of components at runtime [Rockin' the polymorphism for an Elegant UVM testbench Architecture, 2018]. More recently, Intel's "Taming Configuration Complexity" applies a unified random configurable sequence pattern plus hierarchical sequence abstraction and factory overrides to server CPU power-management IP, with the explicit goal of reducing development effort and improving reuse across dynamic state transitions [Taming Configuration Complexity, 2026]. Even the humble debug-verbosity problem gets a factory twist: the same paper notes that overriding report objects lets you target verbosity at specific transactions rather than the whole BFM [User Programmable Targeted UVM Debug Verbosity Escalation, 2025].

## Pitfalls, parameters, and Python

The factory is not free of sharp edges. Parameterized IP is the canonical headache: while parameters work fine for SystemVerilog modules and interfaces, the class-based HVL side stumbles over the HDL-to-HVL virtual-interface connection, the factory, and parametric coverage — a long-standing problem that one Infineon paper consolidates and extends with new recommendations [Working within the Parameters that SystemVerilog has constrained us to, 2024]. The factory's interaction with parameterized types is finicky enough that design-pattern approaches like **chain of responsibility** are now proposed explicitly to scale UVM drivers without breaking existing tested code as specifications evolve [Chain of Responsibility Design Pattern for scalable UVM drivers, 2025].

There is also a sustained argument that the factory is overused. Samsung's "Saving and Restoring Simulation Methodology" exploits the factory to skip repeated initial-setup sequences across many SoC tests, reducing simulation turnaround time — a productive use, but one that depends on the factory as a checkpoint mechanism rather than as a polymorphism tool [Saving and Restoring Simulation Methodology using UVM Factory Overriding, 2020]. On the bleeding edge, the `pyuvm` Python implementation of IEEE 1800.2 re-derives the factory cleanly: any descendant of `uvm_void` is automatically added to the factory, objects are created via `my_component.create(...)`, you can sidestep the factory with a plain instantiation, and overrides go through the `uvm_factory` singleton [Verification Learns a New Language, 2021]. The pattern is the same; the boilerplate is gone. The factory, like most things in UVM, is best understood as a design pattern that the library insists on formalizing — useful precisely to the extent you actually need runtime polymorphism, and a tax when you do not.

## Grounded in these DVCon papers

- **Easy Testbench Evolution Styling Sequences and Drivers** (2023, DVCon Japan) — Rich Edelman and Kento Nishizawa. A practitioner's tour of factory polymorphism across transactions, sequences, and drivers, with full type- and instance-override examples.
- **Verification Learns a New Language: An IEEE 1800.2 Implementation** (2021, DVCon US) — Ray Salemi and Tom Fitzpatrick. Introduces `pyuvm`, re-implementing the factory, FIFOs, and config_db in Python.
- **Saving and Restoring Simulation Methodology using UVM Factory Overriding to Reduce Simulation Turnaround Time** (2020, DVCon US) — Ahhyung Shin, Yungi Um and Youngsik Kim. Uses factory overrides to skip repeated initial-setup sequences and cut SoC simulation TAT.
- **Rockin' the polymorphism for an Elegant UVM testbench Architecture for a Scalable, Highly Configurable, Extensible DUT** (2018, DVCon US) — Michael Baird and Frank Verhoorn. Polymorphism plus string-based factory to match a highly parameterized DUT.
- **Statically Dynamic or Dynamically Static?** (2017, DVCon US) — Sachin Scaria and Sreenu Yerabolu. Uses class type override to make SVA coding modular and reusable at SoC level.
- **Reuse doesn't come for free — learnings from a UVM deployment** (2016, DVCon Europe) — Sumeet Gulati, Srinivasan Venkataramanan and Azhar Ahammad. Lessons from a mobile-audio-chip UVM rollout, including reuse limits the factory cannot fix.
- **Easier UVM for Functional Verification by Mainstream Users** (2011, DVCon US) — John Aynsley. Minimal concept set for hardware engineers, including factory and configuration coding guidelines.
- **From the Magician's Hat: Developing a Multi-Methodology PCIe Gen2 VIP** (2011, DVCon US) — Amit Sharma, Abhisek Verma and Varun S. Early multi-methodology VIP that exercises sequencer APIs and objections alongside factory reuse.
- **User Programmable Targeted UVM Debug Verbosity Escalation** (2025, DVCon US) — Sam Mellor. Targets debug verbosity at specific transactions rather than the whole BFM using factory-overridable report objects.
- **Working within the Parameters that SystemVerilog has constrained us to** (2024, DVCon US) — Salman Tanvir and David Crutchfield. Consolidates the parameterized-IP pain points across virtual interfaces, factory, and parametric coverage.
- **Chain of Responsibility Design Pattern for scalable UVM drivers** (2025, DVCon India) — Chandana K N and Suresh Gandhi S. Proposes chain-of-responsibility to scale drivers without breaking existing tested code.
- **Taming Configuration Complexity: A UVM-Based Approach To IP Verification** (2026, DVCon US) — Bhaskar Vedula, Stephen P. Haake and Chandrakanth N. Betageri. Applies unified random configurable sequences, hierarchical abstraction, and factory overrides to server CPU power-management IP.
